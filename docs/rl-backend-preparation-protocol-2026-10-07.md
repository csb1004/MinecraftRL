# RL 초기 합성곱 준비 — 실행 조건

사용자 ‘계속 해봐’에 따라 첫 추론 지연을 조사한다. `ce-debug` 절차를 적용하되 재승인·worktree·subagent·Git 작업은 하지 않는다.

관측: 기존 첫 추론은 9.42~137.24초, 느린 시행의 20초 stack은 첫 Conv2d 내부였다. 동일 WSL 환경의 독립 합성곱은 첫 2.107초/반복 약 .003초, 실제 모델·저장 화면 재생은 첫 2.106초/반복 .040~.041초였다. 첫 레이어에 대부분 비용이 집중되고 cuDNN cnn/ops 하위 라이브러리가 첫 호출 뒤 매핑된다. NVIDIA cuDNN 8 FAQ도 지연 로딩을 설명한다: https://docs.nvidia.com/deeplearning/cudnn/archives/cudnn-850/developer-guide/index.html

확신의 경계: 지연 초기화가 180초 제어 예산 안에 들어가는 경계는 확인됐다. **기존 100초대 지연의 정확한 CUDA/OS/I/O 원인은 미확정**이며 이를 단순 cuDNN 2초와 동일시하지 않는다. 초기화의 계산 비용을 없앴다는 주장을 하지 않는다.

첫 진단은 LD_LIBRARY_PATH를 누락해 중단됐다. 정책 실행기는 이미 올바른 `/usr/lib/wsl/lib`를 설정한다. 이 잘못된 환경의 결과는 지연 비교에서 제외하고 로그를 보존한다. 첫 실제 모델 진단의 행동 비교도 ndarray와 JSON 비교 오류로 중단됐다. jsonable 변환으로 수정 후 재생 10행동/특징/logp가 원본과 정확히 일치했다. 게임 실행은 아직 하지 않았다.

변경은 한 요인: RLPolicy 생성 중, 실제 첫 Conv2d를 동일한 batch=2·128×128·NHWC에서 전환한 stride의 영 입력으로 한 번 호출한다. 모델의 순환 경로·목표·행동 샘플러·월드는 호출하지 않는다. 모델 가중치·난수·학습 상태를 바꾸지 않는다. backend 준비 시간은 별도 파일에 기록하고, 완료된 뒤 기존 환경 초기화와 제어를 수행한다. 모델 준비 후 STOP이 관측되면 월드 reset 전에 중단한다. 초반 MSE 채택 기준·보상·actor·180초 제어 제한은 바꾸지 않는다.

검증 순서:

1. 알려진 가중치/난수/학습 모드 보존과 비유한 출력 차단 단위 검사를 먼저 실패시키고 구현한다.
2. 새 프로세스의 실제 모델로 준비 시간, 첫 특징 시간, 동일 저장 화면의 특징·행동·logp·순환 상태·Torch CPU/CUDA RNG를 확인한다. 원본 10행동과 정확히 일치해야 한다.
3. 기존 고정 세계 104869와 104831을 각각 한 번, 같은 부모 78회 checkpoint/embedding으로 최대 180초 실행한다. 이는 학습 제외 실행 준비 진단이며 새 정책 성능 비교가 아니다. 첫 제어 추론이 각각 2초 미만인지 사전에 확인 기준으로 정한다. 달성하지 못해도 표본을 버리거나 성공할 때까지 반복하지 않는다.
4. 마지막 별도 시행은 backend 준비 시작 직후 STOP을 주어 정책 전달 0, 월드 reset 차단 또는 감독기의 소유 프로세스 종료를 확인한다. 이미 진행 중인 native CUDA 호출을 즉시 선점한다고 가정하지 않는다.
5. 원시 로그·서버 인벤토리·제어 제한·중단 경계·해시·전체 회귀 검사를 확인한다. 최종 평가 5시드는 사용하지 않고, 정책/가치함수 optimizer 갱신은 0이다.

기준 미충족 시 결과를 기록하고 적용 범위를 재검토한다. 합성 계산과 저장 화면 재생을 실제 Minecraft 성공으로 계산하지 않는다. 전역 드라이버·CUDA 설정·WSL 설정은 수정하지 않는다.

추가 기록: 첫 실제 시도는 Java 버전 검사 20초 초과로 blocked/0 행동이며 backend 준비에 도달하지 않았다. 같은 격리 환경의 Java 8.0_472는 후속 진단에서 3.754902초, exit 0으로 응답했다. 설치 손상 증거는 없고 최초 지연 원인은 미확정이다. 원본 결과 폴더를 보존하고 별도 recovery 폴더에서 준비 실패만 한 번 복구한다. Java 검사 제한 20초와 사전 등록한 두 게임 시드는 유지한다. 추가 준비 실패나 실제 게임 결과에 따른 재시도는 하지 않는다.
