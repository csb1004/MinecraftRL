# 공통 목표 조건부 S2 — 구현과 실제 개발 비교

상태: 성능 비교·독립 원본 감사·별도 실제 STOP 재검증·종료 진단 기록 수정 완료. STOP 유지.

공통 목표 입력과 조건부 학습 경로는 구현·실행됐다. 그러나 **추가 RM 입력을 쓰면 일관되게
성능이 좋아진다는 결과는 얻지 못했다.** 비선형/RM 제거 후보의 관측 완료율이 가장 높았지만,
작은 개발 표본과 초기 화면 차이 때문에 일반화나 인과적 우위를 확정하지 않는다. 후보 자동 승격 없음.

## 구현 범위

- 대상·결과·수량·선행 조건·진행을 보존하는 상태 변화 목표 계약을 추가했다. RM 노드 이름을 학습 특징으로 쓰지 않는다.
- 정책/가치 함수에 단계·수량·진행·관측 유효성·최근 행동 등 21개 특징을 실제 연결했다.
  대상은 기존 MineCLIP 목표 임베딩 경로로 전달한다. 계약의 모든 문자열/선행 조건이 벡터 입력이라는 뜻은 아니다.
- frozen 공식 STEVE-1 backbone 뒤 선형 head와 64 hidden 비선형 residual adapter를 비교했다.
  비선형 actor의 adapter는 265,600개 파라미터다. 기존 출력층도 학습 대상이며 backbone/CNN은 업데이트하지 않았다.
- `off`는 **추가 RM 특징만 제거**한다. 기존 목표 임베딩·상위 큐·완료 기준은 모든 조건에 남는다.
- 실제 결과가 없는 정체를 종료/학습 표본으로 보존하고, 외부 STOP·기술 오류는 학습에서 제외했다.
  반복 행동 자체에는 실패/보상 판정을 하지 않는다. 600tick 정체/300tick 미회수는 개발 한도다.
- 현재 실행 capability는 나무/흙 수집이다. 제작·도구·돌·새 지식 습득까지 구현했다고 주장하지 않는다.

명세: [고정 프로토콜](specs/2026-11-01-general-rm-s2.md), [실행·별도 학습 안내](general-rm-s2-usage.md).

## 실제 학습

새 train 12회에서 3,797행동을 수집했다. 완료 11회, 정체 실패 1회이며 과거 P4/개발 자료를 학습하지 않았다.
초기 행동이 같은 네 조건 모두 저장 행동 확률을 **최대 오차 0**으로 재현한 뒤 자료를 공유했다.
같은 shuffle/optimizer seed 110101/예산으로 PPO를 실행했고, 모두 42회 업데이트 후 KL 한도로 조기 종료했다.
따라서 수집/검증한 3,797개와 실제 optimizer가 사용한 **후보당 1,344개**를 구분해야 한다.
한 번의 수집→업데이트이며, 반복 on-policy 학습이나 자동 지속 학습 완료가 아니다.

| 학습 자료 구분 | 행동 수 |
|---|---:|
| 나무 탐색 | 745 |
| 나무 접근 | 272 |
| 나무 상호작용/채굴 | 1,035 |
| 나무 결과 회수 | 890 |
| 흙 macro 전체 | 855 |

흙 macro의 레거시 로그 단계 이름은 `collect`지만 나무 회수 경험으로 합산하지 않았다.
수량 1/2, 진행률 0/0.5, 유효 정체 실패가 포함됐다. 추가 버튼/거리 보상은 없고 상위 목표 완료당 보상 1이다.
학습 설정·gradient/손실·KL·실제 가중치 변화·체크포인트 해시는 `training/*/training.json`에 보존했다.

## 개발 결과

학습 밖 다섯 seed에서 초기 정책과 네 후보를 각각 한 번 실행했다. 최대 1,200행동/180초이며
시드별 실행 순서를 회전했다. 아래 숫자는 **완료 또는 종료까지 실제 행동 수**다.
실패의 더 짧은 행동 수를 효율 향상으로 해석하지 않는다.

| 과업 / seed | 초기 | 선형 off | 선형 on | 비선형 off | 비선형 on |
|---|---:|---:|---:|---:|---:|
| 나무 1 / 81102001 | 성공 215 | 실패 621 | 실패 622 | 성공 444 | 성공 496 |
| 흙 1 / 81102003 | 성공 224 | 성공 62 | 성공 107 | 성공 268 | 성공 123 |
| 나무 3 / 81102007 | 성공 551 | 성공 523 | 성공 368 | 성공 360 | 성공 375 |
| 나무 1→흙 1 / 81102009 | 실패 600 | 실패 600 | 성공 679 | 성공 644 | 실패 690 |
| 흙 1→나무 1 / 81102013 | 성공 695 | 성공 518 | 성공 717 | 성공 359 | 실패 600 |
| 전체 프로그램 완료 | **4/5** | **3/5** | **4/5** | **5/5** | **3/5** |
| 완료 목표 / 실제 실행한 목표 | 5/6 | 4/6 | 6/7 | 7/7 | 3/5 |
| 미실행 목표 | 1 | 1 | 0 | 0 | 2 |

나무 3개 조건은 모든 조건이 실제 원목 3개를 얻었다. on 조건에서는 1/3·2/3 진행률도 입력에 연결됐다.
양방향 목표 전환은 실제 게임에서 성공 사례가 나왔다. 완료 틱에 다음 목표를 활성화하고,
다음 행동부터 새 목표를 사용했음을 원본 기록과 대조했다. 동시에 여러 아이템을 주운 경우는
목표 수량을 초과할 수 있지만, 완료 후 이전 목표의 새 행동을 보낸 것으로 계산하지 않는다.

수량 3개 성공은 외부 RM이 3개까지 정책 실행을 계속한 효과일 수도 있다. 목표 순서 성공 역시
외부 큐와 기존 목표 임베딩 전환 아래에서의 수행이다. 정책이 새로운 수량·계획·임의 RM을
스스로 이해하거나 새로운 게임 메커니즘을 학습했다는 증거로 확대하지 않는다.

## 추가 RM 입력은 얼마나 사용됐나

실제 train 특징 34개를 고정하고 단계/수량만 바꾼 CPU 반사실 검사를 했다.
버튼/카메라 주변 분포의 최대 TV이며, 실제 게임 성공률이나 타당한 대안 행동 평가가 아니다.
특히 단계 교체는 장면과 모순되는 조건을 만들 수 있다.

| 후보 | 단계 교체 최대 TV | 수량 교체 최대 TV | 전체 업데이트 최대 TV |
|---|---:|---:|---:|
| 선형 off | 0 | 0 | 0.12849 |
| 선형 on | 0.000746 | 0.0000193 | 0.12910 |
| 비선형 off | 0 | 0 | 0.12610 |
| 비선형 on | 0.000982 | 0.0000432 | 0.12879 |

연결과 실제 가중치 업데이트는 확인됐다. 다만 이 검사에서 새 단계/수량 입력의 직접 효과는
전체 출력층 업데이트 효과보다 작았다. 비선형 계층 추가만으로 RM 활용이 충분해졌다고 결론 내리지 않는다.
actor와 critic 구조를 함께 비교했으며, 단일 optimizer seed의 작은 첫 업데이트 실험이다.

## 실패와 남은 병목

1. **결과 회수 경험과 관측의 부족.** 선형 off의 첫 나무 실패는 서버 원목 파괴 1회/인벤토리 0이었다.
   비선형 on의 마지막 흙 실패 화면에는 파인 땅과 떨어진 흙 아이템이 보이지만 실제 획득은 0이었다.
   후자는 시각 근거이며, 고정 관측기로 흙 파괴 횟수/떨어진 아이템 위치까지 검증한 것은 아니다.
2. **새 조건 입력의 활용이 약하고 성능 효과가 일정하지 않다.** 입력 연결 오류가 해결됐다는 것과
   필요한 상황에서 그 입력을 잘 사용하도록 학습됐다는 것은 다르다. 출력층 전체를 바꾼 효과와 구분해야 한다.
3. **스킬 간 단계 의미의 정밀도가 다르다.** 흙은 세부 단계가 관측되지 않아 전체 macro를 `interact`로 표시한다.
   나무의 확인된 채굴 단계와 동일한 특징을 쓰는 한계가 있다. 다음 계약에서는 세부 단계도 unknown/validity로
   명시하는 방식을 검증해야 한다. 이 한계가 이번 실패를 일으켰다고 확정하지 않는다.
4. **학습량/분포와 초기 비교 통제.** 실제 최적화 표본은 1,344개뿐이고 연속 on-policy 업데이트가 없다.
   수량·순서 조합의 성공/실패 및 회수 상황을 더 다양한 초기 상태에서 학습·검증해야 한다.

다음 판단 순서는 시작 월드/렌더 준비 통제 → 공통 회수 상황과 단계 unknown 계약 →
기존 출력층 보존 여부/조건부 계층 학습 범위를 분리한 새 프로토콜이다. 현재 개발 자료를 다시 학습에
넣고 같은 시드의 결과를 독립 평가로 보고하지 않는다. 버튼 보너스나 특정 지형용 스크립트로 대체하지 않는다.

## 비교의 제한과 실행 측정

초기 위치·시선·서버 시각은 20쌍 모두 같았으나 첫 화면이 정확히 일치한 것은 11쌍이다.
특히 81102009는 픽셀 차이 약 0.70~2.06%가 있었다. 먼 지형 표시가 달랐으며 chunk/render 준비 차이일
가능성은 있지만 원인 확정은 아니다. 시작 월드 ZIP 복원은 이 실행기에 아직 통합되지 않았다.
따라서 비선형 off의 5/5를 엄격한 동일 시작 상태의 인과적 성능 우위로 주장하지 않는다.
STOP 이후 이 시드의 실제 첫 상태 특징과 고정 head를 교차한 CPU 분석에서, 같은 초기 head에
관측만 바꿨을 때 행동 주변 분포의 최대 TV는 0.0366~0.0437이었다. 같은 초기 특징에서
학습 head만 바꾼 차이는 0.0476~0.0524였다. 추가 context 값은 모두 같았다.
작은 화면 차이도 정책 분포에 영향을 줄 수 있음을 확인했지만, 이는 첫 상태의 반사실 검사이며
전체 실행의 성공/실패 원인을 분리한 결과가 아니다. 새 행동 수집이나 가중치 업데이트는 하지 않았다.

37회 **15,258행동**의 원본 이벤트와 서버 인벤토리를 독립 대조했다. 보상·완료 순서·목표 baseline·
실제 행동·입력 해제·잔존 PID 검사에 불일치가 없었다. 모두 server/client 각각 +1tick, 차이 2tick이었다.
모든 실행의 실제 JAR 해시는 `dac9a1c9cb6b0a7d848559cd7f55d88f7d5bd89db4bad4d5ed35cf8fe9a530a2`로 같았다.

| 측정 | 실행별 통계의 범위 |
|---|---:|
| 추론 중앙값 | 41.98~52.17 ms |
| 추론 p95 | 51.03~58.75 ms |
| 전체 제어 주기 중앙값 | 120.52~159.21 ms |
| 전체 제어 주기 p95 | 146.37~227.58 ms |
| PyTorch peak allocated 최대 | 1,915.00 MiB |
| 장치 전체 샘플링 VRAM 최대 | 2,787 MiB |

이는 모든 행동을 합친 하나의 p95가 아니라 실행별 통계의 최소/최대다. 장치 VRAM에는 다른 프로세스도 포함되고
짧은 peak를 놓칠 수 있다. 총 제어 시간은 2,240.35초이며 게임 초기화/가중치 검사 시간은 별도다.
환경은 로컬 Windows의 WSL Ubuntu-24.04, Python 3.10.14, torch 2.0.1, MineRL 1.0.0, GTX 1060 3GB다.
서버 관측을 RM/context에 사용한 조건이며 영상 전용 성능이 아니다.

## STOP와 사후 기록 수정

첫 STOP 준비는 공식 가중치 해시 bridge의 120초 timeout으로 행동 0에서 차단됐다.
그때 대용량 원본 감사가 병행되고 있었다. 이를 실제 STOP 성공/실패 표본으로 세지 않는다.
분석 종료 후 동일 bridge/제한으로 재검사했으며 steve1.weights는 9.87초에 원본 해시를 재현했다.
[STOP R1 부록](specs/2026-11-01-general-rm-s2-stop-r1.md)에 따라 동일 후보/프로그램의 STOP 진단만 별도 실행했다.
원래 배치의 실패 기록과 없는 completion receipt를 성공으로 덮어쓰지 않는다.

실제 10행동 뒤 STOP 검사는 **통과**했다. 요청 가시화/ack 이후 새 행동 각각 0,
입력 해제와 held keys 0, 잔존 소유 PID 0, worker exit 2(정상 취소)를 확인했다.
ack 지연은 약 17.74ms, 요청 시작부터 ack까지 상한은 66.02ms다. 단일 진단 측정이며
성능 표본에 합산하지 않는다. 성능 37회는 재실행하지 않았고 STOP 파일을 유지했다.
STOP 전후 고정 파일 152개와 소스 snapshot 128개가 일치했으며 공식 가중치/연구 명세도 같았다.

이후 종료된 목표의 진단 정보가 지워지던 `ResultMonitor` 문제를 수정했다. 큐가 완료/차단돼
active가 없어지면 마지막 목표와 진행 근거를 보존하고, 새 목표가 활성화될 때 초기화한다.
수정 전 회귀 검사에서 두 실패를 재현했고, 수정 후 관련 **79개 검사**가 WSL에서 통과했다.
고정 소스 중 사후 변경은 `semantic_goal.py` 하나이며, actor/context 특징은 변경하지 않았다.
성능/STOP에 사용한 소스는 `source-at-game`으로 보존한다. 수정 후 실게임은 재실행하지 않았으므로
보고한 성능을 수정된 코드에서 재측정한 결과로 해석하지 않는다.
