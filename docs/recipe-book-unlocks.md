# 레시피북 해금·표시·제작 조건

기준은 현재 설치된 MineRL의 Minecraft Java **1.16.5**다. 최신 Java/Bedrock에 그대로
적용한다고 가정하지 않는다. 공식 [제작 안내](https://www.minecraft.net/en-us/article/how-craft)는
인벤토리2×2와 작업대3×3, 레시피북 사용을 설명한다. 아래 세부 조건은 실행에 사용하는
JAR에 들어 있는 해당 버전의 원본 데이터와 설치된 게임 소스를 직접 확인한 결과다.

## 언제 레시피가 추가되는가

`data/minecraft/advancements/recipes/`의 각 JSON은 조건(criteria), 충족 방식(requirements),
해금할 레시피(rewards.recipes)를 정한다. 보통 관련 재료의 인벤토리 변화로 해금되지만
모두 동일한 규칙은 아니다. 전부 획득 재료 목록만으로 추측하면 안 된다.

| 레시피 | 1.16.5의 자연 해금 조건 | 제작에 별도로 필요한 것 |
|---|---|---|
|참나무 판자|`minecraft:oak_logs` 태그 재료 획득|해당 원목1 → 판자4|
|막대기|판자 태그 재료 획득|판자2 → 막대기4|
|작업대|판자 태그 재료 획득|판자4 → 작업대1|
|나무 곡괭이|막대기 획득|판자3·막대기2 및 작업대3×3|
|참나무 보트|물 블록에 들어감|참나무 판자5 및3×3|
|상자|차 있는 인벤토리 슬롯10개 이상|판자8 및3×3|

해금 조건의 `has_the_recipe`는 이미 해당 레시피가 해금된 경우의 별도 충족 경로다.
이를 “아직 모르는 레시피를 알아야 해금된다”는 순환 선행 조건으로 읽지 않는다.
현재 예시의 requirements 내부 배열은 OR다. 데이터팩·서버 규칙이 바뀌면 다시 확인한다.
해금은 조건 이벤트와 플레이어 이력에 따른 상태다. 현재 인벤토리에 재료가 있다는 이유만으로
해금됐다고 추정하지 않고 실제 서버 recipeBook을 읽는다. 재료를 소비한 뒤에도 해금 상태는
남을 수 있으며, 이번 실험에서 강제 해금 명령은 사용하지 않는다.

이번 원본 월드에는 판자·막대기·작업대·참나무 반블록이 해금돼 있고 곡괭이는 미해금이다.
실제 저장 advancement에 판자 획득에 따른 `has_planks` 완료가 있다. 해금은 플레이어의
`recipeBook.recipes`에 저장되며 현재 프로젝트는 이 데이터와 advancement를 함께 복원한다.
`scripts/inspect_recipe_unlocks.py`가 JAR 해시·버전·원본 규칙과 level.dat/playerdata를 읽어
비교 가능한 JSON으로 남긴다. 원본 기록은 `results/recipe-book-source-unlocks.json`이다.
보트·상자 원본 조건은 `results/recipe-book-extra-unlock-rules.json`에 별도 보존했다.

## 해금돼도 화면에 없거나 만들 수 없는 이유

게임의 `RecipeList.canCraft`는 **해금 여부 + 현재 칸 크기에 맞는지 + 재료 충분 여부**를
구분한다. 현재 탭·검색·페이지와 “제작 가능한 것만” 필터도 표시 목록에 영향을 준다.
따라서 책에서 안 보인다고 바로 미해금으로 판정하지 않는다. 3×3 레시피는2×2 책에
표시되지 않을 수 있으며, 해금돼도 재료가 부족하면 제작할 수 없다.

`ServerRecipePlacer.place`는 서버에서도 해금 여부를 확인한다. 재료가 없는 경우 표시되는
유령 배치는 실제 재료 투입이나 획득이 아니다. 현재 원본의 `doLimitedCrafting=false`는
책의 해금 검사를 없애는 설정이 아니다. 이 조건에서 수동 배치와 책 사용을 동일시하지 않는다.

## 클릭의 의미와 제어에 반영한 사항

`RecipeBookGui.mouseClicked`의 정상 책 클릭은 서버에 레시피 배치를 요청한다.
Shift를 누르면 가능한 수량의 배치를 요청한다. 결과 칸의 Shift+클릭은 가능한 제작을
반복하는 별도 정상 동작이다. 일반 책 클릭도 같은 레시피가 이미 배치돼 있으면 투입량을
늘릴 수 있으므로 무조건 재시도하지 않는다.

이번 GUI 보조는 기존 빈 조합 칸에서 단일 레시피 버튼을 한 번 선택하고 서버 응답을
기다린다. 실제 칸의 재료·배치·수량과 결과 미리보기를 검사한 뒤 결과를 한 번 꺼낸다.
미리보기나 해금 알림을 실제 획득으로 세지 않는다. 서버 확정·남은 재료·저장 NBT로
최종 완료를 판단한다. 해금/재료/표시 조건이 맞지 않으면 다른 레시피를 대신 실행하지 않는다.

## 3×3에 필요한 다음 조건

책의 자동 배치 경로는 작업대의 RecipeBookContainer에도 쓰이지만, 현재 실험 코드는
인벤토리2×2만 다룬다. 작업대 배치·접근·열기,9개 입력 칸 관측, 실제 레시피 크기/종류,
페이지·그룹 선택, 정리/중단을 확장해야 한다. 코드상 지원 경로가 있다는 것을 실제3×3
실행 성공으로 보고하지 않는다.

아무 제작물도 없는 상태에서 작업대1·막대기4·나무 곡괭이1을 만들려면 판자 합계9개가
필요하다(4+2+3). 원목3개를 판자12개로 만들면 충분하며, 정상 완료 후 판자3·막대기2가
남는다. 현재 판자4 저장본은 이 연속 목표를 완수하기에 부족하다. 재료 부족을 책이나
정책 실패로 오분류하지 않고, 추가 자연 수집 또는 분리된 재료 fixture 조건을 먼저 정한다.
