# LOGO 판별 함수·구체적 문구의 실제 게임 비교 P3

2026-10-31, Windows 로컬 GTX 1060 3GB / WSL Ubuntu-24.04.
[사전 고정 프로토콜](specs/2026-10-31-logo-conditioning-p3.md)에 따른 개발 비교다.
**판별 함수의 실제 연결은 검증됐지만, 새 문구/전환의 수집 성공률 개선은 확인되지 않았다.**
LOGO 전체 알고리즘 재현, 외부 LLM API 자동 생성, RL 학습 효과를 검증한 실험이 아니다.

재현한 조건이라고 해석하지 않는다. 문구·벡터·실제 전환 시점은 각 은행과 `rm-rows.json`에 있다.

## 무엇을 검증했는가

`scripts/analyze_rm_logo.py`로 원본 이벤트 전체를 스트리밍 감사했다. 생성된 함수를 재실행하는
것에 더해 기존 독립 `WoodReward`로 서버 인벤토리 성공/보상을 다시 계산했다.

- generated predicate before/after, 원시/안정화 RM 단계, 실제 목표 문구와 벡터 해시 일치.
- 실제 dispatch한 행동과 RNN commit 로그, 보상, terminal, 연속 서버 tick 일치.
- STOP acknowledgment/최종 성공/terminal 이후 새로운 dispatch 없음.
- 실행 14회는 neutral 명령·서버 held key 0 확인. 낙사 1회는 terminal 환경이 추가 step을 거부하므로
  neutral/held key는 **미측정**이며 실제 사망·종료와 소유 자식 PID 0을 확인. 성능 실패로 포함.
- 전체 15회 소유 자식 PID 0, worker exit 0. 고정한 136개 파일의 해시 변경 0.
- 실행 전 WSL 관련 테스트 67개, PowerShell 구문 검사 통과. 테스트 통과를 실게임 성공으로 대체하지 않았다.

별도 STOP 진단은 성능 표본에 포함하지 않는다. 첫 실패와 기술 수정 후 재검사는 아래
중단 검증 항목에 구분한다. 성능 종료 시점의 136개 해시 검사는 당시의 증거이며,
이후 STOP 수정이 적용된 현재 소스와 동일하다는 뜻은 아니다.

## 실패에서 확인한 것

### 1. C / 81031001: 채굴 후 미획득과 탐색 재진입

238번째 관측에서 원목 대상/접근 가능 판정, 241번째 행동부터 수집 문구를 사용했다.
실제 원목 채굴은 1,121번째 행동에서 확인됐다. 그러나 원목 획득 없이 1,164번째 행동부터
다시 탐색 문구로 바뀌었고, 1,211행동/180초에서 끝났다.

그 전환 직전 predicate는 `log_broken=true`, `item_acquired=false`, `target_known=false`였다.
기존 관측기의 파괴된 대상 기억이 약 40tick 후 사라지면, 현재 adapter는 줍기 시도를 유지하지 않고
search로 되돌릴 수 있다. **관측 힌트의 수명과 아직 끝나지 않은 하위 목표를 구분해야 한다.**
채굴이 시간 제한 후반에야 된 점도 함께 고려해야 한다. 탐색 복귀를 막았으면 성공했을지는
이번 실험으로 증명하지 못했다. 비교 중 정책/전환 규칙은 수정하지 않았다.

채굴 접수 537tick, 동일 대상 연속 접수 최장 60tick, inventory 화면 7/1211tick이었다.
접수 횟수는 블록 파괴 증거와 다르며, 이 실패를 inventory 화면 체류 하나로 설명할 근거는 없다.

### 2. B / 81031007: 낙사

12번째 관측에서 원목 대상을 등록했지만 접근/채굴 전, 84번째 행동에 사망했다.
높이는 최대 약 65.25에서 40으로 내려갔고 서버 최근 피해 유형 `fall`, 생명력 0을 확인했다.
문구를 구체화하는 것만으로 이동 안전성이 확보되지 않는다. OOM이나 실행기 오류가 아니다.

### 3. C / 81031007: 알려진 대상에 대한 접근 정체

17번째 관측에서 대상을 등록하고 20번째 행동부터 수집 문구를 사용했다.
높이 39 부근까지 내려간 뒤 180초/1263행동 동안 생존했지만 접근 가능/원목 채굴/획득 판정은 없었다.
수평 이동 경로는 약 94.14블록이었다. 움직인 거리 자체가 목표 접근의 진전은 아니었다.

이 조건은 이미 알고 있으나 접근 불가능한 목표에서 벗어날 별도 정체·복구 전이가 없다.
새 성공 판별 함수는 그런 복구 행동이나 이동 스킬을 자동으로 학습시키지 않는다.

## 조건 비교의 한계

- 모두 개발 시드이며 이번 결과를 보고 고른 최종 평가 조건이 아니다. 작은 5시드 결과로
  일반화나 통계적 우월성을 주장하지 않는다.
- 모든 시드에서 세 조건의 초기 좌표/시선은 같았다. 초기 PNG까지 세 조건이 같았던 시드는
  81031003과 81031009, **2/5개**다. 시드만으로 관측 과정 전체가 동일하다고 가정하지 않는다.
- 81031013의 C는 처음부터 `root`만 사용했다. 이 성공/시간 차이를 탐색 전환의 효과로 세지 않는다.
- 초기 화면이 같았던 81031003에서는 새 조건의 시간이 짧았지만, 81031009에서는 A가 더 짧았다.
- 같은 A 문구의 과거 P2 성공은 3/5, 이번 P3는 5/5였다. 별도 실행의 변동성을 드러내는 참고이며
  두 배치를 하나의 동시 대조 실험처럼 합치지 않는다. 초기 조건 안정화/반복 측정이 더 필요하다.
- A/B는 고정 문구를 비교하지만 validator 실행 구현도 다르다. 최종 성공 의미의 동등성은
  과거 replay와 이번 실제 데이터에서 검사했다. B/C는 같은 함수·은행에서 전환 사용 여부가 다르다.
- 목표 임베딩이 행동 분포에 영향을 줄 수 있어도, 사람이 읽기에 더 구체적인 문구가 항상
  해당 정책에서 더 나은 행동을 유발한다는 보장은 없다. 현재 결과로 CNN 또는 CLIP의 학습 실패를 단정하지 않는다.
- 배우는 과정의 실험이 아니다. 가중치를 고정했으므로 새 경험을 통한 RL 개선을 주장할 수 없다.
  관측은 privileged server RM이며 영상 전용 실행 성과도 아니다.

## 중단 검증

별도 seed 81031999, `logo-staged`, 실제 transition 10회 이후 STOP을 요청했다.

첫 진단은 **실패**다. 요청 가시화 후/ack 이후 새 정책 dispatch 각각 0, ack 지연 약
37.1ms(요청 쓰기 시작 기준 상한 약 83.8ms), 실제 입력 해제와 held keys 0, 소유 자식 PID 0을
확인했지만 worker exit **-15**로 강제 종료됐다. 성능 배치 드라이버 exit 1은 이 마지막
진단 실패 때문이며 15회 성능 결과를 취소/재실행하지 않았다. 원본은
`results/rm-logo-conditioning-20261031/stop-probe-audit.json`에 보존했다.

원인은 RM 실행기가 기존 `on_control_closed` callback을 연결하지 않은 것이다. 환경 종료를
기다린 뒤 `execution_valid=True`일 때만 종료 marker를 만들었으므로, 취소에는 marker가 없었다.
이미 입력을 해제했어도 환경·인터프리터 종료 지연이 기본 10초를 넘으면 감독자가 강제 종료했다.
첫 진단에는 MineRL kill command timeout 로그가 있고 환경 정리를 포함한 cleanup이 약 7.55초였다.

[P3.1 부록](specs/2026-10-31-logo-stop-finalization-p3-1.md)에 따라 입력 해제·정책 close 이후,
환경 close 전에 callback으로 제어 종료 marker를 쓰도록 수정했다. 검증된 취소 종료에도
기존의 제한된 정리 유예(현재 기본 60초)를 적용하며 새 행동은 계속 금지한다. 검증되지 않은
STOP에는 기존 10초 제한을 유지한다. 재현 테스트는 수정 전 실패, 수정 후 관련 **72개 통과**.
실패한 release/정책 close에는 유예를 열지 않고, 정상 marker가 있어도 수동 STOP에는 별도의
취소 경계 증거가 필요하며, 취소 정리 유예도 만료되는 것을 검사했다.

성능 종료 후 고정 목록 중 바뀐 실행 코드는 `src/minecraftrl/rm_conditioning.py` 1개다.
변경 후 별도 snapshot/해시를 `results/rm-logo-stop-r1-20261031`에 남겼다.
동일 기준으로 STOP만 1회 재검사하여 **통과**했다.

| 항목 | 첫 진단 | 수정 후 별도 재검사 |
|---|---:|---:|
| 완료 행동 수 | 10 | 10 |
| 요청 가시화 / ack 이후 새 행동 | 0 / 0 | 0 / 0 |
| 요청 가시화 → ack | 37.1 ms | 18.7 ms |
| 요청 시작 → ack 상한 | 83.8 ms | 58.3 ms |
| 입력 해제 / held keys | 확인 / 0 | 확인 / 0 |
| 잔존 소유 PID | 0 | 0 |
| worker exit | -15 (강제 종료) | 2 (정상 취소 반환) |
| 전체 진단 | 실패 | 통과 |

수정 후 취소 제어 종료 marker와 60초 finalization deadline이 기록됐고 timeout은 없었다.
cleanup은 약 7.58초, STOP 가시화부터 helper 완료까지 약 12.49초였다. 제어 종료가 확인된 뒤
환경/인터프리터 종료에 10초보다 긴 시간이 필요하다는 증거와 일치한다. close 오류도 없었다.
이 1회 통과를 모든 가능한 종료 상황의 보장으로 일반화하지 않는다. 최종 STOP 유지.
원본 결과는 각각 `results/rm-logo-conditioning-20261031/stop-probe-audit.json`,
`results/rm-logo-stop-r1-20261031/stop-probe-audit.json`이다. 두 진단 모두 성능/학습 표본에서 제외한다.

## 다음 개선의 우선순위

1. **미완료 하위 목표 유지:** 채굴한 뒤 아직 얻지 못했다면 관측 대상이 사라졌다는 이유만으로
   탐색으로 돌아가지 않도록 RM 상태/전환 계약을 분리한다. 획득·명시적 실패/정체 판정으로 다음 상태를 결정한다.
2. **도달 불가능/위험 상태의 복구:** 알려진 대상에 대한 접근 진전이 없거나 낙하 위험이 관측될 때
   같은 수집 지시를 유지하는 문제를 별도 조건으로 시험한다. 성공 판별과 복구 선택을 구분한다.
3. **문구 효과와 학습 효과의 분리:** 현재 새 모드를 기본값으로 승격하지 않는다. 기존 기준군을
   보존하고, 상태 전이 변경만을 분리한 비교와 고정 관측에서의 조건 민감도/실제 RL 스킬 학습을 구분한다.

위 내용은 이번 결과에 근거한 후속 개선안이다. 이번 배치의 조건을 소급 변경하거나 실패를 재시도하지 않았다.
