# 판자를 만든 뒤에도 조합을 계속한 원인

## RM이 완료를 무시했는가

수집용 TaskState는 실제 순증가가 목표에 도달하면 completed로 바뀐다.
task_runtime은 다음 추론 전에 이 상태를 검사한다. 기존 실제 순차 수집 실험의
최종 완료 이벤트 이후 추론·정책 dispatch는 0회였다. 독립 회귀 검사도 추가했다.
이 근거는 해당 실행과 검사 범위이며 모든 RM 경합의 부재를 증명하지 않는다.

문제가 된 조합은 다른 경로였다. request.json의 task_session=false가 보여주듯,
craft-probe → run_crafting_probe → run_episode로 실행했으며 TaskState를 사용하지 않았다.
초기 180초 실험은 원래 정책 능력 측정용으로 완료 후에도 계속 실행했다. 이후 추가한
정지 콜백도 수집 RM과 별개였다. 따라서 “조합도 이미 RM이 보호한다”는 해석은 틀리다.

## 정지 콜백도 왜 늦었는가

기존 성공 증거는 같은 관측에서 원목 감소 1·인벤토리 판자 증가 4·서버 제작 통계 증가 4를
모두 요구했다. 완료 보고용 조건을 제작 정책을 계속 실행할지 판단하는 조건으로도 썼다.
그러나 인벤토리와 서버 통계의 갱신은 동시에 도착하지 않는다.

| 정지 실험 시드 | 최초 인벤토리 판자 4 | 통계까지 충족한 witness | 사이의 추가 정책 행동 |
|---|---:|---:|---:|
| 104729 | 263 | 267 | 4 |
| 155921 | 45 | 49 | 4 |
| 196613 | 338 | 342 | 4 |

이전 보고의 추가 행동 0회는 마지막 witness 이후만 계산한 값이다. 인벤토리 최초 달성
이후까지 넓히면 4회였으므로, 즉시 정지를 충분히 검증했다는 인상을 바로잡는다.
초기 무정지 실험에는 전체 witness 이후에도 각각 897/1277/885회의 추가 행동이 있었다.

실패 시드 130363과 262147은 판자 4개가 인벤토리에 동시에 들어온 관측 자체가 없다.
전자는 제작 통계가 step 341에 증가하고 이후 버튼으로 소비됐다. 그 시점 프레임에는
커서에 든 판자가 보인다. 후자는 제작 통계가 step 29에 증가하고 step 39에 버튼 제작
통계가 생겼다. 최종 판자 최대치는 각각 0/3개다. 이들은 completed 후 재실행이 아니라
회수 대기 상태를 인식하지 못해 제작 정책이 계속 실행된 사례다.

## 관측과 실행 경계의 누락

설치된 MineRL EnvServer.getInventoryJson은 player.inventory.mainInventory만 집계한다.
커서 물품과 조합 입력 칸은 포함하지 않는다. 또한 Minecraft Container.onContainerClosed는
커서 물품을 dropItem으로 버리며, PlayerContainer의 입력 칸 정리와 동작이 다르다.
그래서 제작 통계만 보고 성공 처리하거나 창만 닫는 수정은 충분하지 않다.

STEVE-1 act는 화면에서 다음 키보드·마우스 행동을 반환한다. RM 완료 상태를 받거나
종료 신호를 반환하는 계약은 없다. 호출자가 유효한 상태에서만 정책을 호출해야 한다.
LLM 프롬프트를 더 강하게 쓰거나 정책을 반복 호출하는 것으로 이 제어 오류를 해결하지 않는다.

## 수정한 상태 경계

1. crafting: STEVE-1 제작 행동을 허용한다.
2. recovering: 원목 소진과 실재 판자 합계 4를 관측하면 진입한다. 합계는 인벤토리·
   커서·실제 조합 입력만 포함하고 결과 미리보기는 제외한다. 다음 정책 추론·dispatch는
   금지된다. wrapper에도 별도 금지 검사를 둔다.
3. completed 또는 failed: 허용된 정리 입력으로 커서 물품을 확인된 빈 칸에 놓는다.
   정책을 멈춘 상태에서 서버 인벤토리 4개·제작 증가 4·서버 커서 0을 확인한 뒤 창을
   닫는다. 서버와 클라이언트의 인벤토리·제작 통계·커서 비움·닫힌 GUI가 확인돼야 완료다.
   저장 NBT가 최종 관측과 다르면 실험 도구가 성공을 거부한다.

## 실제로 발견한 추가 원인: 클라이언트 예측과 서버 확정의 차이

첫 회수 보조 시도에서 커서를 빈 칸에 놓고 곧바로 닫자 클라이언트는 판자 4개였으나
저장 NBT는 0개였다. 따라서 클라이언트 관측만으로 종료해도 된다는 가정도 폐기했다.
그 실패 로그와 중단한 나머지 시행을 보존했고, 성공 표본에 넣지 않았다.

서버 읽기 전용 모니터를 추가한 130363 재실행에서는 다음 흐름이 직접 관측됐다.

| 시점 | 클라이언트 인벤토리/커서 | 서버 인벤토리/커서 | 서버 제작 통계 |
|---|---|---|---:|
| 정책 step 337 | 0 / 4 | 0 / 0 | 0 |
| 회수 클릭 후 마우스 해제 | 4 / 0 | 0 / 4 | 4 |
| 중립 대기 1–3 | 4 / 0 | 0 / 4 | 4 |
| 중립 대기 4 | 4 / 0 | 4 / 0 | 4 |
| GUI 닫기 후 | 4 / 0 | 4 / 0 | 4 |

저장된 level.dat/playerdata도 판자 4개였다. 실제 네트워크 입력은 서버 처리 큐를 거치고,
클라이언트 GUI는 그보다 먼저 결과를 표시한다. 기존 저장 barrier는 당시의 서버 상태를
정상 저장했지만, 확인하지 않은 입력까지 처리됐다는 보장은 없었다. 단순 지연 시간을
추가하는 대신 **서버 확정 상태를 검사하는 제한된 대기**로 수정했다.
이 관측은 로컬 통합 서버에서 검증한 것이며 외부 서버 호환성을 뜻하지 않는다.

읽기 전용 GUI 관측은 실험용 JAR 사본에만 추가한다. 게임 아이템을 지급·이동·제작하는
API를 추가하지 않으며 회수 입력은 MineRL의 일반 camera/attack/inventory 액션이다.
회수 보조의 행동·관측을 별도로 기록하고 순수 정책 성공과 합치지 않는다.
이 변경은 격리된 조합 실험에 적용하며 일반 대화용 제작 RM 연결을 완료했다고 주장하지 않는다.
