# 조합 지원의 현재 상태

**최신 작업대·3×3 검증:** 레시피 JSON에 따른 공통 실행기로 원목3개→작업대 제작·설치·열기
→곡괭이1·도끼1 보존5/5를 확인했다. 서버 인벤토리와 저장 NBT, 실제 저장 블록 모두 일치했다.
별도 커서 중단 시험에서 새 제작 없이 곡괭이·남은 재료를 보존했다.
명시적 GUI 보조이며 학습 정책 개선은 아니다. 가까운 바닥 배치와 두3×3레시피가 실제 확인 범위다.
일반 대화/RM 제작 연결과 임의 레시피/월드 일반화는 남아 있으나, 모두 완성할 때까지 RL을
미루지는 않는다. [결과](workshop-validation-2026-10-05.md), [첫 RL 단계](first-rl-stage.md).

아래는 이전 단계의 기록이다.

**이전 레시피북 보조 검증:** 모델을 로드하지 않은 별도 GUI 제어로 막대기4·판자2 보존5/5,
작업대1 보존5/5를 확인했다. 해금된 단일 레시피 버튼을 클릭해 자동 배치하고 실제 칸과
결과를 검사한다. 초기화 오류1회 수정 후 별도 재시도가 포함돼 있다. 저장 NBT10/10 일치.
이는 명시적 보조의 결과이며 STEVE-1 자체의 제작 성능 개선이 아니다. 3×3·대화/RM 연결,
검색/페이지/그룹 처리는 남았다. [결과](recipe-book-validation-2026-10-05.md),
[해금·재료·화면 조건](recipe-book-unlocks.md). 아래는 이전 조건의 기록이다.

**최신 결과 칸 제한 비교:** 결과 칸·GUI 전환에서만 Shift를 제한한 별도 조건은 정확
막대기4·판자2 저장3/5, 과다 제작0/5였다. 성공3회는 회수 보조를 사용했고 작업대/버튼
오제작2회가 남았다. 좌표 예측·입력 보존·서버와 저장 NBT를 실제로 검증했다.
다음은 잘못된 레시피의 실행 전 검증과 남은 재료 예산 판정이다. 기본 정책 및 대화/RM의
제작 미지원 범위는 유지한다. [최신 비교](craft-result-slot-validation-2026-10-05.md).
아래는 이전 조건의 기록이다.

**후속 입력 제한 비교:** Shift를 제한한 별도 조건에서 정확 막대기4·판자2 보존2/5,
과다 제작0/5를 확인했다. 미제작1회/작업대 오제작2회가 남았다. 두 성공은 커서 회수 보조를
사용했다. 기본 정책은 유지하며, 다음은 재료 이동에 대한 제약을 좁히고 레시피 선택을
검증하는 단계다. [실제 비교](craft-shift-guard-validation-2026-10-05.md).

**2026-10-05 독립 후속 검증:** 판자4에서 작업대1개 제작·저장4/5, 막대기 제작·저장2/5.
막대기는 두 번 모두8개라 정확4개·판자2개 보존은0/5였다. 다른 레시피 선택과 Shift+클릭
일괄 제작의 수량 초과가 남았다. 첫 목표 관측 후 새 정책 행동0, 저장 NBT10/10 일치.
다음은 레시피·재료 예산의 행동 전 제약을 별도 조건으로 검증하는 일이다.
[후속 결과](craft-recipes-validation-2026-10-05.md), [서버 수량 차이](craft-batch-click-cause.md).
아래 판자 결과는 그 전 단계 기록이다.

**대화/RM의 제작 목표는 아직 미지원이다.** 최신 별도 실험은 STEVE-1 제작과 명시적
회수 보조·서버 확정 검사를 결합해 5/5에서 판자 4개를 저장했다. 커서 배치 보조는
2회 사용했다. 순수 정책 학습 개선으로 해석하지 않는다.
[최신 결과](craft-recovery-validation-2026-10-04.md), [근본 원인](craft-rm-root-cause.md).
앞선 witness 정지 실험은 회수·저장 3/5였으며, 늦은 통계가 도착할 때까지 인벤토리
달성 후 4회씩 추가 행동이 있었다. [정정된 이전 기록](craft-retention-validation-2026-10-04.md).
앞선 무정지 실험은 중간 회수 3/5, 최종 보존 0/5였다.
[이전 결과](crafting-validation-2026-10-04.md).
수집 RM의 목표는 wood/dirt뿐이다. 혼합 요청
“원목을 모아서 작업대를 만들어줘”를 수집 부분만 몰래 실행하지 않는 검사를 추가했다.

## 조합이 별도 과제인 이유

1. 계획: 레시피·재료 수량·선행 제작·작업대 필요 여부를 결정해야 한다.
2. 실행: 인벤토리/작업대 화면을 열고 올바른 칸에 재료를 옮겨 결과를 꺼내야 한다.
3. 판정: 실제 재료 감소와 결과 아이템 증가를 관측해야 한다. 화면에 결과가 보이거나
   LLM이 완료했다고 말한 것만으로 완료 처리할 수 없다.

현재 MineRL 1.0 계열은 과거의 `craft`/`smelt` 고수준 액션 대신 GUI와 마우스 제어를
사용한다. 따라서 레시피를 설명할 수 있는 LLM을 연결하는 것만으로 제작 실행 문제가
해결되지 않는다. [공식 MineRL 설명](https://github.com/minerllabs/minerl).

공개 VPT에는 foundation 외에 early-game BC 및 다이아몬드 곡괭이 획득 보상으로
학습한 RL 가중치도 있지만, 현재 검증한 foundation 1x 또는 STEVE-1의 조합 성공을
보장하는 근거는 아니다. [공식 VPT 모델 구분](https://github.com/openai/Video-Pre-Training#agent-model-zoo).

설치된 STEVE-1의 `steve1/run_agent/paper_prompts.py`에는 인벤토리 열기와 여러
수집/이동 문구가 있으나 조합 항목은 없다. 이것은 조합 불가능의 증명도, 성공의
증명도 아니다. 임의 제작 문구에 대한 실제 결과를 따로 관측해야 한다.
[공식 STEVE-1 저장소](https://github.com/Shalev-Lifshitz/STEVE-1).

## 기능 검증의 순서와 남은 범위

- 원목을 가진 고정 저장본에서 원목→판자 제작. GUI 열기/재료 이동/결과 꺼내기를
  프레임과 정책 행동으로 기록하고 인벤토리 소비·생산을 판정한다. 이 선행 실험은
  완료했으며, 상태 경계·커서 회수·서버 확정을 보완한 조건은 5회 모두 저장까지 통과했다.
  순수 정책의 회수 개선과 일반 제작 RM 연결은 별도 범위다.
- 판자→막대기, 판자→작업대를 각각 독립 검사한다. 같은 원목 자원을 중복 사용하지
  않도록 재료 예산과 남은 인벤토리를 확인한다.
- 이후 작업대 배치·열기→나무 곡괭이 제작으로 3×3 조합과 선행 조건을 확장한다.
- 최초에는 현재 정책을 평가한다. 실패하면 실패 위치(미개방/배치/회수/재료 부족)를
  기록한 뒤 제작용 가중치·GUI 제어 스킬 등 후속 접근을 별도 비교한다.

판자→막대기/작업대의 독립 실험까지 구현·실행했다. 3×3 제작과 순차 제작 제어는 아직
구현·실행하지 않았다. 재료를 실험 fixture로 지급한다면 자연
수집과 분리 표기하고, 제작 중 창을 닫거나 STOP한 뒤 눌린 입력/커서에 남은 아이템도
확인해야 한다. 자동 API 제작으로 바꿔 정책 성공으로 보고하지 않는다.
전체 생존 기술 트리를 한 번에 검증하기보다 첫 관문인 판자 제작부터 판정한다.
