# RL 중심 추가 학습과 병렬 이상 감지 — 논의 메모

## 확정한 방향과 현재 상태

사용자는 공식 STEVE-1 이외의 기존 추가 학습 정책과 전용 실험 자료를 정리하고 RL 학습을
연구의 중심에 두도록 요청했다. LLM 사례 기억의 확장이나 복구 스크립트의 성능을 주된 결과로
삼지 않는다. LLM은 학습 필요성과 연습 조건을 제안하고, 실제 정책 가중치 개선을 별도로 평가한다.
기존 공통 BC의 완성을 요구하지 않는다. 원문 연구 명세는 그대로다.

이 문서는 추천 구조이며 새 감시 스레드·RL 학습 요청 서비스가 구현됐다는 뜻이 아니다.
게임/학습 STOP은 유지한다. 아래 숫자는 측정된 성능이 아니라 개발 시작값이다.

최신 사용자 보완: 검색은 세계 현상·몹 변화·관습·대화의 궁금증까지 허용하고, 상호작용 LLM의
한 응답에 자연어 대화와 구조화된 개선 판단을 함께 생성한다. 프로그램이 검증하며 별도 2차
변환 LLM은 기본 경로에서 제외한다. 이는 후속 사용자 합의로 이전 변환기 제안을 대체한다.
[넓은 지식 탐색과 상호작용 계약](unified-interaction-knowledge-2026-10-25.md)을 함께 따른다.

후속 사용자 요구: 운영 중 학습하더라도 본 게임 플레이는 유지해야 한다.
[병행 확인·연습·학습 설계](continuous-play-learning-2026-10-25.md)가 이전의 교대 운영 제안을 대체한다.

후속 사용자 제약: **관측기는 실사용 중 고정**한다. 허용 입력·전처리·인지 모델/가중치·추출 규칙/
프롬프트·출력 스키마와 측정 정의를 고정하고 원시 관측과 시간/출처를 기록한다. 상태 버퍼와 KB
내용은 갱신될 수 있지만 관측기를 사건마다 수정하지 않는다. 고정 관측과 갱신된 KB를 사용하는
LLM의 판단은 달라질 수 있으며 두 변화는 구분해 기록한다. 전체 판단 함수가 불변이라는 뜻은 아니다.
새 사실에 필요한 정보를 기존 관측으로 알 수 없으면 unknown/미지원으로 남기고, 관측 확장은
별도 개발 조건으로 취급한다. [지식을 실제 RL로 연결하는 계약](knowledge-to-policy-learning-2026-10-25.md) 참조.

## 사용자 보완: 맥락을 이해하는 상황 판단 — 2026-10-25

사용자가 교수님의 예시를 추가했다: 주변 차량은 정지했는데 자기 차량만 진행하는 장면에서,
센서로 관측한 주변 상황과 자기 행동의 관계를 판단하고 필요하면 올바른 행동을 RL로 추가 학습한다.
따라서 단순한 무진전/반복 판정을 넘어, 진행 중인 행동도 상황에 부적절할 가능성을 탐지해야 한다.
멀티스레드는 동시 실행 방식이며 판단 능력은 관측 표현과 그 안에서 사용하는 평가 모델에 달려 있다.

주변과 다름, 예측과 다름, 드문 상태는 각각 이상 후보이지 잘못된 행동의 확정 증거가 아니다.
차선/신호/목표 등 맥락 차이 또는 관측 오류가 있을 수 있다. Minecraft에서도 벽 우회 중 목표와
멀어지는 것과 잘못된 이동을 구별해야 한다. 실제 관측, 추론한 가설, 모르는 항목을 분리한다.

추천 보완은 빠른 실행 감시와 비동기 상황 평가를 함께 두는 것이다. 상황 평가에는 최근 여러
관측/프레임, 실제 전달 행동, 목표와 skill 단계, 관측 출처/신뢰도, 알려진 전제조건을 전달한다.
평가자는 관측한 관계, 기대되는 변화, 부적절할 가능성이 있는 행동, 대안 가설, 추가 확인할
관측을 구조화해 반환한다. 단일 프레임만으로 원인을 단정하거나 가려진 상태를 지어내지 않는다.
화면 의미 판단은 별도 VLM/인지 모델 또는 검증된 객체·관계 표현이 필요하다. 스레드를 추가하거나
STEVE-1의 기존 특징을 읽는 것만으로 이런 능력이 생긴다고 가정하지 않는다.

빠른 감지기의 사건 외에도 저빈도 정기 평가를 수행해야 한다. 기존 규칙이 통과시킨 상황만
LLM에 보내면 규칙이 모르는 의미적 이상을 계속 놓친다. 초기 의미 평가 주기는 예를 들어
1~3초의 요청 시작 간격부터 비용/지연을 측정해 조정하며, 매번 그 시간 내 응답한다는 보장이 아니다.
중복/밀린 요청은 합치고 episode·goal revision·policy version·관측 시각으로 응답의 유효성을
검증한다. 빠른 감시의 p95≤200ms 목표를 VLM/LLM 의미 판단 전체의 지연 목표로 보고하지 않는다.
3GiB GPU에서 STEVE-1과 로컬 VLM 동시 추론을 전제하지 않는다. 실제 API 사용은 이번 논의와 별도다.

예: 맨손으로 돌 블록을 부수고 있는데 수집 목적을 만족할 자원을 얻지 못하는 상황은 움직임과
블록 변화가 있어도 부적절할 수 있다. 감시자는 도구 전제조건에 관한 가설을 내고, 관측된 도구
보유 여부와 실제 획득을 확인한다. 도구가 주어진 조건의 선택·장착·채굴 능력 부족과 도구 자체를
마련해야 하는 선행 목표를 구분한다. 학습할 때에는 다양한 배치/시선/도구 보유 조건에서 실제
환경 피드백으로 보상을 주며, LLM이 추측한 정답 행동을 사실인 라벨로 만들지 않는다.

상황 평가자는 관측/이상 후보를 제공하고, 최종 의도와 학습 필요성 판단은 상호작용 LLM의 같은
페르소나/목표 맥락을 거친다. 같은 응답의 학습 요청을 프로그램이 검증한다. 의미적 이상 후보→관측/원인 확인→RL 학습 과제와
평가 조건 생성→실제 경험 수집·가중치 갱신→별도 검증으로 연결한다. 단순 재계획의 개선과
RL로 습득한 능력을 구분하기 위해 학습 후 상황 판단자의 추가 조언 없이도 새 조건을 수행하는지
평가하는 조건을 포함한다. 학습 중 보상 설계의 조정과 최종 성공 판정은 별도 버전으로 관리한다.

이는 새 요구사항과 추천 구현 방향을 기록한 것이며, 의미 판단 모델이나 RL 연동을 구현/실행하지 않았다.

## 권장 실행 구조

### 지식 베이스·온톨로지 활용 제안 — 2026-10-25

사용자가 상황 판단에 knowledge base/온톨로지를 함께 사용하는 방안을 제안했다.
추천 목적은 판단 근거와 공통 의미를 명시하고 RL 학습 과제로 연결하는 것이며,
문서 검색/대화 기억 자체를 연구의 주된 성과로 바꾸지 않는다. 구체적 저장소와 형식은 미선정이다.

- 온톨로지/도메인 스키마: 객체·도구·행동·목표·위험의 유형, 관계와 의미를 정의한다.
  행동의 전제조건·효과·허용 조건은 실행 가능한 명시적 규칙과 함께 관리한다.
- 검증된 도메인 지식: 도구/대상/행동 조건, 레시피, 관측 가능한 기대 효과 등을 게임/모드
  버전·출처·검증 근거와 연결한다. 모든 게임 지식을 먼저 수작업으로 완성하지 않는다.
- 현재 상태/믿음: 최근 관측을 시각·출처·신뢰도·유효 기간·episode/task revision과 함께 관리한다.
  영구 지식과 순간적인 위치/장착 상태를 섞지 않고, 미관측은 false가 아닌 unknown으로 취급한다.
- 사건과 학습 결과: 이상 가설, 근거 관측, 시도 방법, 실제 결과와 정책 버전을 저장한다.
  LLM의 새 규칙은 우선 hypothesis이며 외부 근거로 지지된 지식과 환경에서 검증한 지식을 구분한다.
  상충 근거를 지우지 않고 적용 조건과 버전을 남긴다.

온톨로지는 인지 모델을 대신하지 않는다. 화면에서 객체/관계를 판별해 위 표현에 연결하는
과정이 별도로 필요하다. 구체적 행동 적절성의 시간적·확률적 판단도 OWL의 논리 추론만으로
자동 제공된다고 가정하지 않는다. 현재 상태와 규칙이 불일치하면 관측 오류, 지식 오류,
전제조건 부족, 계획 오류, 실행 능력 부족 중 무엇인지 추가 근거로 구분한다.

감시자는 바뀐 관측과 관련된 작은 규칙 집합/캐시된 지식을 읽고, 무거운 검색·추론과 지식
검증은 비동기로 실행한다. 기존 규칙이 모르는 문제를 위한 정기 상황 평가도 계속 유지한다.
초기에는 작은 명시적 도메인 스키마와 증거 저장소로 검증한다. RDF/OWL을 채택하면 그 의미에
맞는 추론/검증 도구가 필요하며, 단순 JSON 타입 검사를 OWL 추론으로 보고하지 않는다.

온톨로지/KB는 개념과 전제조건의 의미, RM은 해당 목표의 진행·완료·보상 전이, RL 정책은 실제
행동의 학습을 맡는다. KB의 모든 엔티티나 개별 키 입력을 RM 상태로 복사하지 않는다.
기존 목표는 유지하면서 필요할 때 검증 가능한 하위 목표/우선순위를 조정한다.
KB 갱신만으로 정책 가중치가 바뀌지는 않으므로, 능력 부족이 확인된 경우에는 연습 조건과
측정 가능한 보상을 만들고 실제 RL 학습·평가를 수행해야 한다. 지식이 적혀 있다는 이유로
지원되지 않은 skill을 실행 vocabulary에 추가하지 않는다.

논문 실험에서는 구조화된 KB의 효과와 제공한 지식량의 효과를 구분하기 위해 같은 사실을
문장으로 제공한 조건과 관계/규칙으로 제공한 조건도 비교할 수 있다. 학습/평가의 KB·온톨로지·RM·
정책 버전을 기록하고, 평가 중 추가 학습/KB 갱신 허용 여부를 프로토콜에서 명시한다.
이 단계에서는 문서만 보완했으며 KB 서버 설치·모델 호출·게임·학습은 수행하지 않았다.

### KB 초기 구축과 점진 확장 — 2026-10-25

사용자는 자원 외 병목이 남았는지와 구체적인 KB 구축 방식을 질문했다. 병행 구조는 학습 대기와
행동 실행을 분리하는 해법이며, 원인 진단·연습 환경에서 본 게임으로의 전이·실제 가중치 학습·
능력 보존이 해결됐다는 근거가 아니다. 아래는 아직 구현하지 않은 구축 제안이다.

사람이 정의할 범위는 객체·행동·목표·조건·효과·근거의 작은 스키마와 관측/판정 코드의 연결이다.
Minecraft의 모든 사실과 예외를 수작업으로 쓰지 않는다. 새 용어나 관계는 후보로 저장할 수 있지만,
관측 가능한 의미와 판정 방법이 연결되기 전에는 실행/보상의 확정 조건으로 쓰지 않는다.

| 층 | 초기 입력과 관리 방식 |
|---|---|
| 정형 도메인 사실 | `minecraft-data`의 대상 버전 블록/아이템/레시피를 변환기로 가져온다. source commit·원본 hash·게임 버전과 변환 버전을 기록한다. 정확한 항목의 지원 여부와 설치 환경의 차이를 검토한다. |
| 설명형 지식 | 버전이 확인된 문서/위키 자료를 검색용으로 보관한다. MineDojo Wiki는 자료 후보이며 전체를 온톨로지로 변환하지 않는다. 과업뿐 아니라 세계 현상·몹 변화·위험·관습·대화 질문에 관련된 문장을 근거와 함께 추출한다. |
| 현재 상태 믿음 | 관측 모델/허용된 센서가 제공한 대상·위치·보유·행동 결과를 시각·유효기간·신뢰도·출처와 함께 기록한다. 영구 게임 규칙과 분리하고 관측하지 못한 것은 unknown이다. |
| 정책 능력 근거 | 실제 평가의 조건·표본 수·성공/실패·도움 여부·정책 버전을 기록한다. 문서에서 방법을 알았다는 이유로 수행 능력을 등록하지 않는다. |

정형 자료의 최초 가져오기는 이동·자원 수집·기초 제작부터 시작할 수 있지만 검색/지식 수용의
상한으로 삼지 않는다. 새 세계 현상과 대화의 궁금증도 검색·저장 대상이다. 데이터 변환기는
여러 아이템/레시피에 공통으로 적용하며 특정 월드 좌표나 성공 행동 순서를 사실처럼 하드코딩하지 않는다.
범위를 확장할 때도 같은 변환/검색/근거 갱신 절차를 사용한다. 실제 월드의 미관측 좌표나 자원 위치를
정적 도메인 자료에서 알 수 있다고 가정하지 않는다.

지식 항목은 내용/적용 맥락/지지 및 반대 근거/검토 상태/의존 관계/revision을 갖는다. 외부 자료와
관측으로 지지된 상태를 구분하며 LLM의 자체 확신을 검증 근거로 삼지 않는다. 충돌하면 맥락 차이와
관측 오류를 확인한 뒤 해당 항목의 채택을 보류/철회하고, 다른 유효한 근거가 없는 의존 결론을
재검토한다. 근거 기록은 보존하고 배포용 지식 스냅샷을 새 버전으로 발행한다.

초기 저장소 후보는 작은 SQLite 증거 저장소와 메모리 조회용 스냅샷이다. 단일 기록 소유자를 두고
Windows/WSL이 같은 DB를 각각 열지 않는다. 실제 파일시스템의 잠금/동시성은 구현 시 확인한다.
빠른 감시 경로는 관련 규칙과 스냅샷을 읽고 DB/네트워크 검색을 기다리지 않는다. 단순 스키마와
의존성 처리를 완전한 OWL/비단조 논리 엔진으로 부르지 않는다.

구축/검증 순서는 (1) 스키마와 관측 연결, (2) 버전 고정 정형 자료의 변환·표본 대조,
(3) 과업별 검색/추출의 출처·적용 조건 검사, (4) 충돌과 의존 결론 철회 검사,
(5) 동일 학습 계약으로 이어지는 실제 과업 적용이다. 자료 가져오기·DB 생성·모델 호출은 아직 하지 않았다.
KB의 완료 기준은 사실 개수보다 '이 과업에 무엇이 필요하며, 무엇을 모르고, 어떤 근거로 어떤
확인/학습이 필요한지'를 설명하고 잘못된 전제를 수정할 수 있는지다. RL 효과는 별도로 검증한다.

### 비단조 지식 수정과 실행 전 검색 — 2026-10-25

사용자는 기존 지식이 틀릴 수 있으므로 non-monotonic하게 처리하고, LLM이 실패하기 전에도
검색으로 필요한 정보를 얻도록 요구했다. 이는 아래 설계 요구의 추가이며 새 기능 구현은 아니다.

기록은 보존하되 현재 채택한 믿음과 결론은 철회할 수 있어야 한다. 온톨로지 저장이나 신뢰도
점수 조정만으로 이 동작이 구현되지는 않는다. 작은 도메인 스키마 위에 조건부 규칙과
근거 의존성을 추적하는 믿음 수정 계층을 두는 방안을 추천한다. Doyle의 truth maintenance는
믿음의 이유와 의존성을 기록하고 가정을 수정한다는 점에서 참고할 수 있다.

- 지식 항목: 주장, 적용 게임/모드/버전/조건, 출처와 관측 시각, 지지·반대 근거,
  채택 상태(proposed/supported/disputed/retracted), 지식 revision을 기록한다.
  출처 기반 확인과 현지 실험 검증은 별도 근거 유형이며, supported도 이후 철회할 수 있다.
- 추론 결과: 어떤 규칙·관측·가정으로 결론이 나왔는지 연결한다. 관측되지 않음을 거짓으로
  바꾸지 않는다. 순간 상태의 변화와 일반 규칙의 반례도 구분한다.
- 모순 처리: 먼저 관측 오류와 적용 맥락 차이를 점검한다. 한 번 실패했다는 이유로 일반 규칙을
  폐기하거나 최신 검색 결과를 무조건 우선하지 않는다. 필요하면 규칙의 적용 범위를 좁히거나
  예외를 추가하고, 해결되지 않은 모순은 disputed로 남겨 실행 전제의 확정 근거로 쓰지 않는다.
- 영향 전파: 철회된 근거에 의존하는 결론·하위 계획·학습 요청을 재평가한다. 독립적인 유효
  근거가 남은 결론은 유지할 수 있다. 순환 참조만으로 서로를 지지하는 결론은 인정하지 않는다.
  사용자 최종 목표는 보존하고 잘못된 전제에서 나온 방법·우선순위·RM 제안을 수정한다.

검색은 새로운 과업의 전제조건, 버전 변화, 지식 충돌뿐 아니라 사용자 질문/호기심, 처음 보는
현상, 몹 변화와 위험 가능성에도 요청한다. 실행 전에도 가능하며 현재 목표와 무관한 설명형
지식을 수용할 수 있다. 우선 로컬 지식을 확인하고 부족한 항목만 외부에서 찾는다. 정확한 환경에
맞는 공식 문서·소스·레시피/설정 자료 등을 우선하며 URL, 근거 내용, 확인 날짜, 적용 버전을
남긴다. 모든 지식을 직접 실패하며 재발견할 필요는 없지만, 검색 결과와 LLM의 해석을 분리한다.
출처가 지지하는 전제조건은 계획에 잠정 활용할 수 있으며 실제 관측과 충돌하면 다시 검토한다.
검색 문장은 증거로 취급하고 임의 명령이나 학습 코드의 실행 권한으로 취급하지 않는다.

검색과 깊은 추론은 비동기 작업자가 담당한다. 빠른 감시자는 버전이 고정된 메모리 스냅샷을
읽으며 네트워크/DB 완료를 기다리지 않는다. 요청에는 episode·goal·KB revision을 붙이고,
응답이 도착했을 때 현재 맥락에 여전히 적용 가능한지 확인한 뒤 새 revision으로 반영한다.
관련 전제가 확인되지 않은 행동은 제어 소유자가 보류할 수 있다. 검색 시간/호출 예산과
중복 요청 통합을 두며, STOP 처리는 검색 응답과 무관하다. 실제 검색 제공자/API는 미선정이다.

추천 연결은 `과업/관측 → 관련 지식 조회·필요시 검색 → 전제/모순 검토 → 계획 또는 학습 요청
→ 실제 RL 갱신 → 별도 평가 → 근거 갱신`이다. 읽어서 알게 된 레시피·도구 조건과 정책이
선택·장착·이동·조작할 수 있다는 능력은 구별한다. 지식 수정으로 해결되는 계획 오류에는
학습을 강제하지 않고, 수행 능력이 부족하면 다양한 조건의 연습 과제와 실제 상태 기반 보상으로
RL을 수행한다. ReAct는 외부 정보 획득과 계획 수정의 참고이며 정책 가중치 학습의 근거가 아니다.

KB 수정은 이미 학습된 정책 가중치의 오류를 자동으로 제거하지 않는다. 영향을 받는 학습 과제와
후보 정책을 표시해 재평가하고 필요한 경우 후보 사용 보류·이전 검증 버전 복귀·추가 학습을 한다.
rollout/학습 배치별 KB·RM·보상 버전을 고정하고 변경은 명시적 경계에서 적용한다. 진행 중인
과제를 무효로 만드는 중대한 전제 오류는 중단/격리로 처리하고 과거 보상을 조용히 바꾸지 않는다.
변경 전후 근거와 보상 계산 버전을 남기며 최종 성공 판정은 유지한다.

검증에는 잘못된 초기 지식의 수정, 유효한 예외의 보존, 관측 오류에 대한 과잉 수정 방지,
관련 결론/계획의 철회, 수정 이후 RL 능력 향상과 기존 능력 보존을 포함한다. 검색만으로 얻은
계획 개선과 추가 RL 효과를 분리하고, 비교군의 외부 정보 접근·검색 예산을 맞춘다. 논문 평가에는
사용한 출처와 KB 스냅샷을 고정/보존하고 평가 중 지식 수정 및 추가 학습 허용 여부를 명시한다.

### 병렬 작업자 역할

- 게임 제어 루프: env.step과 정책 추론의 유일한 소유자. 관측마다 작은 불변 CPU 스냅샷을
  비차단 방식으로 발행한다. step 번호, 서버 tick, monotonic 수신 시각, episode/task/goal revision,
  policy version, 실제 전달 행동, 현재 skill 단계, 관측 유효성/출처를 붙인다.
- 감시 스레드: 새 관측 알림으로 깨고 최대100ms마다 heartbeat도 확인한다. 최근 상태의 작은
  유한 버퍼를 소비한다. 모든 새 스냅샷의 진행 증거를 반영하되 경로 순환 같은 집계 판정은
  우선5Hz 정도로 제한한다. 느린 화면 의미 분석·LLM·DB를 빠른 감시 루프에서 동기 실행하지 않는다.
- 상황 평가 작업자: 사건과 저빈도 정기 평가 양쪽에서 최근 관측·행동·목표의 관계를 검토한다.
  기존 정체 규칙이 감지하지 못한 부적절한 행동도 후보로 만들 수 있게 한다. 실제 모델은 미선정이다.
- 상호작용/판단 LLM: 사용자 대화와 이상 근거를 같은 페르소나/목표/지식 맥락에서 처리한다.
  자연어 reply와 추가 관측/지식/계획/학습 후보를 한 응답에 생성한다. 검색/학습 대기로 대화를 막지 않는다.
- 응답 파서/검증기: LLM 출력의 형식, 원문 의도, 근거, 지원 기능을 검토하고 후보를 분배한다.
  별도 LLM 변환 없이 기존 Task Commitment/실행 검증을 유지한다. 동일 사건의 중복과 오래된
  revision을 차단하며 검증 실패를 임의의 명령으로 대체하지 않는다. 모든 의미 충돌을 잡는다고 가정하지 않는다.
- 기록 작업자: 수집과 판정 이벤트를 순서대로 저장한다. DB는 전달 경로가 아니라 기록/조회용이다.
  SQLite를 쓰면 단일 쓰기 소유자와 짧은 트랜잭션을 둔다. Windows/WSL의 별도 프로세스가 같은
  파일을 각자 열지 않는다. WAL 잠금/파일시스템 호환성은 실제 배치에서 확인한다.
- RL 학습 프로세스: 동결된 실행 버전에서 별도 후보를 만들고, 명시한 경험/업데이트 예산 내에서
  학습한다. 학습 중 실행 객체를 직접 수정하지 않는다. CUDA는 spawn 등 지원 시작 방식을 사용한다.
  본 게임 플레이를 유지하면서 별도 프로세스/필요시 별도 장치에서 후보를 학습한다.
  현재3GiB GPU에서의 병행 적합성은 실측하며 학습 때문에 본 게임을 정지하는 운영을 기본으로 두지 않는다.

Python 스레드는 가벼운 감시와 I/O 분리에 적합하지만 CPU 집약 분석의 병렬 처리나
hard real-time을 보장하지 않는다. 목표는 지연을 측정하는 soft real-time이다.

## 무엇을 이상으로 판정할지

| 구분 | 근거 | 대응 |
|---|---|---|
| 실행/관측 장애 | 오래된 시각·멈춘 tick·누락 seq·프로세스 heartbeat 중단 | 관측 불확실/시스템 장애. 정책 실패 학습자료로 자동 전환 금지 |
| 이동 정체 | 이동 의도가 지속되는데 위치 변화 작음 + 단계 진전 없음 | 지속 시 이상 후보 |
| 반복 순환 | 실제 방문 순서에서 위치·방향·skill 단계가 반복 + 목표 진전 없음 | 같은 원인으로 사건 통합 |
| 상호작용 정체 | 같은 대상/행동 반복 + 관측 가능한 채굴/재료/환경 변화 없음 | 단계·도구별 허용 시간을 지난 뒤 후보 |
| 과업 장기 정체 | 탐색/회전은 하지만 허용 시간 내 목표 수준의 진전 없음 | 별도 긴 시간 창으로 판단 |
| 완료·위험·STOP | 실제 완료 상태·종료·중단 요청 | 완료/중단 우선. LLM 응답과 DB 기록을 기다리지 않음 |

보상이0이거나 같은 키가 반복된다는 이유만으로 실패를 선언하지 않는다. 정상 채굴, 회전 탐색,
우회 경로, 게임 일시 정지/로딩은 구별한다. 위치만으로는 탐색 범위를 알 수 없어 시선 방향과
새로 관측한 영역도 고려한다. 가려진 목표까지의 직선 거리 증가만으로 우회 실패를 판정하지 않는다.

관측 오류가 없는 동안에만 단계별 증거 시간을 누적하고 의심→확인→처리 중→회복 상태와
해제 기준/재호출 간격을 둔다. 신뢰도 부족은 unknown이지 실패가 아니다. 단기(예:2~3초)
막힘과 장기(예:10~30초) 목표 정체 창은 학습/개발 자료로 조정하며 최종 평가 전 고정한다.

## 현재 코드에서 그대로 옮기면 안 되는 부분

`stall_detection.StallDetector`는 진행 없음/목표 진전 없음/제자리 반복/경로 순환을 분리한다.
그러나 tick 간격이4를 넘으면 observation_gap으로 보고 이력과 진행 시간을 초기화한다.
새 스레드가 최신 관측 하나만5Hz로 취하면 실제 게임 속도/지연에 따라 이 조건을 반복해서
밟을 수 있다. 따라서 기존 판정기를 저주기 호출하는 방식으로 끝내면 안 된다.

새 설계에서는 실제 샘플 주기와 관측 나이를 명시하고, 아직 처리하지 않은 스냅샷을 순서대로
집계한다. 큐가 넘치면 누락 횟수와 범위를 기록하고 그 구간 판정 신뢰도를 낮춘다. CPU/GPU
환경이 느려 서버 tick이 적게 진행되는 상황을 정책 정체와 혼동하지 않는다. 증거 창은 게임 내
진행 시간/유효한 행동 기회로, heartbeat 지연은 monotonic 실시간으로 별도 측정한다.
감시용 버퍼와 RL 궤적 저장은 분리한다. 모니터가 샘플을 합치거나 버렸다고 학습 궤적을
조용히 버리면 안 된다. 학습 로그가 누락된 구간은 학습 자격을 검증할 수 없으면 제외한다.

STOP은 bounded queue 바깥의 Event로 전달한다. 감시자는 게임 입력을 직접 보내지 않고
제어 소유자에게 중단을 요청한다. 기존 StopGate의 '승인 이후 새 정책 dispatch 없음' 의미와
입력 해제·소유 자식 PID 종료를 유지한다. 이미 전송된 step은 별도로 구분한다.

## 학습과 논문 평가

이상 감지는 학습 부족의 증거 후보이지 진단 확정이 아니다. LLM은 사건/기존 시도/능력 목록으로
구조화된 학습 요청을 만들며, 학습기가 허용한 과업·파라미터 범위·보상 템플릿만 실행한다.
사람이 정한 최종 성공 판정은 LLM이 변경하지 못한다. 학습과 평가 seed/월드/버전은 분리한다.
재계획만, 고정 규칙 RL, LLM 판단 RL을 비교하고 상호작용·갱신·계산/API 예산을 기록한다.

주요 결과는 새 조건의 실제 목표 성공률/획득량, 추가 경험 대비 성능 향상, 기존 능력 보존이다.
감시자 지표는 오탐률·미탐률, 이상 시작→확인 지연, 관측 수신→판정 p50/p95/p99, 게임 제어
주기에 추가된 지연, 큐 누락, STOP 이후 dispatch를 포함한다. 관측→판정 p95≤200ms와
감시 계산 예산≤5ms/회는 초기 목표이며 현 환경에서 아직 검증하지 않았다.
지속 조건2초가 필요한 정체는 최초 이상부터200ms 만에 확정할 수 없으므로 두 지연을 분리한다.

개발 초기의 서버 좌표/인벤토리/채굴 진행 관측은 privileged 조건이다. 영상 전용 조건의 감시자에
몰래 공급하지 않는다. 비교군에 같은 관측 권한을 주고 관측 출처와 평가 전용 정답을 분리한다.

## 설계 병목 검토 — 2026-10-25

후속 사용자 요청에 대한 [구체적 해결안과 검증 순서](rl-adaptation-solutions-2026-10-25.md)를 별도로 정리했다.

사용자는 Minecraft 1.16.5 유지와 초기 과업/월드 조건 단순화 방향에 동의하고 현재 설계의
병목을 질문했다. 아래는 문서와 코드에 근거한 설계 위험 평가이며 새 실행으로 측정한 병목은 아니다.
단순화한 초기 조건에서도 지형·배치·시선·도구 조건을 다양하게 두고 별도 평가 조건을 유지한다.

1. 이상 후보에서 학습 필요성으로 넘어가는 진단이 가장 중요한 연결부다. 관측 오류, 전제조건
   부족, 계획 오류, 수행 능력 부족의 경쟁 가설과 구별할 관측/제한된 진단 실험을 명시해야 한다.
   한 번의 실패나 낮은 보상만으로 RL 요청을 확정하지 않는다. 필요한 관측을 얻을 수 없으면
   원인을 모른다고 기록한다. 준비용 조건 개입은 정책의 자율 성공으로 세지 않는다.
2. 학습 요청의 실행 계약이 미구현이다. LLM 제안에 목표/적용 조건, 사용 가능한 관측,
   실제 성공 판정, 연습 초기 상태의 범위, 업데이트 범위, 상호작용/계산 예산,
   중단/채택 기준을 붙인다. 미지원 판정식이나 skill은 실행하지 않고 부족한 연결을 반환한다.
   공식 STEVE-1에서 일반적인 RL 갱신이 작동하는 경로는 별도로 검증해야 한다. 남아 있는
   `rl_policy.RLPolicy`의 동결된 비전/순환 특징과 기존 head/tail 경로를 새 학습기의 완성으로
   해석하지 않는다. 표현에 없는 구분을 학습하려면 head만으로 충분하지 않을 가능성이 있다.
3. 유용한 경험 확보가 필요하다. 실패 지점을 반복 재생하는 것만으로 충분한 개선 신호가
   생긴다고 가정하지 않는다. 선행 조건을 통제한 연습부터 시작해 배치/난이도를 다양하게 하고,
   최종 평가는 원래 과업 조건에서 수행한다. 성공 경험 빈도, 실제 획득, 경험당 개선을 기록한다.
4. 실시간 감지와 능력 습득의 시간을 구분한다. 이전 확인 GPU는 3GiB이며 새 학습 범위의
   메모리/속도는 미측정이다. 본 게임과 연습/학습 프로세스의 병행 간섭을 실측하고, 긴급 중단/재계획을 학습
   완료까지 미루지 않는다. 배포 정책과 학습 후보를 분리하고 전환 경계/순환 상태 처리를 검증한다.
5. 능력 개선과 계획 개선의 분리, 학습 결과의 역방향 연결이 필요하다. 같은 목표 프롬프트와
   동일한 추가 도움 조건에서 전후 정책을 비교하고 planning-only 조건과 비교한다. 새 조건의
   성공률과 기존 능력 보존을 평가하고, 검증된 적용 범위/실패 조건/정책 버전을 LLM에 돌려준다.
   개선되지 않으면 가중치 갱신 횟수를 성과로 세지 않고 원인 가설과 학습 요청을 재검토한다.

새로운 지식의 의미도 실험별로 정해야 한다. 공개된 레시피를 검색한 것만으로 모델이 이전에
몰랐던 지식을 학습했다고 주장할 수 없다. 고정된 초기 정책과 KB에 대해 어떤 조건이 새로
주어졌고, 그 이후 정책 행동이 어떻게 달라졌는지 관측 가능한 정의가 필요하다.

추천 구현 순서는 (a) 통제된 여러 조건에서 공식 초기값의 RL 전후 개선과 자원 사용을 먼저
검증하고, (b) 그 공통 학습 계약에 감시자/LLM 진단을 연결하며, (c) 필요 지식의 검색·추출·
철회를 확장하는 것이다. 첫 검증에서 진단/과제 선택을 고정하는 조건은 구성 요소 검증으로
명시하고 자율 LLM 판단의 결과로 계산하지 않는다. KB는 작은 스키마와 관련 근거부터 시작한다.
공식 STEVE-1의 instruction-tuning은 self-supervised BC에 기반하며, 그 결과만으로 이번
온라인 RL 경로의 효과를 보장하지 않는다. 게임·학습은 재개하지 않았다.
