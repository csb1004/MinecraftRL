# 점프 v2: 다음 발판 방향을 특권 입력으로 — 설계 (2026-11-14)

- 상태: 사용자 지시(11/14) "계속해줘. 중간에 멈추지 말고 네 판단에 필요하다고 판단되면 해".
  세부는 내가 정했다. **(내 결정)** 표시 값은 사용자가 정하지 않은 것이며 바꿀 수 있다.
- 앞선 결과: [점프 코스 결과 2026-11-13](../jump-course-results-2026-11-13.md). 앞선 설계: [점프 코스](2026-11-13-jump-course-design.md).
  과업, 코스, 단계, 교사, 성공 판정은 그대로 둔다. 바꾸는 것은 학생 헤드가 받는 입력뿐이다.
- 이 기술은 아직 LLM 계획 vocabulary에 넣지 않는다.

## 1. 왜

v1 학생(j-final)은 개발 1/8이었다. 사후 분석에서 실패는 대부분 학생이 볼 수 없는 정보를 교사가 쓴 데서 나왔다.

- 다음 발판이 화면 밖(35도 이상)이면 도는 방향이 교사와 같은 비율이 0.35–0.47이었다. 입력(화면 latent + 단계 one-hot)에 방향이 없다.
- 교사는 다음 점프의 틈(2칸)과 오르막을 보고 달리기를 누른다. 학생은 run 단계 달리기를 36번 중 6번만 눌렀다.

## 2. 무엇을 넣나 (특권 입력, 기록에 밝힘)

헤드 adapter 입력을 `[latent, 단계 one-hot, 방향 특징 7개]`로 늘린다. 특징은 단계와 같은 `JumpFeed`가 같은 자세(클라이언트 좌표, 없으면 서버 좌표 + 4틱 예측)로 계산한다.

| 이름 | 값 | 교사가 쓰는 곳 |
|---|---|---|
| `sin_yaw`, `cos_yaw` | 시선에서 다음 발판 윗면 중심까지 yaw 차이의 sin·cos | 회전 방향 |
| `pitch` | 같은 점까지 pitch 차이 / 60(±1로 자름) | 시선 높이 |
| `edge` | 땅에서 진행 방향 가장자리까지 거리 / 3(0..1), 공중 0 | 점프 시점 |
| `gap2` | 다음 점프의 틈이 2칸이면 1 | 달리기 |
| `rise` | 다음 발판 윗면 − 지금 발판 윗면(−1..1로 자름) | 달리기 |
| `past` | 다음 발판 가까운 가장자리를 지난 거리 / 3(−1..⅓로 자름) | 공중에서 앞으로 떼기 |

- goal·fallen 단계와 단계를 모르는 결정은 0 벡터다. 이미지만 쓰는 갈래(`use_stage` 끔)는 단계처럼 특징도 0이다.
- 이것은 목표 방향을 주는 입력이다. 학생이 화면만으로 방향을 찾는 문제는 풀지 않는다.
  나중에 영상만으로 이 특징을 예측하는 모듈을 함께 학습하면(연구 방향 11/7의 CNN 동시 학습), 그것으로 대신할 수 있다. **(내 결정)**
- 특징은 결정마다 latent 기록에 남긴다. 자료를 만들 때 기록에서 다시 계산해 기록과 다르면 그 실행을 거부한다(단계와 같은 규칙).
- 채굴 헤드와 기존 체크포인트는 특징 0개로 그대로다. 체크포인트에 특징 목록을 저장하고, 목록이 다르면 불러오지 않는다.

## 3. 학습

- v1 실행(R0 공식, R1 j-r1, R2 j-r2: 36판)은 기록된 telemetry로 특징을 다시 계산해 그대로 학습 자료로 쓴다. 게임은 다시 하지 않는다.
- 학습 설정은 v1과 같다(KL 10, 단계 균형, patience 2). 검증은 v1 j-final과 같은 행(R2의 코스 111·112).
- **오프라인 관문(게임 전, 미리 정함):** v1 R0–R2 자료로 학습한 j2-a의 검증 NLL이 같은 행에서 v1 j-final의 검증 NLL(3.835)보다 낮아야 한다.
  아니면 게임을 시작하지 않고 원인부터 본다. **(내 결정)**
- **수정(11-14 01:53, 게임 전, 오프라인 관문 불통과):** 처음 학습한 j2-a(특징 배율 1)의 검증 NLL은 3.870으로 v1 3.835보다 높았다.
  같은 epoch끼리 비교하면 j2-a가 1–15 epoch 내내 낮았다. 하지만 v1이 마지막 16 epoch에서 크게 내려갔고, j2-a는 patience로 13 epoch에서 멈췄다.
  더 큰 문제는 헤드가 특징을 거의 쓰지 않은 것이다. 학습 행 turn에서 교사 쪽으로 돌 확률이 0.77로 v1 0.70과 비슷했다.
  원인은 입력 크기다. 특징 7개는 크기 1 이하인데 latent는 2048칸이다(행 노름 약 36). 그래서 은닉층이 거의 latent로만 움직였다.
  자료의 특징에 10을 곱한 사본으로 한 시험 학습(파이프라인 아님, `spike/`)은 검증 NLL 3.065였다.
  검증 행에서 교사 쪽으로 돌 확률은 0.86–0.98, 달리기 확률은 0.95–1.0이었다.
  그래서 **특징이 있는 헤드는 특징에 배율 10을 곱해 넣는다**(체크포인트에 `feature_gain` 기록). 관문은 같은 규칙으로 배율 10 헤드 j2-a10에 다시 적용한다.
  j2-a는 남기되 게임에 쓰지 않는다. 개발·최종 판정은 바꾸지 않는다.
- DAgger: j2-a10 → R3(학습 코스 12판, 샘플링 n4) → 자료 R0–R3 → j2-b → R4(n5) → 자료 R0–R4 → j2-final.
  검증용으로 마지막 라운드의 코스 111·112 실행을 뺀다. **(내 결정)**

## 5. 구현

- `reacquire_head.py`: `ReacquireHead(features=())`, 결정마다 `head.feature`, 체크포인트의 `features`, `install`은 체크포인트의 특징 목록을 따른다.
- `jump_course.py`: `JUMP_FEATURES`, `jump_features(...)`, `JumpFeed.features()`.
- `stage_live.py`: 헤드에 특징이 있으면 `ReacquireHook`이 결정마다 넣고, `LatentLog`가 기록한다.
- `reacquire_data.load_latents`: 기록에 특징이 있으면 읽는다.
- `jump_data.py`: `features=True`면 특징을 다시 계산해 자료에 넣고 기록과 비교한다. `build_jump_dataset.py --features on`.
- `reacquire_training.py`: 자료에 특징 목록이 있으면 같은 목록의 헤드를 만들어 학습한다.
