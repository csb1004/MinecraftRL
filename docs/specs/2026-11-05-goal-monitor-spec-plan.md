# 목표별 감시 명세 생성 — 연구 계획 (2026-11-05)

상태: **계획만 있음.** 11/16~11/20 발표에서 "다음 연구"로 소개할 안이다. 코드 변경, 실험, API 호출은 없다.
근거 수치는 11/5 평가 기록 25회(`results/iron-demo-eval-20261105*/*/timeline.jsonl`)를 읽기 전용으로 다시 센
것이다. 성공률이나 효과의 증거가 아니다.

## 1. 요약

LLM이 목표를 하위 목표로 나눌 때 다음을 함께 제안하게 한다.

- **끝나는 방식:** 하위 목표마다 시간형 또는 탐색형("찾을 때까지").
- **감시할 신호:** 하위 목표마다 세 종류.
  - 진행: 앞으로 나아가는지
  - 이상: 점검할지
  - 낭비: 효율을 떨어뜨리는 행동 (§7)
- **제약:** 목표 전체나 하위 목표에 걸리는 조건. 형태는 항상 / 기한 / 조건부 세 가지다 (§8).
  제약은 사람이 작성하고, LLM은 제약을 만들지 않는다(2026-11-05 결정).

프로그램은 고정 관측 목록과 실제 실행 기록으로 이 제안을 검증하고 보정한 뒤 실행 중 감독에 쓴다.
시간은 모든 하위 목표에 붙지 않는다. 탐색처럼 찾을 때까지 하는 일에는 시간 제한 대신 "아직 탐험하고 있는가"를 본다.

## 2. 왜 필요한가

현재 "철 캐줘" 파이프라인([설계](2026-11-03-iron-pipeline-demo-design.md))의 감시는 다음과 같다.

- 감시 규칙은 사람이 손으로 썼다(`src/minecraftrl/pipeline/monitor.py`).
- 세계를 멈추는(hold) 것은 진행 불가 신호뿐이다: `guard_unknown`, 지속 위반, `destroy_not_harvestable`,
  `needed_tool_lost`, `blocked_overhead`, `climb_without_block`, `stationary_repetition`, `low_health`, `rule_skill_failed`.
- `no_progress`, `repeated_cycle`, `no_goal_progress`, `harvest_without_drop` 같은 정체 신호는
  "비효율은 이상이 아니다" 원칙에 따라 **기록만 한다**.
- 어떤 신호를 볼지가 하위 목표에 따라 거의 바뀌지 않는다. 예외는 사람이 오르기 단계에 붙인
  `expect: rise` 하나다. 정체 감지기도 모든 단계를 `search` 단계로 다룬다.
- 2차 평가의 실패는 대부분 탐색 시간 초과였고, 15분 실행 상한에 닿아서야 드러났다
  ([결과](../iron-pipeline-demo-results-2026-11-05.md)).

## 3. LOGO와의 관계

| | LOGO (논문 초록 기준) | 이 계획 |
|---|---|---|
| 생성물 | 하위 목표 + 달성 검증 함수 | 하위 목표 + 끝나는 방식 + 감시 신호 (+ 시간형이면 두 기준 시간) |
| 쓰임 | 목표 조건부 정책의 보상, 스킬 재조합 | 실행 중 감독: 언제 점검하고 언제 재계획할지 |
| 검증 | LLM 생성 → 검토 | [LOGO adapter 규칙](2026-10-31-logo-validator-adapter.md)을 그대로 따른다: 고정 관측, 제한된 연산, 호출자가 소유한 최종 성공 조건, 반례 검사 |

논문 본문은 열람하지 못했다(403). 세부 알고리즘을 재현했다고 주장하지 않는다.
연구 단계로는 [4단계 명세](2026-10-31-four-stage-research-spec.md)의 S3(이상 감시 + LLM 피드백)에 해당한다.
S3에 필요한 근거는 오탐·미탐·지연이다.

## 4. 감시 명세 (하위 목표 하나당)

| 항목 | 정하는 쪽 | 내용 |
|---|---|---|
| 완료 조건 | 호출자/RM (기존) | 서버 인벤토리 같은 등록 predicate. LLM이 바꿀 수 없다 |
| 끝나는 방식 | LLM 제안 → 프로그램 검사 | `bounded`(시간형) 또는 `until_found`(탐색형) |
| 진행 신호 | LLM이 §5 목록에서 선택 | 예: 목표 아이템 수 증가, 높이 상승, 새 위치 칸, 새 시야 |
| 이상 신호 | LLM이 §5 목록에서 선택 | 예: 캤는데 드롭 없음, 필요한 도구를 잃음, 같은 경로 반복 |
| 낭비 신호 | LLM이 §5 목록에서 선택 | 예: 이동 키를 누르는데 제자리, 이미 간 곳만 맴돎. 점검이 아니라 효율 지표와 학습 비용에 쓴다(§7) |
| 제약 | 사람 작성 / 계획 / 시스템 (§8) | 항상 지킬 것, 기한, 조건부. LLM은 제약을 추가하거나 풀지 않는다 |
| 기준 시간 두 가지 | 프로그램 (실행 기록) | 시간형에만 붙는다. **목표 시간**(최고 기록)과 **점검 기준**(성공 기록의 상위값 × 여유). LLM이 낸 값은 기록이 없을 때만 쓰는 초안이다 |
| 넘었을 때 | 프로그램 규칙 | 점검(§6) |

### 끝나는 방식

- **시간형:** 대상이 이미 알려져 있고 걸리는 시간이 일정한 일이다. 제작, 장착, 도구를 든 채굴, 오르기가 여기에 든다.
  점검 기준을 넘기면 점검한다. 최고 기록은 목표 시간으로만 쓴다(아래).
- **탐색형(찾을 때까지):** 대상의 위치를 모르는 일이다. 시간 제한이 없고, 탐험이 계속되는지를 감시한다.
  실행 전체 상한은 마지막 안전장치로만 남긴다.
  [목표 작성 규칙](2026-10-31-goal-condition-authoring-rules.md)대로 탐색형도 세 가지를 밝혀야 한다:
  무엇을 찾는지, 왜 찾는지, 찾았음을 어떻게 판정하는지. 진전 기준이 있으므로 "무기한 대기"가 아니다.
- **전환:** 탐색형은 대상을 찾으면 시간형(접근·채굴)으로 바뀐다.
  - 지금 관측으로 "찾음"을 알 수 있는 것은 조준선 블록(`hit_block`)이 대상일 때뿐이다. 즉 손이 닿는 거리에서만 알 수 있다.
  - 더 먼 곳에서 "보인다"를 알려면 새 관측이 필요하다. 이는 서버 특권 관측이므로 별도 조건으로 검토한다(§11).

### 시간형의 두 기준 시간 (사용자 제안, 2026-11-05)

사용자 제안: 하위 목표마다 행동 기록의 **최고(가장 빠른) 시간**을 저장하고, 그 시간에 일정 비율을 더한 만큼까지는
이상으로 보지 않는다. 예를 들어 최고 60초에 여유 20%면 72초까지는 정상이다. 탐험처럼 찾을 때까지 하는 부분은
일부러 기록하지 않는다. 이 기준과 RL의 시간 페널티를 함께 쓰면 더 효율적으로 움직이도록 유도할 수 있다.

기록으로 확인해 보니(§9.3), 최고 기록에 작은 여유를 더한 값을 **이상 기준으로 쓰면 정상 성공 회차 대부분이 걸린다.**
그래서 최고 기록의 두 가지 쓰임을 나눈다.

| 기준 | 계산 | 쓰임 | 넘었을 때 |
|---|---|---|---|
| 목표 시간 | 최고 기록 | RL 시간 페널티의 기준, 효율 지표(예: "최고 대비 1.8배") | 이상이 아니다. 느린 만큼 시간 비용만 준다 |
| 점검 기준 | 성공 기록의 상위값(최댓값 또는 높은 분위) × 여유 | 이상 감지 | 점검(§6) |

- 두 기준 사이는 "느리지만 정상"이다. 설계 원칙("비효율은 이상이 아니며 RL 시간 비용으로 다룬다",
  [설계](2026-11-03-iron-pipeline-demo-design.md) 26행)과 맞는다.
- 일의 양이 다른 단계는 단위당 시간으로 기록한다. 예: 오른 칸 수당, 아이템 개수당. 대상이 다른 제작은 대상별로 나눈다.
- 탐색형은 찾기 전 구간을 기록하지 않는다. 찾은 뒤의 접근·채굴 구간은 시간형이므로 기록한다.
- 최고 기록은 새 기록이 나올수록 내려가기만 한다. 목표 시간으로는 괜찮지만, 이상 기준으로 쓰면 시간이 갈수록 오탐이 늘어난다.
- 현재 파이프라인은 RL 학습을 하지 않는다. 시간 페널티는 단계별 학습을 할 때 쓸 설계 항목이다.

### 예: "철 캐줘" (빈 KB에서 재계획한 뒤의 RM2)

| 하위 목표 | 끝나는 방식 | 진행 신호 | 이상 신호 | 기록상 시간 (25회) |
|---|---|---|---|---|
| 원목 4개 | 탐색형 → 찾은 뒤 시간형 | 새 위치·새 시야, 원목 수 | 같은 경로 반복, 보호 블록 가드 | 완료 15회 2–132초 |
| 나무 곡괭이 제작 | 시간형 | 인벤토리 변화 | 제작 실패 | 완료 14회 5–12초 |
| 조약돌 3개 | 시간형 (주변에 돌이 있는 시연 월드 기준) | 조약돌 수 | 캤는데 드롭 없음, 필요한 도구를 잃음 | 완료 13회 14–37초 |
| 돌 곡괭이 제작 | 시간형 | 인벤토리 변화 | 제작 실패 | 완료 12회 3–9초 |
| 철광석 1개 | 탐색형 → 찾은 뒤 시간형 | 새 위치·새 시야, 철광석 수 | 같은 경로 반복, 필요한 도구를 잃음 | 완료 9회 15–557초 |

## 5. 고정 관측 목록

LLM은 이 목록에서만 신호를 고른다. 새 신호가 필요하면 별도로 검토한 뒤 새 revision으로 다시 요청한다.
LLM이 스스로 목록을 늘릴 수 없고, 생성된 코드를 `exec/eval`로 실행하지도 않는다.

| 신호 | 계산 근거 (현재 `Sample` 필드) | 현재 코드 |
|---|---|---|
| 목표 아이템 수 증가 | 서버 인벤토리 | `StallDetector` (`objective_inventory_increased`) |
| 새 위치 칸 / 새 시야 | 서버 위치(2칸 격자), yaw(8방위) | `StallDetector` (`new_position_cell`, `new_search_view`) |
| 같은 경로 반복 / 제자리 반복 | 위치 이력, 행동 키 | `StallDetector` (`repeated_cycle`, `stationary_repetition`) |
| 높이 상승 | 서버 y | `FastMonitor` (`expect: rise`) |
| 캤는데 드롭 없음 | 파괴 기록, 수확 가능 여부, 인벤토리 | `FastMonitor` (`harvest_without_drop`) |
| 필요한 도구를 잃음 | 인벤토리, 들고 있는 아이템 | `FastMonitor` (`needed_tool_lost`) |
| 찾음 (손 닿는 거리) | 조준선 블록 `hit_block` | 세션의 `mining_start` 판정 |
| 체력 | 서버 체력 | `FastMonitor` (`low_health`) |
| 이동 키를 누르는데 제자리 | 행동 키, 서버 위치의 약 2초간 변화 | 새 계산 (기존 관측만 사용) |
| 이미 간 곳만 맴돎 | 위치 칸·시야 방문 이력 | `StallDetector` (`no_progress`) |
| 시선 각도 | pitch | 새 계산 (기존 관측만 사용) |
| 월드 시각 | 서버 `world_time` (`Sample.tick`) | 기한 제약용 (§8) |

## 6. 넘었을 때: "점검" 범주

지금은 두 범주뿐이다: hold(세계를 멈추고 느린 경로로 감)와 기록만 하기. 그 사이에 세 번째 범주인 **점검**을 둔다.
시간 초과 자체를 이상으로 보지 않는다. 점검은 "전제가 맞는지 확인할 계기"로만 쓴다.
따라서 "비효율은 이상이 아니다" 원칙은 유지한다.

- **시간형이 점검 기준을 넘김 → 계획과 지식 점검.** 현재 단계의 전제(도구, 지식 claim)를 SQLite와 규칙으로 다시
  확인하고, 틀렸으면 재계획한다.
  - 예: E03(2차)은 틀린 지식 때문에 곡괭이 없이 조약돌 단계에 들어가 596초 동안 조약돌을 하나도 얻지 못했다.
  - 같은 단계의 다른 13회는 14–37초에 끝났다.
- **탐색형이 정지함(진행 신호 없음, 반복) → 탐색 전략 점검.** 어떤 대응을 쓸지는 열린 질문이다(§11).
  - 후보: 조건 문구 바꾸기, 공개된 규칙 보조, 실패로 보고.
  - 규칙 보조를 쓰면 그 사실을 알린다. 정책 실패를 숨기고 스크립트 제어로 대체하지 않는다.
- **목표에 시간 조건이 있을 때만 느림 자체가 문제가 된다.** 예: "해 지기 전에 철 캐줘". 이때도 감시 규칙에
  "느림은 이상"을 넣지 않고, 목표의 기한 제약(§8)으로 다룬다.

## 7. 비효율: 시간 페널티만으로는 부족하다

시간 페널티는 "빨리 끝내라"는 바깥 목표다. 하지만 무엇 때문에 느렸는지는 알려 주지 않는다.
600초짜리 탐색에서 벽에 대고 걸은 시간과 잘 둘러본 시간에 똑같은 비용이 붙는다. 그래서 RL이 원인 행동을 스스로 찾아야 한다.
실행 한 번이 5–15분이라 그만큼의 시행을 모으기도 어렵다.

### 7.1 기록에서 본 시간의 행방 (25회)

- 전체 14,688초 가운데 정책 실행이 95%다. 멈춘 시간(hold, LLM, 느린 경로)은 3%, 규칙 스킬은 2%다.
  비효율은 거의 전부 정책 행동 안에 있다.
- 정책 시간의 62%(8,695초)는 철광석 단계, 29%(3,984초)는 원목 단계에서 썼다.

탐색 단계를 "시간 안에 끝남(완료 또는 hold)"과 "시간 초과"로 나눠, 정책 틱 가운데 각 행동의 비율을 비교했다.

| 단계 | 결과 | 정책 틱 | 아래를 60° 넘게 봄 | 약 2초 제자리 (채굴 아님) | 이동 키를 누르는데 제자리 |
|---|---|---|---|---|---|
| 철광석 | 시간 안에 끝남 | 72,468 | 18.8% | 9.4% | 6.6% |
| 철광석 | 시간 초과 (3개 단계) | 19,140 | 46.3% | **71.0%** | **56.8%** |
| 원목 | 시간 안에 끝남 | 22,623 | 0.1% | 14.6% | 4.7% |
| 원목 | 시간 초과 (3개 단계) | 16,358 | 0.0% | 0.4% | 0.2% |

- **철광석 시간 초과는 대부분 막혀 있었다.** 정책 틱의 71%가 제자리였고, 57%는 이동 키를 누르는데도 움직이지 못했다.
- **원목 시간 초과는 반대로 계속 움직였다.** 제자리 비율은 0.4%다. 그런데 이 3회 모두 `no_progress`(새 칸·새 시야 없음)가
  켜졌다(§9.2). 이미 간 곳을 맴돈 것이다.
- 같은 "느림"인데 원인이 다르다. 철광석은 물리적으로 막혔고, 원목은 탐색 범위가 문제였다. 시간 페널티는 둘을 구분하지 못한다.
- 같은 행동이 하위 목표에 따라 정상일 수 있다.
  - 오르기에서는 정책 시간의 65%가 아래를 봤고 96%가 제자리였다. 기둥 쌓기의 정상 동작이다.
  - 원목은 끝난 경우가 오히려 제자리 비율이 높았다(14.6% 대 0.4%).

한계: 시간 초과 단계는 원목 3개, 철광석 3개뿐이다. 지표는 기록을 본 뒤 정했다. 아래를 보는 것은 파고 내려가는 정상 동작일 수도 있다.

### 7.2 제안: 낭비 신호와 유형별 대응

| 낭비 유형 | 신호 예 | 대응 |
|---|---|---|
| 물리적 막힘 | 이동 키를 누르는데 제자리 | 진행 불가 신호다(느림이 아님). `blocked_overhead`처럼 점검하고 막힘을 푸는 하위 목표를 넣는다. 학습에서는 그 구간에 비용 |
| 탐색 범위 | 이미 간 곳만 맴돎, 새 시야 없음 | 학습: 새 칸·새 시야에 작은 보상(상한 있음). 지식: 대상이 있을 만한 곳(예: 철광석이 나오는 높이) |
| 행동 속도 | 시간형 단계가 최고 기록보다 느림 | 학습: 최고 기록 기준의 시간 페널티(§4) |
| 계획·시스템 | 규칙 대기, hold, LLM 대기 | 학습 대상이 아니다. 계획과 코드를 고친다(지금은 전체의 5%) |

- 낭비 신호를 그대로 보상으로 주면 정책이 그 신호만 쫓을 수 있다. 예를 들어 새 칸만 돌아다니고 원목은 캐지 않을 수 있다.
  그래서 보상은 작게 두고 상한을 두어, 성공 보상이 지배하게 한다. 가능하면 최적 정책을 바꾸지 않는 potential 기반 형태를 쓴다.
- 어떤 낭비 신호를 쓸지는 하위 목표별로 고르고, 기록에서 성공과 실패를 실제로 가르는지 확인한 뒤 정한다(M2).

## 8. 제약 조건 공식화

지금 제약은 흩어져 있고 형식이 없다.

- **계획에서 유도한 것** (`planner.oversight()`):
  - 보호 블록(`guarded`): 목표 아이템과 정책 단계 블록의 계열. 필요한 도구 없이 부수지 않는다.
  - 필요한 아이템(`needs`): 잃지 않는다.
- **시스템:** 체력 6 이하면 hold, 실행 상한 900초, API·지식 라운드 예산(`budgets`).
- **목표 작성 계약의 `constraints`** (`goal_contract.py`): 자유 문장 최대 8개. 정책 문구에만 들어가고 판정에는 쓰이지 않는다.
- **사용자 발화의 제약**("해 지기 전에", "곡괭이 아껴서")을 받는 길은 없다. 목표 파싱은 아이템과 개수만 뽑는다.

### 8.1 세 가지 형태

| 형태 | 뜻 | 예 | 시간 논리 표기 |
|---|---|---|---|
| 항상 | 실행 내내 참이어야 한다 | 철광석을 맨손으로 부수지 않음, 필요한 도구를 잃지 않음, 체력 > 6 | G p |
| 기한 | 정한 시각 전에 참이 되어야 한다 | 해 지기 전에 철광석 1개 | F≤T p |
| 조건부 | 어떤 조건일 때만 적용된다 | 구덩이를 탈출하는 동안 흙은 탈출에만 쓴다 | G(q → p) |

RM은 이런 형태를 상태 전이로 나타낼 수 있다. 그래서 하위 목표 RM과 같은 틀에 둔다.

### 8.2 제약 하나의 필드 (형식 예시이며, 확정된 스키마는 아님)

```json
{"id": "c-deadline-1", "form": "deadline", "scope": "goal",
 "source": {"kind": "human", "author": "team", "note": "해 지기 전에"},
 "predicate": "server inventory iron_ore >= 1",
 "by": "world_time mod 24000 < 12000",
 "strength": "hard", "on_risk": "warn", "on_violation": "report_violation"}
```

| 필드 | 값 | 정하는 쪽 |
|---|---|---|
| `form` | `always` / `deadline` / `conditional` | 작성자(사람) → 프로그램 검사 |
| `scope` | 목표 전체 / 특정 하위 목표 | 작성자(사람) → 프로그램 검사 |
| `source` | 사람 작성 / 계획 / 시스템 | 출처별 규칙(아래) |
| `predicate`, `by`, `while` | §5 관측만 쓰는 제한된 연산식 | 컴파일과 반례 검사 |
| `strength` | `hard`(어기면 안 됨) / `soft`(어기면 비용) | 계획·시스템 제약은 hard. 사람이 쓴 제약은 작성자가 정한다 |
| `on_risk`, `on_violation` | 경고, 점검, hold, 행동 전 차단, 비용, 위반 보고 | 프로그램 규칙 |

지금 있는 제약을 이 형식으로 옮기면 다음과 같다.

| 현재 | form | source | strength | 처리 |
|---|---|---|---|---|
| 보호 블록 가드 | always | 계획 | hard | 행동 전 차단(공격 가림) |
| 필요한 아이템 | always | 계획 | hard | hold (`needed_tool_lost`) |
| 체력 > 6 | always | 시스템 | hard | hold |
| 실행 상한 900초 | deadline | 시스템 | hard | 정지 |
| API 호출 예산 | always (호출 수 ≤ 예산) | 시스템 | hard | 호출 거부 |

### 8.3 규칙

1. **출처 (2026-11-05 결정):** 제약은 사람이 작성한다. 계획·시스템 제약은 프로그램이 만든다.
   LLM은 제약을 추가하거나 풀지 않는다. 사람이 쓴 제약도 LLM 명세와 같은 검사(관측, 컴파일, 반례)를 받는다.
   LLM 제약을 미룬 이유:
   - 잘못된 금지는 스스로를 숨긴다. 금지된 행동을 하지 않으니, 그게 괜찮았다는 관측도 끝내 생기지 않는다.
   - 2차 평가에서도 관측되지 않는 LLM 조건 오류(Silk Touch)가 반박되지 않고 남았다([결과](../iron-pipeline-demo-results-2026-11-05.md) §5-11).
   - 나중 후보: 사용자 발화에서 인용해 추출하기, 근거 있는 LLM 추론 제약을 그림자 모드(막지 않고 기록만)로 두기.
2. **관측:** §5 목록만 쓴다. 판정할 관측이 없으면(예: "조용히") `unsupported`와 이유를 돌려준다.
3. **우선순위:** 시스템(STOP, 안전) > 사용자 hard > 계획 유도 > soft 순이다. 충돌하면 실행 전에 보고한다.
4. **미리 막을 수 있으면 미리 막는다:** 되돌릴 수 없는 행동(블록 파괴)은 지금의 가드처럼 행동 전에 가린다. 나머지는 사후에 감지한다.
5. **기한 실현성 검사 (최고 기록의 또 다른 쓰임):**
   - 계획 시점: 남은 시간형 하위 목표의 최고 기록 합이 남은 시간보다 크면, 기한 안에 불가능하다고 실행 전에 보고한다.
   - 실행 중: 점검 기준의 합이 남은 시간보다 크면 위험을 경고한다.
   - 탐색형이 남아 있으면 시간을 장담할 수 없다고 그대로 알린다. 추정치를 지어내지 않는다.
6. **성공 판정과 분리:** 결과는 목표 달성(서버 인벤토리)과 제약 준수를 따로 보고한다.
   예: "철광석 1개 획득, 기한 제약 위반".

## 9. 기존 기록에서 본 근거 (25회, 읽기 전용 재집계)

### 9.1 단계별 소요 시간 (단계 시작 → 종료, 초)

| 스킬 | 완료 | 완료하지 못함 |
|---|---|---|
| 제작 `craft` | 26회, 3–12 | hold 10회 |
| 장착 `equip` | 17회, 1–2 | 없음 |
| 조약돌 `mine_stone_text` | 13회, 14–37 | 시간 초과 2회: 596 (E03, 틀린 지식), 21 (실행 상한에 닿음) |
| 오르기 `climb_out_text` | 16회, 중앙값 8, 최대 71 | hold 1회 (E07, 탈출 블록 허비) |

시간형으로 볼 단계는 시간이 좁게 모인다. 탐색 단계는 꼬리가 길고, 특히 철광석은 성공과 실패의 시간이 겹친다.
그래서 탐색에는 시간 제한이 맞지 않는다.

### 9.2 기록만 하던 정체 신호가 켜진 시점

| 실행 | 신호 | 단계 | 켜진 시점 | 단계 종료 | 결과 |
|---|---|---|---|---|---|
| r2/E01 | `repeated_cycle` | 철광석 | 69초 | 744초 | 시간 초과 |
| r2/E06 | `repeated_cycle` | 철광석 | 72초 | 200초 | 시간 초과 |
| r2/W3 | `repeated_cycle` | 철광석 | 46초 | 808초 | 시간 초과 |
| r2/W1 | `no_progress` | 원목 (2번째) | 52초 | 424초 | 시간 초과 |
| r3/E01 | `no_progress` | 원목 | 51초 | 648초 | 시간 초과 |
| r3/E02 | `no_progress` | 원목 | 48초 | 623초 | 시간 초과 |
| r2/W1 | `no_progress` | 원목 (1번째) | 108초 | 283초 | hold |
| r2/E07 | `repeated_cycle` | 오르기 | 38초 | 101초 | hold (블록 허비) |

- 탐색 단계의 시간 초과 6회 모두, 단계 시작 46–72초에 정체 신호가 이미 켜져 있었다. 그 뒤에도 단계는 200–808초까지 이어졌다.
- 완료된 탐색 단계(원목 15회, 철광석 9회)에서는 두 신호가 한 번도 켜지지 않았다.
- 반대로 맨손 철광석 탐색이 451–783초 걸린 뒤 결국 찾은 4회(r2/E04·E06·E07, r3b/E02)에서도 신호는 없었다.
  - 탐험은 계속하면서 오래 걸린 경우라, "찾을 때까지" 원칙에서는 정상이다.
  - 다만 r3b/E02는 이 때문에 실행 상한에 닿았다. 신호는 "탐험이 멈춤"을 잡을 뿐 "느림"은 잡지 않는다.
- 오르기에서는 `repeated_cycle`이 성공 회차(W2)에서도 켜졌다. 제자리 점프는 오르기의 정상 동작이기 때문이다.
  같은 신호라도 하위 목표 종류에 따라 볼지 말지 정해야 한다는 근거다.
- `no_goal_progress`는 25회 중 거의 모든 실행에서 켜졌다. 구분력이 없다.

### 9.3 "최고 기록 + 여유"를 이상 기준으로 쓰면

완료된 시간형 단계 가운데 각 여유로 계산한 기준을 넘는 회차의 수다. 모두 정상 성공이므로, 걸리면 오탐이다.

| 단계 | 완료 | 최고 | 최대 (최고의 몇 배) | +20% | +50% | +100% |
|---|---|---|---|---|---|---|
| 제작 (전체) | 26 | 2.7초 | 12.3초 (4.6배) | 18회 | 17회 | 16회 |
| 장착 | 17 | 1.0초 | 1.8초 (1.7배) | 10회 | 5회 | 0회 |
| 조약돌 3개 | 13 | 13.5초 | 37.0초 (2.7배) | 10회 | 8회 | 4회 |
| 오르기 | 16 | 3.4초 | 70.8초 (21배) | 15회 | 12회 | 9회 |

대상별·단위당으로 나눠도 크게 줄지 않는다(+20% 기준):
- 나무 곡괭이 제작: 14회 중 13회 (최고 5.4초)
- 돌 곡괭이 제작: 12회 중 4회 (최고 2.7초)
- 오르기 한 칸당: 16회 중 13회 (최고 1.1초, 최대 24.3초)

반면 성공 기록의 최댓값 × 1.2(조약돌이면 약 44초)로 잡아도 E03(596초)은 잡힌다.
최고 기록은 목표로 쓰고, 이상 기준은 성공 기록의 퍼짐으로 정해야 하는 근거다.

**한계:**
- 25회뿐이고 seed는 개발·평가 각각 하나다.
- 사후 집계다.
- 같은 기록으로 기준을 정하고 평가하면 과적합이므로, 평가에는 새 seed가 필요하다.
- 신호가 켜진 뒤 무엇을 했으면 성공했을지는 이 기록으로 알 수 없다.

## 11. 하지 않는 것과 열린 질문

**하지 않는 것:**
- LLM이 새 센서나 관측, 자유 코드를 만드는 것
- LLM이 기준 시간 숫자나 최종 성공 조건을 정하는 것
- 시간 초과로 성공이나 실패를 대신 판정하는 것 (성공은 서버 인벤토리로만 판정)
- 정책 학습 (단계별 adapter 학습은 별도 과제)

**열린 질문 (팀이 정할 것):**
1. 점검하는 동안 정책을 멈출지(hold), 계속 움직이게 둘지.
2. 탐색이 멈췄을 때 어떻게 대응할지: 조건 문구 변경, 공개된 규칙 보조, 실패 보고 중 무엇을 쓸지.
3. 점검 기준의 여유: 성공 기록의 최댓값에 몇 배를 둘지, 아니면 높은 분위를 쓸지. 목표 시간(최고 기록)을 넘긴
   만큼 주는 RL 시간 페널티의 모양(초과 비율에 비례 등). 기록이 없는 새 하위 목표의 초기값은 무엇으로 할지.
4. "찾음"을 더 일찍 알기 위한 관측(멀리서 보임)을 둘지. 둔다면 특권 관측이므로 영상만 쓰는 조건과 구분한다.
5. 탐색 진행 신호의 창 크기. 현재 값은 개발 가설이다: 탐색 400틱(20초), 2칸 격자, 8방위.
6. 낭비 신호를 학습 보상에 얼마나, 어떤 형태로 넣을지. 신호만 쫓는 보상 해킹의 위험이 있다.
7. LLM 제약(발화 인용 추출, 근거 있는 추론)을 언제, 어떤 등급(그림자 모드, 행동 전 hold)으로 열지.

## 12. 발표용 세 줄

- **지금:** 감시 규칙은 사람이 썼다. 실패 대부분은 15분 상한에 닿아서야 드러난 탐색 정체였다.
- **제안:** LLM이 하위 목표마다 끝나는 방식(시간형 / 찾을 때까지)과 감시 신호를 제안하고, 프로그램이 검증한다.
  시간형은 최고 기록을 목표 시간(RL 시간 페널티)으로, 성공 기록의 퍼짐을 점검 기준으로 쓴다.
  비효율은 유형별 낭비 신호로 나누고, 제약은 항상 / 기한 / 조건부 형식으로 적는다.
- **근거:** 기록상 탐색 시간 초과 6회 모두, 46–72초에 정체 신호가 이미 켜져 있었다. 기록만 하고 쓰지 않았을 뿐이다.
  같은 시간 초과라도 철광석은 정책 시간의 71%가 제자리였고, 원목은 계속 움직였지만 같은 곳을 맴돌았다.
