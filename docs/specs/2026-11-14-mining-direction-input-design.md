# 채굴 v2: 대상 블록 방향을 특권 입력으로 — 설계 (2026-11-14)

- 상태: 사용자 지시(11/14) "계속해줘. 중간에 멈추지 말고 네 판단에 필요하다고 판단되면 해". 세부는 내가 정했다(**(내 결정)**).
- 앞선 결과: [대상 위치를 섞은 채굴 학습](../mixed-layout-results-2026-11-13.md). 학습하지 않은 낮은 철광석을 layout 4/4, layout2 4/4로 캤다.
  하지만 성공 단계 시간 중앙값이 21초·41초로 공식 19초보다 길어 개발 판정에서 두 번 떨어졌다.
  학생은 근처에서 학습 때 높이를 보다가 가까이 붙어서야 내려다봤다.
- 같은 날 점프 v2에서 같은 문제를 봤다. 화면 밖이나 예상 밖 위치의 목표 방향을 헤드 입력이 담지 못했다.
  그래서 같은 구조를 쓴다: [점프 v2 설계](2026-11-14-jump-direction-input-design.md)(특징 입력, 배율 10, 기록·재계산 검사).
- 과업, 단계, 교사(sight), 성공 판정(서버 인벤토리)은 그대로 둔다. 바꾸는 것은 학생 헤드의 입력뿐이다.

## 1. 특징 (특권 입력, 기록에 밝힘)

교사 라벨이 겨누는 블록(`target_of`: 캐는 중이거나 조준한 대상 블록, 아니면 가장 가까운 남은 대상, collect에서는 방금 깬 블록)까지:

| 이름 | 값 |
|---|---|
| `sin_yaw`, `cos_yaw` | 눈에서 블록 중심까지 yaw 차이의 sin·cos |
| `pitch` | pitch 차이 / 60(±1로 자름) |
| `dist` | 눈에서 블록 중심까지 거리 / 9(0..1로 자름) |

- 대상이 없거나, 단계를 모르거나, gui 단계이면 0 벡터다. 특징은 `LiveStageFeed`가 단계와 같은 행·같은 블록 배치로 계산한다.
- 헤드는 특징에 배율 10을 곱해 넣는다(점프 v2 오프라인 점검과 같은 이유).

## 2. 학습

- 자료: 앞선 채굴 자료 l-r0-9와 같은 실행(R0–R6 벽 + L7–L9 세 배치, 교사 sight, 철광석 제외)에 특징을 다시 계산해 넣는다(`m-r0-9`).
  그다음 배치 균형 사본을 만든다(`m-r0-9g`, layout2와 같은 묶음). 검증 실행도 l-r0-9와 같다(L9의 6판).
- m-a: m-r0-9g로 학습(KL 10, 균형, patience 2, 특징 배율 10).
- **오프라인 관문(게임 전, 미리 정함):** m-a의 검증 NLL이 같은 행에서 layout2(l-final2)의 검증 NLL보다 낮아야 한다. **(내 결정)**
- DAgger 한 라운드: L10 = m-a로 학습 배치 3개 × 블록 6개(샘플링 12) → 자료 m-r0-10 → 배치 균형 사본 → m-final. 검증은 L10의 6판. **(내 결정)**

## 3. 평가 (게임 전에 정함)

- **개발:** 철광석, low 배치(학습 안 한 높이), seed 130363, 샘플링 1–4, 갈래 `direction`(m-final) 4판.
  공식과 sight 갈래는 11-13 개발 결과(`dev-low/`)를 그대로 비교에 쓴다. seed, 샘플링, 배치, 게임 빌드가 같다.
  **판정:** 앞선 라운드와 같은 `hold_verdict(공식, sight, direction)`.
  성공 수가 sight 이상이고, 파괴 비율이 sight보다 높고, 성공 단계 시간 중앙값이 공식(19초) 이하여야 한다.
- **최종(개발 통과 때만):** final5 seed 223606(처음 씀), 샘플링 51–58, 갈래 direction, sight, 공식 각 8판. 판정은 같은 규칙이다.
- 개발 seed 130363 low 배치는 이 질문에 세 번째로 쓴다. 개발용이라 허용하지만, 최종 판정만 일반화 증거로 본다.
- 실행 스크립트: `results/multi-block-20261108/launch/direction.sh`. 점프 v2 배치(`jump2.log`)가 끝난 뒤 시작한다(게임은 한 번에 하나).
