  - "그거 설계 명세서 만들어줘. 구현은 다른 세션에서 진행할거야"
- 표시 규칙:

- 관련 문서:

## 0. 요약

- 지금 학습한 기술 헤드의 특권 입력은 모두 "블록이나 지점까지의 방향·거리"다.
  - 채굴 조준점, 놓을 칸·면, 다리 가장자리, 다음 발판이 여기에 속한다.
  - 코드에서는 정답 블록 지도(fixture로 채운 `Geometry`)와 서버 자세로 계산한다.
- 이 설계는 특권 숫자마다 예측기를 따로 만들지 않는다.
  - 화면과 정당한 자기 자세만으로 **주변 블록 지도**를 복원하는 인식 모듈 하나를 둔다.
  - 그 지도를 정답 지도 자리에 꽂는다.
- 기존 특징 함수와 헤드는 그대로 쓴다.
  - 새 과업은 "지도에서 숫자를 계산하는 함수"만 더하면 된다.
- 인식 모듈은 행동 라벨이 필요 없다.
  - 학습 때만 게임 내부의 실제 블록으로 라벨을 붙인다(특권 라벨).
  - 그래서 시험장 몇 개가 아니라 다양한 자연 월드에서 자료를 모을 수 있다.

## 1. 배경과 근거

### 1.1 지금의 특권 입력

| 헤드 | 특징 | 지금 계산 근거 | 정당하게 바꿀 길 |
|---|---|---|---|
| 철광석 채굴 v3 | `AIM_FEATURES`: 조준점까지 yaw sin·cos, pitch, 거리 | fixture 블록 − 부서진 블록(`Geometry`), 서버 자세 | 지도에서 대상 블록·보이는 면을 찾는다 |
| 블록 놓기 | `PLACE_FEATURES`: 목표 칸 방향·거리, 놓을 면 방향 | 과업 좌표, 주변 고체 블록(`choose_face`) | 목표 칸은 설계도(플래너), 주변 고체는 지도 |
| 건축 | `BUILD_FEATURES` = 놓기 + 남은 칸 | 설계도, 서버 설치 기록, 자기 자세 | 설계도는 그대로, 고체는 지도 |
| 다리 잇기 | `BRIDGE_FEATURES`: 진행 방향, 조준 pitch, 가장자리, 남은 칸 | 과업 좌표(발판·다리 칸) | 출발·도착 발판과 가장자리를 지도에서 찾는다 |
| 점프 코스 v2 | `JUMP_FEATURES`: 다음 발판 방향, 가장자리, 틈, 높이 차 | 코스 좌표 | 발판 윗면을 지도에서 찾는다(한 번 본 발판은 지도에 남는다) |
| 기술 내부 단계(먼 곳→조준→채굴→회수) | 단계 one-hot | fixture 좌표와 서버 자세(`stage_replay`) | 지도 + 정당한 관측(조준선 블록 등) |

- 위치: `reacquire_teacher.py`의 `MINING_FEATURES`·`AIM_FEATURES`·`target_of`, `place_task.py`의 `place_features`·`choose_face`,
  `build_task.py`, `bridge_task.py`, `jump_course.py`, `pipeline/stage_replay.py`의 `Geometry`·`fixture_blocks`, `pipeline/stage_live.py`.
- 새로 학습한 기술은 모두 LLM vocabulary에 없다. 이유는 위 특권 입력이다([최소 요구 능력](2026-11-15-minimum-capability-gaps.md) §2).

### 1.2 특권 입력을 빼면 무너진다는 근거

- 점프:
  - 특권 방향 없는 v1은 개발 1/8, 방향을 넣은 v2는 개발 7/8, 최종 8/8이었다.
  - 오프라인 점검에서 j2-final 헤드에 참 단계 + 특징 0을 넣었다.
    - 라벨 쪽으로 돌 확률이 0.80에서 0.52로 떨어졌다.
    - 라벨이 달릴 때 달릴 확률은 0.92에서 0.15로 떨어졌다.
  - 출처: [점프 특징 예측 오프라인 점검](2026-11-14-jump-feature-predictor-offline.md) §5.
- 채굴: 11-07의 화면만 보는 학생은 철광석이 화면 밖일 때 교사 라벨을 거의 맞히지 못했다(일치율 .015–.025, [progress](../progress.md) "돌아서기 학습 1단계").

### 1.3 STEVE-1 latent로는 부족하다는 근거

- STEVE-1 cond latent(2048칸)로 점프 특징을 예측하려 했다. 결과는 아래와 같다([같은 문서](2026-11-14-jump-feature-predictor-offline.md) §5).
  - 화면 밖 도는 방향 정확도는 0.52–0.55, 화면 안(15도 미만)에서도 0.61–0.69였다.
  - 결론: latent는 다음 행동용 표현이지 물체 위치 표현이 아니다.
- 고정된 STEVE-1 영상 인코더 특징으로 조준선 블록을 선형 분류했다([11-07 E절](../skill-stages-replay-2026-11-07.md)).
  - 평가 월드 균형 정확도 0.72, 학습 화면 0.99로 과적합했다.
  - 이 probe는 조준선 한 칸만 물었다. "화면 어디에 무엇이 있나"는 묻지 않았다.
- 그래서 화면 픽셀에서 위치를 직접 배우는 별도 모듈이 필요하다.

### 1.4 STEVE-1 전체 미세조정을 하지 않는 이유

- GPU는 GTX 1060 3GB다.
- `weights/steve1/steve1.weights`는 998,232,471바이트(fp32, 약 2.5억 파라미터)다.
  - Adam 전체 학습은 가중치·기울기·상태만 약 4GB가 들어 3GB를 넘는다.
  - 헤드 학습만으로도 최대 약 2.6–2.9GB를 썼다.
- 수만 행 규모의 DAgger 자료에 맞추면 과적합할 위험이 크다.
- 공식 일반 능력(원목·조약돌 채굴)도 잃을 수 있다.
  - 지금 설계(고정 + 0 초기화 residual + KL)가 이를 막고 있다.

## 2. 목표와 범위

- **목표:**
  - 화면 프레임과 정당한 자기 자세만으로 주변 블록 지도를 복원한다.
  - 지금 헤드의 특징을 그 지도와 정당한 과업 정보(설계도)에서 계산한다.
  - fixture·서버 기하 없이 같은 헤드가 같은 과업을 해내는지 서버 상태로 판정한다.
- **범위 밖:**
  - STEVE-1 미세조정(§1.4).
  - 헤드 구조 변경(P4 전까지). 헤드 재학습은 P4에서만 한다.
  - 몹, 떨어진 아이템, GUI·인벤토리 화면. 지도 채널 자리만 남긴다(§4.2).
  - 탐색 학습. 지도의 "모름" 칸을 쓰는 별도 설계로 둔다(§8).
  - 텍스처팩. 사용자가 확인을 미뤘다. 기본 텍스처만 쓴다.
- **세지 않는 것:**
  - 인식 정확도, 지도 오차, 오프라인 헤드 확률은 정책 성공이 아니다.
  - 정책 성공은 지금처럼 실제 서버 상태(인벤토리·설치 기록·위치)로만 판정한다.

- 라벨 생성 코드와 실사용 특징 코드는 모듈을 나눈다.
  - 실사용 경로가 라벨 모듈을 import하지 않는지 테스트로 묶는다.

## 4. 구조

```
화면 프레임 ──► (A) 프레임 인식기 ──► 칸별 블록 종류 + 거리 ──┐
자기 자세(F3 값) ──────────────────────────────────────────┼─► (B) 지도 누적 ──► (C) PerceivedGeometry ──► 기존 특징 함수 ──► 헤드
설계도(플래너) ─────────────────────────────────────────────────────────────────┘
```

### 4.1 (A) 프레임 인식기

- 입력: 화면 프레임.
  - 해상도는 16:9를 유지해 256×144 또는 160×90 중 P1에서 고른다 **(내 결정)**.
  - STEVE-1의 128×128은 가로를 찌그러뜨리므로 기하용으로 쓰지 않는다.
- 출력: 화면을 격자(기본 16×9 칸, 설정값)로 나눈 칸마다 세 가지를 낸다.
  - 블록 종류 확률
  - 칸 중심 광선이 처음 닿는 블록까지의 거리
  - 하늘·먼 곳 여부
- 블록 분류 `perception_classes_v1` **(내 결정)**:
  - `frame_labels.CLASSES`(공기, 방벽, 잔디, 흙, 돌, 원목, 철광석, 작업대, 기타)에 지금 과업의 블록을 더한다.
    - 더할 블록: 조약돌, 석탄·청금석 광석, 모래, 점토, 흰 양털, 참나무 판자, 석재 벽돌.
  - 버전 문자열을 체크포인트와 기록에 남긴다.
- 후보 둘을 P1에서 비교한다 **(내 결정)**.
  - **A1:** 픽셀에서 바로 학습하는 작은 인코더-디코더(목표 500만 파라미터 이하).
  - **A2:** 고정 STEVE-1 영상 인코더의 중간 공간 특징 위에 작은 디코더.
    - 실행 중 STEVE-1이 이미 계산하므로 추가 비용이 작다.
    - 마지막 2048차원 출력은 공간 정보가 없어서 쓰지 않는다.
- 공식 STEVE-1 가중치는 바꾸지 않는다.

### 4.2 (B) 지도 누적

- 자기 주변 월드 좌표의 3D 칸 격자를 둔다(기본 가로 ±16, 세로 ±8, 설정값).
- 칸마다 저장하는 값:
  - 블록 종류 증거
  - 확신도
  - 마지막으로 본 틱
- 갱신 방식:
  - 프레임마다 칸 예측을 자기 자세와 카메라 모델(§6 P0에서 보정)로 3D에 올린다.
  - 광선이 닿은 칸에는 종류 증거를, 그 앞 칸들에는 공기 증거를 더한다.
- 블록이 바뀌는 경우(자기가 부수거나 놓음)에는 서버 기록을 쓰지 않는다. 다시 본 관측이 옛 값을 덮는다.
  - 최근 관측에 가중치를 더 준다.
- 본 적 없는 칸은 "모름"이다. 확신도가 문턱(τ) 미만인 칸도 모름으로 친다.
- 채널 자리: 블록 종류만 v1에서 쓴다.
  - 몹·아이템 채널은 이름만 예약한다.

### 4.3 (C) PerceivedGeometry와 과업 기하 추출

- `pipeline/stage_replay.Geometry`와 같은 인터페이스를 가진다(`blocks`, `by_family`, `add`, `remove`, `copy`).
  - 확신도 τ 이상인 칸만 블록으로 내놓는다.
  - 추가로 `unknown(pos)`와 `confidence(pos)`를 둔다.
- 기하를 쓰는 기존 함수는 이것을 그대로 받는다: `target_of`, `aim_view`, `choose_face`의 고체 목록.
- 과업 좌표를 쓰는 기술은 얇은 추출기를 둔다. 새 과업도 이 층만 더한다.
  - 점프: 서 있을 수 있는 윗면을 연결해 발판을 만든다.
  - 다리: 출발·도착 발판과 가장자리를 찾는다.
  - 놓기·건축: 목표 칸은 설계도에서, 주변 고체는 지도에서 가져온다.
- 특징 계산은 기존 함수를 그대로 쓴다.
  - 그래서 "참 기하 vs 지도 기하"의 차이가 곧 인식 오차다.

### 4.4 기하 출처 스위치

- 각 feed(`LiveStageFeed`, 놓기·건축·다리·점프 feed)에 `geometry_source = 'fixture' | 'perceived'`를 둔다.
- 기본값은 `'fixture'`다.
  - 기존 CLI·체크포인트·완료 실험의 동작과 해시를 바꾸지 않는다(AGENTS.md).
- `'perceived'`에서는 fixture·과업 좌표를 읽는 코드 경로를 아예 타지 않는다. 테스트로 묶는다.
  - 예외: 설계도는 과업 명세로 받는다.

## 5. 자료와 라벨

### 5.1 특권 라벨 생성 (학습·분석 전용)

- **L1 칸 라벨:** 프레임마다 칸 중심 광선을 게임 안에서 레이캐스트해 (처음 닿은 블록, 거리)를 기록한다.
  - 실제 렌더 카메라(FOV, 화면비, 눈 높이)로 쏜다. 그래서 프레임과 정확히 맞는다.
  - 읽기 전용 관측 패치로 만든다. 기존 `WorkshopObservation.java`처럼 월드를 쓰지 않는다.
- **L2 주변 블록:** N프레임마다 자기 주변 칸의 실제 블록을 덤프한다. 지도 평가(P2)의 정답이다.
- 파일 이름과 스키마에 `privileged_labels`를 넣는다. 정책·헤드 입력 경로에서 읽지 않는다.
- 시점 일치:
  - 서버 자세는 키 입력보다 약 4틱 늦다([progress](../progress.md) 점프 코스 기록).
  - 라벨 카메라는 클라이언트 자세 기준이어야 한다.
  - 화면 흔들림(view bobbing)은 끄거나 라벨에 반영한다. P0에서 확인한다.

### 5.2 수집

- 자연 월드를 돌아다니며 화면 + L1 + L2를 모은다.
  - 걷는 주체는 공식 STEVE-1 프롬프트("explore" 계열, "mine …")와 스크립트 시야 훑기를 섞는다 **(내 결정)**.
  - 이 수집은 정책 평가가 아니다. 수집 중 성공을 정책 성공으로 세지 않는다.
- 광석처럼 드문 블록은 자연 지형 안에 fixture로 섞어 근거리 예시를 늘린다.
  - 그 fixture 좌표는 라벨에만 쓴다.
- 기존 시험장 기록(2단계마다 저장한 프레임)은 지형 정답이 없으면 라벨로 쓰지 않는다.
  - 예외: fixture 블록에 닿은 칸만 쓰는 부분 라벨. 쓰면 기록에 밝힌다.
- 규모 목표: 학습 world seed 20개 이상, 라벨 프레임 5만 장 이상 **(내 결정)**.
  - 바이옴(숲·평원·동굴 입구)을 섞는다.

### 5.3 seed 분리

- 인식 학습·개발·최종 world seed를 새로 정한다.
- 정책 개발·최종에 쓴 seed는 인식 학습에 쓰지 않는다.
  - 예: 130363, 104729, 223606, 264575, 577215, 662607, 357913, 244948, 302585, 866025.
- "처음 씀" seed는 쓰기 전에 기록에 없는지 확인한다.
  - `docs/`와 각 결과 폴더의 원장을 grep으로 확인한다.
  - 배치가 도는 중에는 `results/` 전체를 스캔하지 않는다.
- 헤드 오프라인 점검(P2)의 자료 생성기는 학습 seed가 아닌 실행을 거부한다(점프 예측 점검 §2). 이 보호 장치를 우회하지 않는다.

## 6. 단계와 판정 (각 단계는 확인할 수 있는 상태 변화로 끝난다)

판정 수치는 그 단계의 자료를 보기 전에 정하고 원장에 남긴다. 아래 수치는 제안이며 **(내 결정)**이다.
구현 세션이 단계 시작 전에 고칠 수 있다. 고치면 이유를 남긴다.

### P0 카메라 보정 (학습 없음)

- 카메라 모델(FOV, 화면비, 눈 높이, 흔들림 처리)로 화면 가운데 광선을 쏜다.
- 판정:
  - 그 광선이 클라이언트 조준선 기록(`hit_block`·`hit_pos`)과 같은 블록에 닿는 비율이 99% 이상.
  - L1 라벨을 프레임에 겹친 그림을 사람이 몇 장 확인한다.
- D1이 "자세를 직접 읽기"면 같은 프레임에서 F3 OCR(`f3_bitmap.py`) 값과 1e-2 블록 안에서 일치하는지 확인한다.

### P1 프레임 인식기 (오프라인, 인식 개발 seed)

- 지표:
  - 칸 단위 블록 종류의 클래스별 재현율·정밀도
  - 거리 오차(자기 6블록 안 칸의 중앙 절대 오차)
  - 과업 대상 블록 검출(8블록 안, 재현율·정밀도)
- 판정(A1·A2 각각):
  - 과업 대상 블록(철광석·원목·조약돌·석재 벽돌) 재현율 0.80 이상, 정밀도 0.80 이상.
  - 6블록 안 거리 중앙 오차 0.5블록 이하.
- 함께 보고:
  - 11-07 CNN probe(조준선 블록 균형 정확도 0.72)와 같은 질문의 값
  - VRAM, 추론 시간
- 통과한 후보 중 VRAM이 작은 쪽을 고른다.

### P2 지도·특징 오차 (오프라인, 학습 seed의 기존 헤드 기록 재생)

- 기록된 프레임 + 클라이언트 자세만으로 지도를 만든다.
- 그 지도로 계산한 특징을 같은 행의 특권 특징과 비교한다.

| 헤드 | 판정 (모두 넘어야 그 헤드의 P3로 간다) |
|---|---|
| 채굴 v3 | 대상을 본 적 있는 행에서 조준 방향 오차 10도 이하(교사 카메라 한 번의 상한) 80% 이상, 거리 오차 1블록 이하 80% 이상 |
| 놓기·건축 | 목표 칸 방향 오차 10도 이하 90% 이상, 고른 면 일치 0.90 이상 |
| 점프 | 다음 발판이 화면 밖인 행에서 도는 방향 부호 일치 0.80 이상(11-14 기준 2와 같음) |
| 다리 | 진행 방향 오차 10도 이하 80% 이상, 가장자리 거리 오차 0.3블록 이하 80% 이상 |
| 공통 | 헤드에 지도 특징을 넣었을 때 교사 라벨 쪽 확률이 참 특징 때보다 0.10 넘게 떨어지지 않는다(11-14 기준 3과 같음) |

### P3 게임 평가 (헤드별, 게임 전에 판정을 따로 적는다)

- 갈래: 지도 특징 헤드, 특권 특징 헤드(기존 결과 재사용 가능), 공식 STEVE-1.
- 개발 seed에서 먼저 하고, 통과하면 처음 쓰는 최종 seed로 한다.
- 성공은 서버 상태로만 판정한다.
- 판정에는 "성공 수가 공식 이상"을 반드시 넣는다.
  - 채굴은 공식이 이미 8/8이다. 그래서 헛손질·시간 조건도 같이 둔다(채굴 v3 판정과 같은 형태).
- 첫 대상은 채굴 v3다 **(내 결정, §11 D2)**.
  - "철 캐줘"에 넣을 때 필요하기 때문이다([최소 요구 능력](2026-11-15-minimum-capability-gaps.md) §4).

### P4 (선택) 헤드 재학습

- P3가 특징 오차로 무너지면 시행한다.
- 교사 라벨은 그대로 둔다. 헤드 입력만 지도 특징으로 바꿔 DAgger 한 라운드를 돈다.
- 판정은 P3와 같은 형태로 새로 정한다.
- 이 단계는 사용자 결정 후에만 한다(§11 D3).

## 7. 실시간 구성

- 인식과 지도 갱신은 별도 스레드에서 돈다. 구조는 빠른 감시 스레드(`pipeline/monitor_thread.py`)와 같은 형태다.
  - 제어 루프는 결정 때 마지막 지도를 읽는다.
  - 행마다 지도 나이(프레임 수)를 기록한다.
  - 지도 나이가 1결정을 넘으면 그 행의 특징을 "늦음"으로 표시한다.
- 행동 전 가드는 그대로 제어 스레드에 둔다.
- 인식 스레드는 세션이 소유한다.
  - STOP 뒤에는 새 정책 행동이 없어야 한다.
  - 스레드가 종료됐는지, 자식 PID가 정리됐는지 확인하고 기록한다(AGENTS.md).
- VRAM 예산:
  - 실행 중 STEVE-1 추론과 인식기의 합이 3GB 안이어야 한다. P1에서 잰다.
  - 넘으면 인식기를 CPU에서 낮은 빈도(2–4결정마다)로 돌린다. 그 사실과 지도 나이를 기록한다.

## 8. 다른 과제와의 연결 (이 설계의 범위 밖, 인터페이스만)

- **탐색:** 지도의 "모름" 칸이 탐색 목표가 된다. 교사(특권 대상 위치)로 학습하고, 평가는 지도만으로 한다.
- **"찾을 때까지" 감시:** 새로 알게 된 칸 수와 같은 칸 맴돌기가 진척 신호가 된다.
  - 지도는 이 신호를 계산할 함수(`known_cells`, `revisit_ratio`)를 노출한다.
- **vocabulary 등록:** P3를 통과한 헤드만 따로 통합 설계를 거쳐 등록한다. 이 설계는 vocabulary를 바꾸지 않는다.

## 11. 사용자 결정 사항

- **D1 자기 자세를 읽는 방법.**
  - (a) 클라이언트 자세 값을 직접 읽는다. F3 화면에 나오는 것과 같은 값이며, 화면에 F3를 띄우지 않는다. P0에서 OCR과 일치를 확인한다.
  - (b) 화면에 F3를 띄우고 OCR(`f3_bitmap.py`)한다. 정책이 보는 화면에 글자가 겹쳐 STEVE-1 입력이 바뀐다.
  - 제안은 (a)다.
- **D2 P3 첫 대상.** 제안은 채굴 v3이고, 그다음은 놓기·건축, 점프, 다리 순이다.
- **D3 P4(헤드 재학습) 허용 여부.**
- **D4 블록 분류 범위와 텍스처팩 확인 시점.** 기본 텍스처로 시작한다.
