# 센서 등급 복구 설계 — 2026-11-23

사용자 요청: "잘못 놓아도? 확인해보니 이상한데? 그러면 복구할 수 있는거지. … 잘못 놓은 블럭을 캐고, 제대로 다시 설치. … 블럭 개수도 딱 맞게 주는 게 좋을 것 같아."
이상감지 질문("어떻게 이상감지를 할거야?")에 대한 답과, 구조가 커져도 되는지("그때도 감지 가능하면 진행해")를 확인한 뒤 진행한다.

## 1. 이상감지 (감시, `build_sensor_repair.RepairMonitor`)

판단 입력은 본 지도(센서), 인벤토리(몸 센서), 설계도 지시뿐이다. 서버 기록은 판정과 감시 채점에만 쓴다.

| 규칙 | 조건 | 다음 행동 |
|---|---|---|
| `wrong_kind` | 설계도 칸에 다른 종류의 블록 (여러 재료 설계도) | 캐고 다시 놓기 |
| `must_be_empty` | 설계도가 `air`로 표시한 칸에 블록 | 캐서 회수 |
| `stray` | 설계도 밖, 공기로 잰 적 있는 칸에 받은 블록 | 캐서 회수 |
| `unaccounted` (장부) | 블록 종류마다 받은 수 − 손 > 본 우리 블록 + 줍는 중, 10프레임 연속 | 기록만 (행동 없음) |

- 같은 종류가 다른 설계도 칸에 들어간 것은 순서만 바뀐 채움이고 이상이 아니다.
- 근거(11-22·23 기록 85판, 설치 305번): 모든 설치가 누른 그 행에 본 지도에 나타났고, 누르기 직전 행에 그 칸은 공기로 재어져 있었으며, 종류도 서버 기록과 같았다. 서버 기록 없이 공기→블록이 된 칸 10개는 모두 판 끝 4행 안(서버 기록이 4행 늦어 판이 먼저 끝남)이었다.
- 구조 크기와 무관한 이유: 설치는 항상 십자선 광선 위(맞은 면 바로 앞 칸), 손 닿는 거리(4.5 이하) 안에 생기고, 센서 광선은 8블록까지 본다. 커지는 것은 감지가 아니라 복구(안쪽·높은 칸에 손이 닿는지)의 한계다.
- 한계: 블록 종류는 클라이언트 월드 값으로 읽는다(센서 설계 §2.6의 인식 완벽 가정). 화면 픽셀 인식이 아니다.
- 빛기둥 확인은 넣지 않았다. 철·금·다이아는 서로 바꿔도 신호기가 켜져서 바꿔치기를 못 잡는다.

## 2. 복구 (캐기 헤드, 카테고리 블록 × 공격)

- 대상: 감시가 낸 이상 칸 중 가장 가까운 것.
- 단계 `DIG_STAGES`: reach, move(건축 교사처럼, 블록의 면이 보이는 자리로), dig(면을 보고, 십자선 직선 광선이 블록을 칠 때만 공격; 한 번 치기 시작하면 블록 어디든 계속), collect(캔 칸이 공기가 되면, 떨어진 칸에서 가로 1칸 안의 바닥 칸으로 걸어가 그 블록 손 개수가 캘 때보다 1 늘 때까지; 비어 있는 설계도 칸에도 설 수 있음; 최대 100프레임, 넘으면 잃은 것으로 기록), done.
- 특징 `DIG_FEATURES`(11개): 건축 특징과 같은 계산(dig는 aim, collect는 move로 보여 줌), 이름만 `d_`.
- 도구 규칙(공개, `rule_select`): reach·move·dig에는 다이아 곡괭이, 건축 단계에는 현재 칸의 블록. 복구 과업에서는 클라이언트 손 아이템(누른 행에 바로 바뀜)을 읽고, 다른 아이템이 나오면 그 칸을 기억하고 다음 칸을 눌러 본다(주운 블록은 첫 빈 칸으로 들어가므로).
- 한계: 바닥에 선 채 줍는 범위는 약 1.4블록이다. 신호기 피라미드 가운데 칸 위·안에 떨어진 블록은 바깥에서 1.8블록이라 못 줍고, 받은 수가 딱 맞으므로 그 판은 끝낼 수 없다. 그대로 실패로 보고한다.

## 3. 두 헤드 (`head_switch.SwitchHead`)

- 건축 헤드 s-final(11-22, 그대로)과 캐기 헤드는 같은 공식 STEVE-1 행동 헤드 위의 서로 다른 잔차다.
- 세션 훅은 단계 목록 `COMBINED_STAGES`(건축 단계 + `dig_` + 캐기 단계)를 본다. 감시에 열린 이상이나 줍는 중인 블록이 있으면 캐기 헤드, 없으면 건축 헤드가 돈다. 전환은 타임라인에 `repair_monitor`의 `head` 사건으로 남는다.
- 지시 문구(임베딩)는 건축과 같다("build a small structure"). 한 단계 안에서 두 헤드가 같은 조건을 쓰기 때문이다.

## 4. 과업과 판정

- 캐기 학습 과업 `dig_task(id)`: 잘못된 블록 1 + id % 3개(신호기 재료), 앞 2–6칸·옆 −3..3, 서로 붙지 않음, 1/3은 돌벽돌 받침 위. 설계도는 그 칸들을 `air`로 둔다. 지급은 재료 1개씩과 곡괭이(5번 칸).
- 판정(`RepairJudge`, 서버 설치·파괴 기록과 서버 인벤토리):
  - 캐기 과업: `air` 칸이 모두 비고, 캔 블록이 모두 서버 인벤토리에 돌아옴.
  - 복구 시연: 10칸이 모두 각자의 블록, 설계도 밖 우리 블록 0개. 받침 같은 fixture 블록은 군더더기가 아니다.
- 모드(`configs/build-v1.json`): `dig_train` 1601–1612(학습 seed), `dig_dev` 1701–1704(331662, 처음 사용), `beacon_repair` 1801–1804(316227, 신호기 시연 seed, 어떤 헤드도 학습하지 않음). 제한 시간: 캐기 60초, 복구 시연 120초.

## 5. 학습과 판정 기준 (결과 전에 정함)

- 교사 점검(준비용) `dig_train` 12판, 관문 10/12.
- R0 공식 → d-r1 → R1 → d-r2 → R2 → d-final. 학습 설정은 센서 건축과 같다(kl 10, balance, patience 2, feature-gain 10, use-coef 1).
- 개발 판정: `dig_dev` 4과업 × sampling 1–2에서 d-final 성공 ≥ 5/8이고 같은 조건 공식보다 많아야 통과.
- 시연(판정 없음, 개발 결과와 함께 보고): 복구 교사 점검 1801–1804 다음, s-final + d-final로 `beacon_repair` 8판(sampling 1–2). 성공 수, 감시가 잡은 이상 수, 캐고 주운 수, 잃은 수를 그대로 보고한다.
