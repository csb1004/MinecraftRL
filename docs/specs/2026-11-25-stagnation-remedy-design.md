# 정체 감지 뒤 복구: 실행 피드백 → 해결책 → 남은 계획 수리 — 설계 (2026-11-25)

- 사용자 지시 (11-25): "정체 감지 이후 복구 같은 부분 저 논문을 많이많이 참고해서 고쳐줘." 참고: MineEvolve(arXiv 2603.13131v3, 2026-05).
- 같은 날 결정: 실제 센서 대응은 뺀다([센서 등급 설계](2026-11-19-sensor-tier-observation-design.md) 맨 위). 이 설계의 입력은 서버 인벤토리·자세 같은 게임 구조화 상태이고 감시·판정에만 쓴다. 정책 입력은 바꾸지 않는다.

## 1. 왜

- 11-24 점검 E3: 구덩이 탈출 두 번째 구간에서 정책이 4,026행 동안 앞으로+점프만 했다. 감시가 2,109행에 `repeated_cycle`을 냈지만 정체 신호는 기록만 해서 판이 시간 제한까지 갔다.
- 정책 단계에는 시도 창이 없다. 성공하거나 판이 끝날 때까지 돈다. 11-05 평가부터 시간 초과 8번이 모두 이 모양이다.
- `stationary_repetition`은 보류는 하지만 질의할 지식이 없어 느린 판단이 `stop`으로 끝난다.

## 2. MineEvolve와의 대응

| MineEvolve | 여기서 |
|---|---|
| Monitor: 하위 목표 실행마다 e = (z, y, Δs, Δv, f, p, ℓ) | 정책 단계 시도마다 `execution_feedback` 사건. 실행 중에는 감시 스레드가 창 단위 p로 정체(ℓ)를 낸다 |
| 식 (2) p = λx·Var(x)/(εx+Var(x)) + λv·‖Δv‖₁/(εv+‖Δv‖₁) + λg·p_goal | 같은 식. λ = 1/3씩, εx = 1 블록², εv = 1개. Var는 창 안 수평 위치 분산, Δv는 서버 인벤토리 L1 변화, p_goal은 목표 수량 증가(오르기는 높이 상승)가 있으면 1 |
| 식 (3) ℓ = 1[p < εp ∧ y = 0] | 창 W = 600틱(30초)이 찼을 때 p < 0.1이면 `stagnation` 보류 |
| 식 (5) 최근 h번 중 실패 비율 ≥ η 또는 ℓ = 1이면 해결책 | 같은 단계 최근 3번 시도 중 실패 2번 이상(η = 2/3), `stagnation`, `stationary_repetition` |
| Inducer: 해결책 = (trigger, failure type, risk pattern, repair action, scope) | LLM이 실행 가능한 어휘(§4)에서 수리 행동 하나를 고르고 trigger·risk pattern·이유를 낸다 |
| Curator 식 (6): schema ∧ match ∧ exec ∧ spec ∧ ¬conflict | 같은 다섯 검사(§5). 받은 것만 KB `remedy` 관계로 저장 |
| Curator: 신뢰도, 지지 수, 사용 기록, 검색 | 적용 결과를 게임 관측 지지·반박으로 붙인다. 신뢰도 (지지+1)/(지지+반박+2) |
| Adaptor 식 (8): 끝낸 앞부분은 두고 남은 계획만 수리 | 수리 행동을 앞에 넣고 멈춘 단계를 이어서(첫 시도 수량 유지) 다시 시도. `replan`이면 현재 인벤토리로 남은 계획을 다시 짠다 |

- 하지 않는 것: 성공에서 기술(skill)을 유도하는 쪽, 프롬프트 예산 B로 묶는 검색, 정책·헤드 학습. 이 논문도 저수준 정책은 학습하지 않는다.

## 3. 기준값의 근거 (지난 기록, 게임 0회)

- 대상: 11-05 평가 1–3d차, 개발 확인, 11-16 감시 스레드 점검, 11-24 점검의 정책 단계 시도. 창이 다 찬 시도만 센다.
- W = 600틱, εp = 0.1: 완료된 시도 25개 중 2개가 보류될 값까지 내려간다. 둘 다 오래 막혔다가 늦게 끝난 시도다(11-05 W2 오르기 815행, 11-24 W0b 철광석 7,921행).
- 같은 값에서 시간 초과 8번은 모두 시도 시작 뒤 607–957행에 잡힌다(실제로는 수천 행을 더 돌았다). E3 climb-2는 607행이다.
- W = 400틱이면 완료 33개 중 5개, εp = 0.2면 25개 중 4개가 걸린다. 그래서 600틱·0.1로 정했다.

## 4. 실행 가능한 수리 어휘 (Vexec)

| 행동 | 하는 일 | 실행 가능 조건 |
|---|---|---|
| `turn_away` | 180° 돌고 시선 수평(알린 규칙 행동, 11-05부터 있음) 뒤 같은 단계 다시 | 항상 |
| `level_view` | 시선만 수평으로 뒤 다시 | 항상 |
| `switch_skill` | 같은 목표의 다른 등록 기술로 다시(예: `mine_iron_text` ↔ `break_iron_text`) | 설정 기술 가운데 목표가 같은 다른 기술이 있을 때 |
| `equip` | 규칙 기술로 다른 물건을 손에 들고 다시(예: 오르기에서 판자 대신 흙) | 그 물건이 인벤토리에 있을 때 |
| `clear_above` | 머리 위 치우기 하위 목표를 끼운 뒤 남은 높이만큼 다시(11-04부터 있음) | 오르기 단계일 때 |
| `replan` | 현재 인벤토리로 남은 계획을 다시 짠다 | 플래너가 문제 없는 계획을 낼 때 |

- 그냥 다시 하기는 어휘에 없다(Vspec). 모든 수리는 기록에 남는다.

## 5. Curator 검사

- Vschema: 필드가 다 있고 행동이 어휘 안.
- Vmatch: trigger가 고정 상태 필드(실패 유형, 기술, 목표, 오르기 여부, 손 물건)로만 이루어진다.
- Vexec: §4의 조건을 지금 상태에서 만족한다.
- Vspec: 인자가 필요한 행동은 인자가 있고, 지금과 같은 것을 다시 하게 하지 않는다(같은 기술로 `switch_skill`, 이미 든 물건으로 `equip`은 거부).
- ¬Cconflict: 같은 trigger에서 반박된(`disputed`·`retracted`) 같은 행동은 거부.
- 저장: subject = `<실패 유형>:<기술>`, relation `remedy`, object = {action, arg, risk_pattern}, 조건 = 게임 버전. 근거는 `llm_assertion`. 같은 trigger에 이미 쓸 수 있는 해결책이 있으면 LLM을 부르지 않는다.

## 6. LLM이 없을 때와 예산

- `--allow-paid`가 없으면 KB의 해결책만 쓴다. 없으면 이번 보류에만 `turn_away`를 쓰고 저장하지 않는다(임시 해결책).
- 해결책 호출도 실행당 `budgets.llm_calls` 안에서 센다. 같은 (단계, 보류 종류) 상한 `step_retries`는 그대로다.

## 7. 상한

- 정체 보류(`stagnation`, `stationary_repetition`)는 창 하나(30초·20초)의 게임 시간이 지나야 다시 난다. 그래서 같은 단계 보류 상한(`step_retries`)으로 판을 끝내지 않고, 판의 시간 제한까지 계속 수리한다. 11-24 W0b처럼 오래 헤매다 끝내는 판을 일찍 끊지 않기 위해서다.
- `guard_violation_persistent`는 즉시 다시 날 수 있어서 상한을 그대로 둔다.
- `equip`은 오르기에서는 쌓을 수 있는 블록, 그 밖의 단계에서는 도구만 실행 가능으로 본다(맨손·틀린 도구 공격은 가드가 막는다).

## 8. 목표를 받을 때 지식 먼저 채우기

- 사용자 지적 (11-25): "이상감지가 일어나기 전에는 먼저 planning, 개선이 안일어나는 것 같은데? … 플래너가 정보가 부족해서 제대로 못하는거야?"
- 맞다. 첫 계획은 지식 저장소만 보고 만든다. 빈 저장소에서는 "철광석 캐기" 한 단계짜리 계획이 되고, 지식은 게임 안에서 가드가 맨손 공격을 막은 뒤에야 물었다(11-24 E1–E3: 첫 보류까지 403–2,742행을 썼다). E2는 첫 답에 원목 지식이 없어서 원목 앞에서 한 번 더 멈췄다.
- 바꾼 것 (`Oversight.plan_ahead`, `cli.plan_ahead_steps`): 게임을 시작하기 전에, 계획에 부족한 것을 이름으로 물어 채운다.
  - 부족한 것 = 플래너가 못 찾은 조리법·재료 + 계획이 부술 블록 가운데 채굴 조건을 모르는 것(가드가 멈출 자리).
  - 빈 저장소면 전체 사슬을 한 번 묻고, 그 뒤로는 부족한 이름만 묻는다. 최대 `knowledge_rounds`회, 실행당 LLM 예산 안에서 센다.
  - 채운 뒤 계획이 완전하면 그 계획으로 시작한다. 아직 부족하면 첫 계획을 그대로 두고, 예전처럼 가드가 마지막 순간에 묻는다.
  - 유료 승인(`--allow-paid`)이 없으면 묻지 않고 부족한 이름만 기록한다. 지식이 다 있으면 호출 0회다.
- 가드는 그대로다. 미리 받은 지식이 틀리면 게임 관측으로 반박하는 기존 경로가 처리한다.
- 하지 않은 것: 지지받은 해결책을 실패 전에 미리 적용하기(예: 처음부터 다른 기술로 시작). 한 번의 성공으로 기본 기술을 바꾸는 일이라 근거가 더 쌓인 뒤에 정한다.

## 9. 확인

- 단위 검사: 창 진척 계산과 정체 보류, 시도 피드백, Curator 다섯 검사, KB 검색·지지·반박, 수리 행동별 큐(첫 시도 수량 유지), LLM 없을 때 임시 해결책, 시작 전 계획(빈 저장소·부족한 고리·완전한 저장소·LLM 없음).
- 게임 점검: 11-24 점검과 같은 조건(개발 월드 130363)의 "철 캐줘" 판. 정책 평가가 아니다. 보는 것: 정체 보류가 난 곳, 고른 수리와 그 결과, 성공 판이 쓸데없이 끊기지 않는지.
