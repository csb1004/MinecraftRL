# U2: 단일 목표 계약 실제 실행과 병목 진단

2026-11-02 사용자 요청: 통합 구조를 실험하고 병목 및 개선안을 보고한다.
U1의 전달 일관성을 실제 게임에서 검사하며 새 학습이나 정책 승격은 하지 않는다.

## 실행 전 고정

- 동일한 기존 S2 `linear-on` checkpoint 하나를 두 입력 형식에 사용한다.
  `results/rm-general-s2-20261101/training/linear-on/checkpoint.pt`는 진단용 기존 후보이며
  공식 정책 또는 성능 개선이 입증된 정책으로 부르지 않는다. 공식 backbone과 후보 head 모두 고정한다.
- canonical `goal_spec_v1` 대 그 입력에서 결정론적으로 생성한 legacy `goal_queue_v1`.
  두 형식의 실행 프로그램은 같아야 한다. 문구, 임베딩, RM, 관측기, 행동 공간, 수량 특징은 고정한다.
- 개발 시드 81122001/81122003/81122007/81122009/81122013에 각각 원목1, 흙1, 원목3,
  원목1→흙1, 흙1→원목1을 배정한다. 같은 시드의 두 arm은 같은 정책 sampling seed를 사용한다.
  시작 순서는 legacy/canonical을 번갈아 배치한다. 5조건×2=10회, 최대 1200행동/180초 제어.
- 기존 S2는 저장 월드 복원이 없으므로 동일 시드로 월드를 재생성한다. 저장 월드 동일성을 주장하지 않는다.
  실제 시작 pose/인벤토리/tick/시각/PNG를 비교하고 차이가 있으면 인과 해석을 제한한다.
  이 실험을 위해 정책/관측기/월드 복원 구현을 변경하지 않는다.
- 기존 progress_limits(stall 600tick, recovery 300tick)를 사용한다. 유효 실패는 재시도하지 않는다.
  기술적 실패는 별도 보존하고 수정/재시도는 새 실행 ID와 부록으로 기록한다.
- 실제 STOP는 별도 1회, canonical 원목64를 사용해 10행동 후 요청한다. 성능 표본에서 제외한다.
  요청/ack 이후 새 dispatch 0, 입력 해제와 소유 자식 PID 정리, 최종 STOP 유지를 검사한다.

## 검사 및 진단

1. 실제 궤적의 목표 해시, 대상, 수량 특징/tensor, 임베딩 hash/key와 프로그램 원본을 검사한다.
2. 원시 서버 이벤트로 보상/완료/목표 전환, 완료 뒤 행동 없음, 인벤토리 증가를 독립 대조한다.
3. 획득량, 단계 체류, 실제 채굴/획득 구분, 정체/사망/시간초과를 기록한다.
4. 추론 및 전체 제어 주기 중앙값/p95, GPU 사용량, 시작 상태 차이를 보고한다.
5. 동일한 저장된 시각·recurrent 특징에서 수량/단계/추가 RM context만 바꿔 행동 분포 변화를
   측정한다. CPU 오프라인 반사실 검사이며 새 게임 성과나 원시 encoder의 인과 검사로 세지 않는다.
   수량1→3은 진행량0 표본에서 비교하고 완료 상태에 행동을 요구하지 않는다.

코드/설정/후보/공식 파일의 해시와 실행 소스를 동결한다. 원본 자료는 보존한다.
외부 LLM/API, 추가 가중치 학습, 유료 자원, GitHub 게시 0.
형식 통일 자체로 성능이 향상될 것이라고 가정하지 않는다. 검증된 전달과 실제 조건 활용/운동 능력을 분리한다.
결과에 근거한 일반적인 개선안을 후속으로 제시하고 임의의 추가 튜닝 배치를 이어가지 않는다.
