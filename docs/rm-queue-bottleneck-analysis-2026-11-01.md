# 현재 RM → RL 병목 진단 — 2026-11-01

사용자 요청: 현재 병목과 문제 원인 분석. 기존 P4 자료와 실제 실행 소스를 대조했다.
새 게임, 추가 학습, 유료 API, GitHub 게시를 실행하지 않았다. STOP을 유지한다.
원본 실험·체크포인트는 수정하지 않았으며 아래 숫자는 개발 실험의 진단 결과다.

## 판단

가장 큰 병목은 **RM 단계 정보가 행동 정책을 충분히 바꾸지 못하는 구조와 부족한 학습 경험**이다.
우선순위 큐의 목표 전환은 실제 게임에서 동작했지만, 그것이 접근·채굴·회수 능력을 학습시켜 주지는 않는다.
학습 후보의 전체 프로그램 완료는 초기 5/5 대비 4/5였고 후보는 미승격 상태다.
작은 표본과 초기 화면 차이 때문에 이를 일반적인 성능 하락의 인과 증명으로 해석하지 않는다.

## 1. RM 단계가 정책에 들어가지만 영향이 매우 작다 — 확인

`s1_learning.py`에서 이미지·목표 임베딩을 처리하는 pretrained recurrent backbone은 동결되어 있다.
그 출력 뒤에 단계 one-hot 4개, 획득 비율, 미회수 결과 여부를 붙여 actor/value head에 전달한다.
actor head는 선형 계층이므로 추가 RM 입력의 직접 효과는 단계별 logit 편향이다.
같은 화면 특징을 단계에 따라 다르게 가공하는 학습 경로나 RM 입력에 따른 recurrent state 갱신은 없다.
전체 actor head의 기존 특징 가중치도 업데이트하므로, 단계 열만 학습한 실험은 아니다.

실제 학습 특징 9개에서 화면/목표/RNN 특징을 고정하고 단계만 바꾼 반사실 검사:
초기 head의 분포 차이 0, 후보의 buttons/camera 주변분포 total variation 최댓값 약 **0.00001954**.
이는 해당 표본에서 직접적인 단계 활용이 매우 약하다는 증거이며, 실환경 행동 차이 또는 일반화 검사는 아니다.
또한 wood의 approach/mine/collect는 같은 root 목표 임베딩을 사용한다. search만 seek 임베딩으로 바뀐다.

따라서 'RM 단계를 만들었으니 정책도 각 단계를 수행한다'는 연결이 아직 성립하지 않는다.
CNN이나 MineCLIP 자체가 잘못 학습됐다는 결론은 이 결과에서 나오지 않는다.

검증할 개선 후보: 동결 특징과 RM 상태를 함께 처리하는 작은 비선형 조건부 계층 또는
정책 일부의 조건부 미세조정을 같은 예산으로 비교한다. 기존 head-only와 단계 입력 제거 조건도
유지하여 전체 head 갱신 효과와 RM 정보 활용 효과를 분리한다. 조건별 목표 문구까지 동시에 바꾸지 않는다.
목표는 단계 변경에 무조건 큰 행동 변화를 만드는 것이 아니라, 관측에 맞는 선택과 과업 성능을 개선하는 것이다.

## 2. 학습량·단계 분포·보상 신호가 충분하지 않다 — 확인

전체 19회는 진단 5회 + 학습 수집 4회 + 개발 비교 10회다. 실제 학습은 **4회·451행동·15 minibatch update**다.
4회 모두 단일 목표 성공이며 실패·복구 궤적이 없다. 단계별 자료는 search 49, approach 4, mine 135, collect 263이다.
다만 collect 263 중 **217은 dirt의 전체 과업을 collect로 표시한 것**이고 실제 wood 회수 구간은 **46행동**이다.
wood 학습은 두 번뿐이다. 모든 학습 목표 수량이 1이라 획득 비율 입력은 학습 내내 0이었다.
이 자료로 일반적인 접근·회수·여러 개 수집·실패 탈출을 배웠다고 할 수 없다.

현재 gamma=0.999, GAE lambda=1이고 초기 value는 0이다. 종단 보상 1의 첫 행동 return은
각 실행에서 약 **0.869~0.912**다. 보상이 이전 행동까지 전달되지 않는 상태는 아니다.
반면 초기 value가 상태별 기대 성공을 구분하지 못하고 모두 성공한 짧은 자료만 있어,
advantage가 사실상 '보상까지 남은 길이'에 크게 좌우된다. 전체 배치 정규화 후 search 49개와
approach 4개 advantage가 모두 음수였다. 이것은 그 행동이 틀렸다는 뜻도, 정규화 구현 오류라는 뜻도 아니다.
초기 업데이트가 필요한 준비 행동의 가치를 구분하기 어렵다는 진단 근거다.
KL 조기 종료는 발생하지 않았다. 큰 gamma나 더 강한 보상만으로 해결된다고 볼 근거는 없다.

검증할 개선 후보: 여러 학습 월드에서 접근·연속 상호작용·회수·실패 후 재접근·수량 변화의 경험을 확보한다.
개발 실패 시드를 학습으로 편입하면 별도 평가 시드를 사용한다. value 예측과 단계별 advantage를 점검하며
반복 수집/업데이트하고, 학습 완료 여부를 가중치 변경이 아니라 분리된 개발 성능으로 판단한다.

## 3. 실제 채굴 연속성과 회수 능력이 부족하다 — 증상 확인, 세부 원인은 미확정

개발 seed 81033013 비교:

| 항목 | 초기 정책 | 후보 정책 |
|---|---:|---:|
| 행동 수 | 1,121 | 1,212 |
| 실제 서버 원목 파괴 | 4 | 0 |
| 동일 대상의 연속 서버 채굴 상태 구간 수 | 49 | 138 |
| 최장 구간 | 66tick | 55tick |
| 프로그램 완료 | 완료 | 시간 제한 |

후보는 attack 990행동, mine 단계 1,091행동이었지만 원목 획득도 0이었다.
즉 공격 횟수나 mine 라벨을 성공 대용 지표로 쓸 수 없다.
최장 55tick 구간이 끝난 다음 관측에서는 오른쪽 이동이, 49tick 구간 끝에서는 attack 해제가 있었다.
다른 종료 구간에는 해당 행동에서 공격을 유지했어도 채굴 flag가 사라진 사례가 있다.
행동과 서버 관측의 지연이 있을 수 있으므로 이 상관만으로 모든 중단 원인을 분류하지 않는다.

실제 로컬 Minecraft 소스에서 공격 중단은 client 채굴 진행 초기화 경로를 가지며,
server 채굴 flag는 진행 중 채굴 외에 지연 완료 처리를 포함한다.
따라서 **55tick이라는 숫자만으로 필요한 채굴 시간을 못 채웠다고 확정할 수 없다**.
client block damage, START/ABORT/FINISH packet, 대상 일치의 시간 정렬 기록이 없으므로
정책의 시선/공격 유지 문제와 개별 채굴 처리 문제를 완전히 분리하는 근거는 아직 부족하다.

별도 진단 81031013은 실제 파괴 1회 뒤 원목을 줍지 못하고 result_not_acquired로 차단됐다.
collect 단계 298행동 중 attack 276, forward 22였다. 미완료 회수 상태를 기억하는 수정은 동작했지만,
회수 상태를 유지하는 것과 실제 회수 행동을 잘 수행하는 것은 별개의 문제다.

검증할 개선 후보: 고정 평가 관측기를 바꾸지 않고 기존 로그에서 시선·공격·이동·대상 지속을 먼저 대조한다.
패킷/채굴 진행 기록이 꼭 필요하면 별도 버전의 진단 계측으로 분리하고, 정책 입력이나 기존 성능 조건에
소급 적용하지 않는다. 특정 좌표에 대한 scripted 해결 대신 여러 배치의 연속 상호작용/회수 능력을 평가한다.

## 4. 정체 감지가 실험 한도와 맞지 않고, LLM 복구는 아직 실행 경로가 없다 — 확인

학습·개발의 stall/recovery 한도는 각각 **3,600 server tick**이다.
후보 실패는 180.0756초에 1,212행동, 마지막 진전 이후 1,123tick이었다.
따라서 이 실행에서는 정체 한도에 도달하기 전에 전체 제어 시간 제한으로 끝났다.
진단 조건은 더 짧은 별도 한도를 사용해 정체/미회수를 실제 차단했다. 모든 모드가 같은 설정은 아니다.

이 새 queue 경로에서 `learning-request.json`은 차단 근거를 저장하는 기록이며
`executed=false`, `API_calls=0`이다. 자동 LLM 대안 생성·검증·추가 학습·후보 채택은 구현된 것으로 볼 수 없다.

검증할 개선 후보: 실제 server tick과 wall time의 역할을 명시하고, 실행 한도 안에 정체를 발견할 수 있는
판정 지연을 검증한다. 정상 장시간 채굴을 정체로 오판하지 않는 대조 조건도 필요하다.
이후에야 감지 → LLM 제안 → 지원 가능한 RM/학습 요청 검증 → 분리 학습 → 평가 후 승격을 연결한다.

## 5. 실행 속도와 비교 통제가 개선 효과 판별을 제한한다 — 확인

개발 조건의 추론 중앙값은 실행별 약 46~52ms지만 전체 제어 주기는 약 133~158ms다.
환경 step과 매 행동 PNG 기록도 비용이므로 GPU 추론만의 병목은 아니다.
이번 실패 1,212tick은 게임 명목 시간 약 60.6초이며 wall control 약 180초와 다르다.
학습 예산·정체 한도를 wall 초만으로 비교하면 실제 경험량 차이가 섞인다.

19회·8,660행동의 인접 관측을 재검사했다. **모든 행동에서 client/server tick이 각각 1씩 증가했고,
server-client offset은 2tick으로 일정**했다. 이번 실패를 누적 tick drift로 설명할 근거는 없다.
다만 이 일치가 개별 패킷 처리나 client 화면 예측까지 정상임을 보증하지는 않는다.

개발 다섯 쌍의 초기 pose/world time/server tick은 같았지만 초기 pixel까지 같은 쌍은 1/5였다.
5시드·각 1회로 후보 실패의 원인을 가중치 업데이트 하나로 확정할 수 없다.
이번 head 학습/추론에서는 OOM이 관측되지 않았다. 전체 backbone 학습 자원은 아직 별도 문제다.

검증할 개선 후보: 시작 월드·관측·샘플링 조건과 실제 행동 예산을 고정하고 반복 개발 평가를 구성한다.
학습 기록 저장 비용은 측정 후 비동기화/주기 조정을 비교하되, 평가/실패 분석에 필요한 기록은 보존한다.

## 우선순위와 남은 범위

1. 채굴 중단과 미회수를 공통 실패 유형으로 진단하고 판정 지연/실행 예산을 정렬한다.
2. 충분하고 균형 잡힌 공통 스킬 학습 자료와 RM 조건 활용 대조군을 마련한다.
3. 동결 기반 모델 유지하에 최소한의 조건부 학습 범위를 비교하고 별도 개발 시드로 채택 여부를 결정한다.
4. 이 기반 위에 LLM의 RM 작성·추가 학습 요청과 후보 평가 절차를 연결한다.

목표 큐의 wood→dirt 전환은 검증됐다. wood→stone은 wood 완료 후 미지원으로 차단한다.
현재 queue 경로의 제작/도구/돌 executor가 검증된 것으로 간주하지 않는다.
LLM이 더 좋은 RM을 작성해도 그 내용을 수행할 정책의 능력과 학습 경험은 따로 확보해야 한다.
