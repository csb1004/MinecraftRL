# LLM 계획과 기존 RM 실행 연결

사용자 승인: “그래 이걸 하고 저게 되는지 보자”. 앞선 두 선택지 복구는 전체 상위
플래너 구현이 아니었다. 이번 단위는 기존 목표/진척을 보존하면서 계획 그래프를 실제
정책 조건 선택에 연결하고, 실패 기록을 다음 계획 입력에 전달하는 것이다.
연구 명세 원문, 기본 정책, 최종 평가 시드, 유료 사용 범위는 바꾸지 않는다.

## 계약과 구현 순서

1. 제안은 요청/근거/스케줄 버전에 연결한 최대 8개 하위 목표 DAG다. 각 노드는 목적,
   우선순위, 선행 노드, skill, 진입/완료 조건, 시간/틱 한도, 실패 후 처리 방식을 담는다.
   `root` 노드는 기존 원목+1 RM의 고정 참조다. 보상/완료 조건 변경은 허용하지 않는다.
2. 미지원 skill도 가설로 제안·보존할 수 있다. 지원 판정은 로컬 registry가 한다.
   미지원 노드는 행동으로 번역하지 않으며 해당 선행 조건을 완료 처리하지 않는다.
   현재 실행기는 원목 수집과 한정된 탐색 조건만 지원한다. 우회 방향/벽 끝 찾기를
   구현된 skill로 위장하거나 임의 문장을 탐색 embedding으로 바꾸지 않는다.
3. 스케줄러는 의존 관계가 충족된 노드의 우선순위를 비교한다. 원래 RM 객체와 완료
   evidence는 계속 유지하며, 임시 목표 동안 원래 실행 우선순위만 낮춘다. 탐색에서
   새 목표 획득/상호작용 증거가 생겨도 원목 획득 완료와 구분한다.
4. 실제 controller의 계획 대기/neutral/재검토 경로를 재사용한다. 하위 정책이 행동을
   생성하며 planner는 키 입력을 만들지 않는다. 전이에 계획/노드/스케줄 버전을 기록하고
   실제 선택 embedding을 policy에 전달한다. 동적 계획 실행은 eval 전용이다.
5. 실행 결과와 실패를 보존해 후속 요청에 전달한다. 같은 관측/방법의 반복은 기존 전체
   이력 guard가 차단한다. 새 제안 문구/노드 ID/우선순위로 중복 검사를 우회하지 못한다.
   한 에피소드의 계획 요청은 최대 3회, 전체 제어는 최대 180초다. STOP/취소/수동 pause,
   목표 버전 변경, 완료, 불명확한 관측은 자동 재개하지 않는다.
6. 기존 두 선택지 프로토콜과 그 결과는 보존한다. 새 계획 프로토콜은 별도 opt-in 경로다.

## 검증

- DAG/우선순위/미지원 단계/중복/시간 한도, 실제 RM 진척 보존과 완료 우선,
  입력 해제/STOP/늦은 응답, 실패 뒤 다음 요청을 로컬 계약 및 controller 검사로 확인한다.
- 실제 보존 궤적에서 새 계획 입력과 실행 가능/불가 판정을 재생한다. 재생은 새 게임이나
  실제 LLM 응답으로 계산하지 않는다.
- 변경 코드 Windows/WSL 회귀 검사 후 개발 월드에서 고정 계획의 실제 신경망 실행을
  확인한다. 원목 획득과 부분 진전을 분리하고 GPU/지연/주기/중단/자식 종료를 기록한다.
- 유료 API 잔여 승인 0. 실제 LLM의 대안 생성 검사는 실행 가능한 payload와 검증 결과를
  준비한 다음 별도 승인 대상으로 제시한다. 고정 응답을 LLM 추론 결과로 부르지 않는다.

후속 승인/실행: 사용자 `API 1회 검사 승인`에 따라 과거 실패 입력의 제안 생성1회를
실행했다. 상세 결과와 식별자 검증 수정은 [검증 기록](rm-planner-validation-2026-10-10.md)을 따른다.
아카이브 제안은 live 설치/행동을 허가하지 않는다. 승인 잔여0회이며 추가 호출은 하지 않는다.

대화 TaskState의 여러 사용자 과업을 동시에 실행하는 범용 장기 스케줄러까지 완료했다고
주장하지 않는다. 이번 스케줄러는 실제 RL 에피소드의 기존 root RM과 임시 하위 계획에 연결한다.
