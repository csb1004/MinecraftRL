# E1 — 공통 결과 스킬과 RM→RL 연결

상태: 원래 배치/학습/전체 감사/실제 STOP 및 자원 간섭 보충 한 쌍 완료. 후보 승격 없음.
원문 연구 명세와 4단계 로드맵은 유지한다.
[명세](specs/2026-11-02-effect-skill-e1.md), [사용법](effect-skill-e1-usage.md).

## 구현한 구조

`상위 목표 계약 → 다음 실제 결과 요청 → 조건부 정책 → 확정 결과 → 독립 RL 학습`으로 연결했다.
추가 예측 모델을 만들지 않았고, 특정 나무 좌표나 키 입력 순서를 해결책으로 넣지 않았다.

상위 큐는 최종 수량·우선순위·의존성·완료 판정을 계속 소유한다. 하위 스킬은 목표 ID/개정/
해시·대상·기준 인벤토리·다음 획득 최고치를 공유한다. 실제 인벤토리가 이전 최고치를 넘어야
성공하고, 한 행동에서 여러 개를 얻으면 한 번만 보상한다. 소모/버리기 뒤 같은 수량 재획득에는
새 보상을 주지 않는다. 현재 구현된 효과는 원목/흙의 인벤토리 증가이며 다른 과업 실행 능력을
추가한 것은 아니다.

요청의 필요 증가량·확인된 진전은 실제 actor/critic 입력에 연결된다. 목표 임베딩은 기존
검증된 바인딩을 유지하며 매 스킬 완료마다 무조건 교체하지 않는다. PPO는 스킬 성공에서
GAE를 끊고, 미완료 제한 종료에는 저장한 다음 상태의 가치로 bootstrap한다. 원래 목표 보상과
별도 스킬 보상을 함께 보존한다. `skill-events.jsonl`은 실제 dispatch 이후 시작·확정 결과·
종료를 남긴다. 향후 LLM/모니터/SQL은 이 계약과 결과를 사용할 수 있지만 아직 연결한 것은 아니다.

기존 R1 residual actor 형태를 재사용하고 공식 backbone/motor를 고정했다. FiLM 등 새 actor까지
동시에 바꾸면 원인 분리가 어려워 이번에는 추가하지 않았다. 별도 E1 scope/checkpoint와
명시적 실행 옵션을 사용하며, 기존 R1/S2/default 경로는 유지한다.

## 실제 학습과 원래 개발 비교

새 train 실행 4회, **1,417행동**, 상위 완료 보상 4회/하위 획득 성공 8회로 PPO 90회 업데이트.
행동 확률·critic 재현 최대 오차 0, 공식 motor 보존, adapter delta L2 0.5529945.
실제 optimizer 시간 11.63초, 학습 peak CUDA 약 195.82MiB. 이는 frozen feature/head 학습의 수치다.
공식 전체 모델의 end-to-end 학습 비용으로 해석하지 않는다.

후보 SHA256: `00bf9d965ee0177e32aa301b7b64d3fbefa739fcf7b632e3aa0a502c1dbb0f92`.

원래 관측 완료 횟수는 초기 **4/5**, 후보 **3/5**다. 후보의 시간 제한 1회는 사용자가 잠깐
다른 게임을 실행했다고 확인한 조건이며, 순수한 정책 차이로 해석하지 않는다. 원본을 보존하고
같은 초기/후보 한 쌍만 별도 폴더에서 추가 확인한다. 성공한 재시도로 원래 표를 교체하지 않는다.

기존 개발 월드를 재사용한 소규모 탐색 실험이다. 초기 대 학습 후보 비교이므로 새로운
스킬 보상 자체의 효과만을 분리한 실험도 아니다. **이 가중치는 승격하지 않는다.**

## 확인한 병목

1. **부분 성과의 학습 연결은 개선했다.** 실제 원목3 수집에서 원래 목표 보상 1회와 별도로
   획득 스킬 3회가 기록된다. 이전 U2의 2개 획득 후 실패한 1,110행동을 오프라인 재계산해도
   전체 실패/보상 0은 유지하면서 획득 2회만 식별했다. 이 재생 자료는 학습에 사용하지 않았다.
2. **접근·회수 행동의 일반화는 미해결이다.** 후보의 마지막 실패는 접근 단계 679행동,
   채굴 단계 58행동, 실제 파괴 0이었다. 원목→흙 후보는 실제 첫 원목 회수까지 추가 채굴이
   이어져 4회 파괴 후 여러 원목을 함께 획득했다. 완료 뒤 더 행동한 문제가 아니다.
3. **한정된 학습 분포의 대가가 있다.** train은 자연 시작 1개 시드와 단순 회수 배치 2개다.
   수량3은 좋아졌지만 다른 시작 조건의 접근은 퇴행했다. 원인별 기여를 분리하기 전까지
   CNN/MineCLIP 결함이나 새 스킬 계약의 우월성을 단정할 수 없다.
4. **원래 흙→원목 후보의 제한 종료에는 실행 자원 간섭이 있다.** 추론 45.32초/20.56초
   지연과 GPU sampler timeout, 장치 메모리 peak 2945MiB가 기록됐다. 사용자의 동시 게임 실행
   확인을 보존한다. 다음 원목 실패는 추론 중앙값 57.74ms/p95 68.08ms로 이 현상과 구분된다.

## 일시적 외부 게임 부하 이후 보충 확인

새로 고정한 한 쌍만 추가했고 원래 결과를 대체하지 않았다. 같은 checkpoint/월드/시드,
추가 학습 0. 보충 두 실행의 시작 pose·PNG·실제 특징은 모두 정확히 같았다.

|보충 흙1→원목1|결과|행동|추론 중앙값/p95|최대 추론|
|---|---|---:|---|---|
|초기 정책|두 목표 완료|473|58.25/69.58ms|1,992.69ms (1초 초과 1회)|
|후보|첫 흙 목표 정체, 원목 미실행|600|57.46/67.80ms|245.58ms|

후보는 **흙 대신 원목 2개를 획득**했다. 서버 인벤토리와 올바른 흙 목표 임베딩/요청/tensor
바인딩을 대조해 확인했다. 원목 획득을 현재 흙 목표나 아직 활성화하지 않은 다음 목표의
성공으로 계산하지 않았다. 후보에서는 GPU sampler 오류와 수십 초 지연이 없었다.
따라서 원래의 일시적 실행 간섭은 별도 문제이며, **추가 학습 후 목표 준수/기존 능력 보존 실패는
여전히 남는다.** 관측/문자열/보상 배선이 맞다는 사실이 정책의 의미 이해·일반화를 보장하지 않는다.

초기 정책도 원래 262행동에서 보충 473행동으로 바뀌었고, 원래 초기 실행과 보충 초기 실행의
첫 PNG는 달랐다. 렌더링·확률적 정책의 실행 변동을 감안해야 한다. 보충 성공/실패를 원래 표에
소급 대입하거나 유리한 실행만 선택해 성능 수치로 제시하지 않는다.

## 다음 실험의 기준

스킬 계약을 유지하고 서로 다른 접근·회수·재료 보유 실패를 포함한 **train 전용** 분포를 늘린다.
동일 초기 정책/자료/입력/업데이트 예산에서 원래 최종 보상만 쓰는 대조군을 두어 credit 변경의
효과를 분리한다. 별도 조건 입력 ablation과 같은 시작 상태의 상반된 목표 시험으로 실제 정책이
RM 조건을 쓰는지도 평가한다. 이번 train은 1,417행동 중 자연 원목3 996행동으로 편중돼 있다.
목표/스킬별 균형과 기존 공식 정책 능력 보존을 독립 기준으로 검사해야 한다. 이 편중이 퇴행의
유일한 원인이라고 확정한 것은 아니다.
잠근 미사용 평가 월드와 기존 능력 보존 검사를 통과하기 전에는 기본 정책으로 채택하지 않는다.
조건별 예외 조작이나 개발 실패를 곧바로 학습에 넣어 성공률을 맞추는 방식으로 진행하지 않는다.

LLM이 새 목표를 작성하는 단계는 기존 `goal_spec_v1` 검증을 사용한다. 이상 감지/학습 요청은
같은 요청과 확정 결과를 참조하고, 이후 지식 저장소는 증거·버전·반례를 보존하는 구조로 연결한다.
새 과업은 고정 관측으로 판정 가능한 결과와 실제 지원 정책이 함께 등록되어야 한다.

## 검증 및 자료

관련 WSL 회귀 **79개 통과**. 실제 14회 **5,907행동**의 서버 로그/인벤토리/스킬 보상,
실제 입력 tensor와 목표 바인딩 불일치 0. 시작 pose 5/5 동일, 첫 PNG/특징은 3/5 정확히 동일했다.
나머지 두 조건의 변경 픽셀 비율은 각각 약 0.194%, 0.199%였다. 렌더링 재현의 한계도 보존한다.
별도 실제 STOP은 10행동 뒤 요청 시작/확인 이후 새 dispatch 0, 입력 해제 확인,
held keys 0, 잔존 소유 PID 0. 요청 파일 fsync 완료 시각보다 ack가 먼저여서 `visible` 기준
지연이 음수로 기록됐다. 이를 음의 지연으로 해석하지 않고 요청 시작→ack 상한 약 2.1ms와
실제 행동 기록을 사용한다. 단일 검사로 실시간 성능을 보장하지 않는다.

원래 배치 벽시계 약 76.66분 중 실제 제어 합은 18.88분이었다. 실행별 추론 중앙값 범위
50.02–64.79ms, p95 61.84–347.49ms; 제어 주기 중앙값 135.61–199.81ms,
p95 173.93–611.50ms. 자원 간섭 조건의 수십 초 추론 outlier는 p95만으로 드러나지 않는다.
설정 제한은 180초이며 간섭 실행은 이미 진행 중이던 추론을 마친 뒤 181.16초에 제어를 종료했고,
해당 마지막 추론 결과는 dispatch하지 않았다(추론 309회, 실제 행동 308회).
원본 서버 이벤트 약 1.199GiB, PyTorch peak 약 1915MiB(모델 로드 포함), 장치 전체 peak 2945MiB.
01:18 KST에 원래 배치를 종료했고 01:22에 소스/입력/공식 파일·snapshot·결과 해시를 재검증했다.

보충 2회 **1,073행동**도 원본 서버·스킬 결과·실제 tensor 불일치 0.
합계 **16회·6,980행동**이며 별도 STOP 진단 10행동은 성능 표본에서 제외한다.
보충 완료 후 01:36 KST에 원래 결과 해시·소스·입력·공식 파일이 그대로임을 다시 확인했다.
모든 실행의 입력 해제·소유 PID 정리 확인, 게임/학습 종료, STOP 유지.
코드 검토는 프로젝트 지침에 따라 주 실행 흐름에서 수행했으며 독립 제2 검토자는 사용하지 않았다.
