# 순차 수집 RM 묶음 — 구현 및 종합 검증

추천안 A(기존 정책으로 다단계 과업 구현) 및 묶음 전체 추가 API 최대 30회 승인에
따라 구현과 검증을 연속 진행했다. 결과는 **제한된 순차 수집 과업의 통합 통과**다.
일반 그래프 RM, 제작·이동·귀환, 인간다움 및 장기 연구 전체의 완료를 뜻하지 않는다.

## 구현

- 1–8개 wood/dirt 수집 단계의 검증, 실제 인벤토리 기반 단계 전환, 완료 이력.
- 현재 단계 수정 및 남은 순서 교체, 전체 과업 pause/resume/cancel.
- 단계 전환 때 revision 증가, 입력 해제, 정책 조건 reset. 이전 확인/명령 차단.
- schema 2 계획 체크포인트와 기존 schema 1 읽기 호환, paused 복원.
- LLM 계획 제안·별도 확인, 단계 배열의 순서/수량 검증, 비계획 응답의 stages 거부.
- PowerShell 직접 계획 명령과 한 번에 실행하는 종합 검증 진입점.

사용법과 정확한 baseline 의미는 [sequence-rm.md](sequence-rm.md)를 따른다.

## 로컬 검사

기능 추가 전 실패하는 검사를 작성하고 구현했다. 계획 단계 순서가 달라도 기존
평가기의 세 scalar 필드만 같으면 일치로 처리되는 문제도 실패 검사로 재현해 수정했다.

- Windows 89개 중 85개 통과, Linux 전용 4개 제외(1.534초).
- WSL 89개 통과(31.687초).
- 마지막 프롬프트 문구 정리 뒤 의미 어댑터 관련 24개 추가 통과(0.468초).
- PowerShell 두 스크립트 구문 검사 및 실제 파일 발행을 통한 2단계 JSON 확인.
- 단일 과업, 저장, STOP, 대화 기억 등 기존 회귀 포함.

## 실제 API

gpt-5.3-codex를 총 **10회** 호출했다. 한도 30회 중 20회는 사용하지 않았다.
이번 묶음 이전 27회를 포함한 프로젝트 누적 호출은 37회다. 재시도 없음.
입력 10,549 / 출력 370 = 10,919 tokens. 개인 기억은 읽거나 전송하지 않았다.

첫 5회: 나무→흙 순서, 역순, 미래 제안, 수량 없는 순서, 미지원 제작이 섞인
순서를 검사했고 모두 기대된 구조를 반환했다. 다음 3회는 실제 게임의 순서 요청,
활성 흙 단계 수정, 복원 후 재개에 사용했다.

최종 자체 검토에서 프롬프트 첫 문장의 오래된 "세 필드만 반환" 안내가 새 네 필드
스키마/후반 지침과 상충함을 발견해 문구를 정리했다. 실제 오류는 발생하지 않았지만
일관성을 위해 수정하고, 새 계획 및 남은 계획 교체를 2회 더 호출해 확인했다.
남은 계획 교체의 완료 이력 유지는 로컬 상태 적용으로 검사했다. 이 기능의 별도
실게임 실행을 주장하지 않는다. 모터 제어 코드는 이 문구 수정으로 바뀌지 않았다.

실게임에 사용한 프롬프트 SHA256:
4fd1edcfeab099df8658bfa55f93fb0ac6f37813a5b73af02fbce6178e05566b.
최종 문구 및 추가 2회 SHA256:
8ff98f7b3251c0d5643cd8a4be8ffa99a88bb63e674a2519298802bbc5c6ed5f.
최종 문구로 전체 게임을 다시 실행하지는 않았다.

## 실제 게임 통합

실험 폴더: results/sequence-acceptance-20261004T025836469371Z.
Windows/WSL의 기존 STEVE-1 환경, GTX 1060 3GB, seed 130363, 실행별 제어 한도 180초.
검증용 저장 슬롯은 sequence-20261004T025836469371Z 및 별도 취소 슬롯이다.

| 구간 | 결과 | 정책 step | 제어 / 종료 처리(초) |
|---|---|---:|---:|
| 0: 순서 수행·수정·저장 | 원목 1개 완료 → 흙 1개 획득 → pause → 흙 목표를 추가 2개로 수정 → 저장 | 471 | 67.247 / 4.926 |
| 1: 복원·남은 단계 완료 | 원목 완료를 유지, 흙 1개 복원 → 새 resume 확인 → 흙 총 3개, 전체 과업 completed | 150 | 25.348 / 4.421 |
| 2: 별도 취소 | 첫 추론 결과 폐기, 정책 dispatch 전 취소, 다음 단계 미진입 | 0 | 3.396 / 4.471 |

첫 구간의 최초 계획은 원목 1개→흙 64개였다. 목표 변경을 시험하기 위해 흙을 1개
얻은 뒤 수정 시점 baseline=1, target_count=2로 바꿨다. 따라서 최종 흙 3개 중
수정 이후 순증가 2개로 변경된 과업을 완료했다. 원래의 흙 64개 목표를 완료했다고
계산하지 않는다.

| 측정 | 구간 0 | 구간 1 |
|---|---:|---:|
| 추론 중앙값 / p95(ms) | 42.797 / 52.506 | 41.620 / 48.519 |
| 제어 주기 중앙값 / p95(ms) | 127.202 / 148.635 | 126.656 / 151.498 |
| PyTorch allocated / reserved peak(MiB) | 2098.717 / 2144 | 2098.670 / 2144 |
| 전체 GPU 관측 peak(MiB) | 2835 | 2795 |

취소 구간 GPU 전체 peak는 2794 MiB이며 정상 수집 성능 표본으로 넣지 않는다.
복원 관측에서 oak_log=1, dirt=1이 일치했고 위치 차이는 1.029805블록으로 기존
허용 범위 2블록 이내였다. 좌표가 완전히 같았다는 뜻은 아니다.

전체 이벤트를 사후 재검사했다.

- 원목 완료 뒤 입력 해제, 그 뒤 흙 정책 dispatch 순서를 확인했다.
- 첫 pause 이후 정책 dispatch 0회.
- 복원 후 새 resume 전 약 2.939초 동안 정책 dispatch 0회. 원목 단계 반복 0회.
- 별도 취소에서 추론 결과 1개 폐기, 취소 acknowledgment 이후 dispatch 0회.
- 세 구간 모두 STOP acknowledgment 이후 dispatch 0회, neutral_command_sent,
  정상 월드 저장, 소유 자식 잔존 0개.
- 별도 전체 프로젝트 프로세스 조회에서도 Python/Java 잔존 0개. STOP 다시 잠금.

구간 0과 2의 cancelled/invalid 원본 상태는 의도된 중단 결과로 보존한다.
구간 1은 실제 task_completed다. 세 실행을 정상 수집 성공률의 3/3으로 합치지 않는다.
