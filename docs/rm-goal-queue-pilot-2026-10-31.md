# P4: 지속 RM·우선순위 목표 대기열·S1 head RL

**학습/성능 19회 완료. 개발 비교는 초기 head 5/5, 후보 4/5 성공이며 후보를 승격하지 않는다.**
별도 실제 STOP 검사도 통과했으며 모든 게임/학습을 종료하고 STOP을 유지한다.
실행 전 [P4 프로토콜](specs/2026-10-31-queue-s1-p4.md),
[구현 계약](specs/2026-10-31-persistent-rm-goal-queue.md), [사용 안내](goal-queue-s1-usage.md).
원본은 `results/rm-goal-queue-20261031`에 보존한다. P1~P3 결과를 수정하거나 재실행하지 않았다.

## 바뀐 동작

상위 목표는 우선순위·의존성·완료 상태를 가진 대기열에 남는다. 현재 목표를 수행하는 동안에는
대기 시간이나 우선순위 수정으로 자동 선점하지 않는다. 실제 서버 인벤토리 순증가로 완료한 뒤
같은 월드와 recurrent state를 유지해 다음 실행 가능한 목표로 넘어간다. 의존성의 선행 목표는
완료만 인정하며 차단/취소를 성공으로 취급하지 않는다.

하위 단계는 현재 대상 힌트와 이미 확인한 사건 이력을 구분한다. 실제 원목 채굴이 확인되면
관측 힌트가 만료돼도 결과 회수 상태를 보존한다. 제한 안에 획득하지 못하면 이유와 과거 상태를
기록하고 차단한다. 새로운 운동 행동을 스크립트로 대신 실행하지 않는다.

현재 실행 스킬은 wood와 dirt다. 돌 수집은 목표로 저장할 수 있지만 `unsupported_skill`로
차단된다. 도구 제작·돌 채굴의 실제 정책 능력을 구현했다고 주장하지 않는다.
대기열 파일은 감사 기록이며 새로운 월드로의 자동 이어하기 기능은 아니다.

## B. 새 학습 경로와 검증 경계

공식 image/goal/recurrent backbone을 고정하고 actor/value에 search/approach/mine/collect,
현재 목표 획득 비율, 확인된 결과 회수 대기 여부의 6개 입력을 연결했다.
초기 actor의 추가 입력 열은 0, value는 0이다. 초기 정책과 후보의 비교에는 동일한 새 S1
수집기를 사용한다. 이전 P3 수집기의 실적을 초기 head 비교 표본으로 대신 쓰지 않는다.

학습 수집 4회, 제한된 offline PPO 1회, 별도 개발 seed 5개×초기/후보 2조건을 사전 고정했다.
수집 확률 재현, 데이터 적격성, 실제 gradient와 가중치 변화, 개발 성능을 구분해 확인한다.
학습 중 backbone을 GPU에 로드하지 않는 별도 trainer를 제공한다. 기존 retired 체크포인트는
복구하지 않았으며 새 후보는 공식 모델을 덮어쓰거나 자동 승격하지 않는다.

실제 학습 수집은 4회 모두 성공했고 451행동(93/94/141/123)을 사용했다. 수집 시점의
log probability 재현 최대 오차는 0이었으며, PPO 1 epoch·15 minibatch update를 실행했다.
actor 추가 입력 열 변화 L2 norm은 0.00324220, value 추가 입력 열은 0.00707184다.
optimizer 구간은 약 3.18초, PyTorch peak allocated GPU 메모리는 511.53MiB였다.
자료 수집·파일 읽기·모델 준비 시간과 전체 장치 메모리를 이 수치에 포함했다고 해석하지 않는다.
후보 SHA256은 `3e6a4df6d4b55bc84984d4f1b7a4b4abfe53d0762d902c659f843ba6f9ca2333`다.

이는 실제 가중치 갱신 확인이며 성능 향상 확인은 아니다. 학습 자료의 접근 단계는 4행동뿐이며,
수량 1 목표만 사용해 획득 비율 입력은
완료 전 항상 0이었다. 모든 단계/수량을 충분히 학습했다고 주장하지 않는다.

학습 자료의 run별·phase별 최초 실제 특징 9개를 고정해 one-hot phase만 바꾼 별도 CPU 검사에서,
초기 head의 행동 분포 차이는 0, 후보의 camera/buttons 각각의 total variation 최댓값은
약 `1.95435e-5`였다. actor 단계 열은 바뀌었지만 이 검사에서의 직접적인 영향은 매우 작다.
`goal_fraction` 열은 0 그대로다. 이 반사실 head 검사는 새로운 실제 게임·단계 입력의 성능
인과 실험이 아니며, 전체 후보 변화가 단계 정보 때문이라고 해석하지 않는다.
근거: `head-context-audit.json`과 재현 코드 `analyze-head-context.py`.

개발 seed 81033009의 후보 실행에서는 dirt 목표 중 원목 1개가 부수적으로 먼저 들어왔다.

이미 가진 자원으로 충족하는 **보유 수량** 목표를 구현했다는 의미는 아니다.

## D. 지연·자원·감사와 해석

19회·8,660 실제 정책 행동을 원본 서버 이벤트와 독립 대조해 모두 일치했다.
실행별 획득량·추론/제어 주기 중앙값·95백분위는 `analysis.json`과 `run-metrics.csv`에 보존한다.
개발 비교의 실행별 추론 중앙값은 45.95~52.09ms, 95백분위는 54.38~140.43ms였으며,
제어 주기 중앙값은 132.83~158.12ms, 95백분위는 173.36~266.81ms였다.
19회 전체에서 PNG 쓰기 중앙값은 실행별 23.54~46.17ms, 환경 step 중앙값은 40.04~57.17ms다.
서로 다른 실행/분포의 중앙값을 더해 전체 지연으로 사용하지 않는다.

정책 로드를 포함한 PyTorch peak allocated는 각 실행 1,915.00MiB였다. 다른 프로세스까지
포함한 장치 전체의 표본 최고 사용량은 실행별 2,725~2,849MiB였고 짧은 peak를 놓칠 수 있다.
이 경로에서는 자원 부족을 관측하지 않았다. 전체 backbone 학습의 자원 요구량은 검사하지 않았다.

- 고정된 privileged server 관측이 RM 단계/보상에 연결된다. 영상 전용 정책 조건의 결과로
  해석하지 않는다. 관측기/JAR는 이 배치에서 변경하지 않았다.
- dirt는 공식 영상 임베딩과 collect라는 큰 단계만 사용한다. wood 세부 단계와 동일한
  내부 단계 인식 능력이 검증된 것으로 표시하지 않는다.
- 실행당 최대 180초는 wall control 한도다. 정책 행동 하나는 server 1tick이며 게임의
  명목 시간(20tick/초)과 전체 제어 시간은 다르다.
- 학습 완료, 개발 성능 향상, 처음 보는 RM 일반화, 전체 LLM→RL 지속학습의 성공은 별개다.
- `learning-request.json`은 차단 증거를 보존할 뿐, LLM 호출/자동 학습을 실행하지 않는다.
- 이 작업의 외부 API·유료 자원·Colab 연결·GitHub 게시 0. 연구 명세 원문 보존.
- 실행 전 관련 WSL 검사 121개 통과. 배치 종료 후 아래 수정의 관련 회귀 검사 22개를
  Windows와 WSL 각각 통과했다. 실제 새 경로의 STOP도 아래 별도 실행에서 통과했다.

`work.json`과 `source-at-game`이 실행 코드·조건을 고정한다. `audit.json`은 원본 이벤트 감사,
`analysis.json`과 `run-metrics.csv`는 분리된 집계다. 초기화·취소·미실행은 성공 표본이 아니다.

## E. 배치 종료 후 기술 수정과 STOP

성능 종료 시 고정 파일 156개와 연구 명세 해시가 모두 일치했다.
원래 드라이버는 마지막 STOP helper가 queue의 중첩 bank 경로를 인식하지 못해 exit 1이었다.
실패 지점은 게임 시작 전 사전검사이며, 원래 STOP 게임 표본은 없다. 성능/학습 19회는 완료했다.

[P4.1 부록](specs/2026-10-31-queue-stop-p4-1.md)대로 배치 종료 후에만 helper의 manifest 경로를
수정했다. 별도로 reprioritize 후 select가 이전 priority 값을 반환하던 메타데이터 문제를 고쳤다.
스케줄러의 실제 순서는 이미 변경된 값을 사용하고 있었으며, 고정된 P4 성능 배치에서는
reprioritize를 호출하지 않았다. 최초 program은 불변으로 보존하고 현재 우선순위/변경 이력을
별도로 기록한다. 두 문제 모두 수정 전 재현, 수정 후 회귀 검사로 확인했다.

원래 `source-at-game`·실패 로그·실험 결과는 보존하며 두 코드 변경의 전후 해시는
`post-batch-fixes.json`에 기록했다. 수정 후 소스와 별도 STOP 자료는
`results/rm-goal-queue-stop-r1-20261031`에 보존한다. 완료한 성능 배치를 재실행하지 않았다.

별도 seed 81031999에서 queue+S1 초기 head로 실제 10행동 후 STOP를 보냈다.
요청 시작 시각/STOP 확인 이후 새 dispatch 각각 0, neutral 입력 해제 확인, held keys 0,
잔존 소유 PID 0, 정상 취소 worker exit 2였다. cleanup 7.69초, archive timeout/close 오류 없음.
검사 helper는 exit 0으로 끝났고 STOP을 유지한다. 이 10행동은 성능/학습 표본에 넣지 않는다.

요청 시작부터 acknowledgment까지 약 38.81ms의 상한을 관측했다(단일 표본).
파일 fsync가 끝나기 전에 worker가 STOP를 확인해서 fsync 완료 시각 대비 차이는 음수였다.
이를 음수 지연으로 해석하지 않으며 시작 시각 기준 상한을 사용한다. 원본/독립 검사는
`stop-probe-audit.json`, `independent-stop-audit.json`에 보존했다.

공식 가중치/구성 4개와 연구 명세 SHA256도 최종 재검사에서 그대로였다.
`candidate-decision.json`에 개발 평가 후 미승격 결정을 기록했다. 생성 당시의
`training.json`은 수정하지 않으며 그 파일의 `evaluated=false`는 생성 시점 상태다.

## 후속 학습에서 고정해서 비교할 항목

현재 451행동은 학습 경로의 첫 개발 검증이다. 다음 학습은 특정 벽/좌표에 맞춘 규칙을
추가하기보다 여러 학습 시드에서 접근·채굴·회수의 실제 경험을 확보하는 방향이 맞다.
접근 4행동과 획득 비율 입력의 무변화를 데이터 부족 근거로 남긴다.

- 먼저 단계별 경험량·실패 종류·목표 수량 범위를 사전 고정하고 학습/개발/최종 평가를 분리한다.
  이번 개발 시드를 학습에 사용한다면 더 이상 평가 시드로 재사용하지 않는다.
- 단계 입력 사용/제거 조건을 같은 학습 예산으로 비교해, 전체 head 갱신의 효과와 RM 입력의
  효과를 분리한다. 현재의 가중치 변화만으로 단계 활용이나 일반화를 주장하지 않는다.
- 보유 수량 목표, 미지원 제작/도구/돌 스킬, 세계 복원과 큐 이어하기는 별도 계약과 실제 검증이
  필요하다. JSON에 이름만 추가해 능력이 구현된 것처럼 실행하지 않는다.
