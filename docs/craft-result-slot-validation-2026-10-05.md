# 결과 칸 Shift 제한 실제 비교 — 2026-10-05

Shift 제한을 현재 2×2 인벤토리의 결과 칸으로 좁혔다. 실제 고정 시드5회에서
정확히 막대기4개·판자2개를 저장한 회차는 **3/5**, 과다 제작은 **0/5**였다.
전체 Shift 제한의2/5보다 한 회 많지만 성공 시드가 바뀌었으며, 소규모 비교의 관측값이다.
세 성공 모두 커서 회수 보조가 사용됐다. 순수 정책 개선이나 일반 제작 지원 완료가 아니다.

## 변경과 실행 조건

읽기 전용 Java 관측에 GUI 크기와 결과 칸 중심을 추가했다. MineRL의 키→커서 이동→클릭
순서에 맞춰 클릭 시점 좌표를 예측하고, 결과 칸에서는 전달할 sneak만0으로 바꾼다.
첫 관측 전과 inventory 키를 누르는 GUI 전환 행동도 Shift0으로 제한한다.
그 외 재료 이동·월드 행동은 원본 제안을 보존한다. 좌표 예측 오차가1픽셀을 넘거나
지원하지 않는 GUI를 만나면 기술 오류로 중단한다. 결과 미리보기는 획득으로 세지 않는다.

옵션은 기본 꺼짐이며 기존 전체 제한과 동시 사용을 거부한다. 레시피를 대신 선택하거나
재료를 배치하는 기능은 없다. 정책 제안과 실제 전달값을 별도로 기록한다.
[실행 전 조건](craft-result-slot-protocol.md), [전체 Shift 제한 비교](craft-shift-guard-validation-2026-10-05.md).

동일한 자연 수집→판자 제작 저장본(판자4·흙1)을 독립 복사해 STEVE-1 `craft sticks`로
실행했다. 시드 순서는130363/155921/104729/196613/262147, 각 제어 예산180초다.
Windows/WSL의 GTX1060 3GB에서 실행했고 추가 API·Colab 연결은0이다.

정확 예산 성공은 제약 없음0/5, 전체 제한2/5, 결과 칸 제한3/5다.
목표 수량 이상의 막대기 제작·저장 자체는 각각2/5,2/5,3/5다. 과다 제작은2/5,0/5,0/5다.
각 조건은 같은 저장본의5개 정책 시드이며 서로 다른5개 월드나 일반화 검증이 아니다.

시드130363은 제약 없는 원본과 이번 실행의 **정책 제안88개가 모두 동일**했다.
같은 마지막 Shift+클릭 제안에서 Shift를 제거한 뒤 막대기4개가 커서에 생성됐고,
회수·서버 확정·저장을 거쳐 판자2개가 남았다. 원본은 막대기8개로 확정됐다.
대조는 `results/craft-result-slot-paired-130363.json`에 보존했다.

실패155921는52번째 행동에 이미 작업대1개가 인벤토리에 관측됐다. 실패104729는
버튼1개를 만들어 판자3개를 남겼다. 서버/클라이언트 수량 불일치가 아니라 다른 레시피를
실제로 제작한 실패다. 제약 변경으로 행동 경로가 달라질 수 있어 특정 시드의 성공을
보장하지 않는다. 목표 외 레시피의 재료 소비를 막는 검사와 실패 후 재료 예산 판정은 남았다.

## 정지·좌표·저장 감사

- 실제 정책 행동3274개에서 sneak 외 필드가 모두 같았다. Shift 값17개를 바꾸고,
  제한 대상 밖의 Shift1 제안563개를 보존했다.
- 실제 커서 좌표2524개를 독립 계산과 대조했다. 최대 오차 약1.42e-14픽셀로 허용 범위 내다.
- 성공3회는 첫 목표 관측 후 새 추론·정책 전달0회. 모든5회는 STOP 확인 후 새 호출0회.
- 모든 실제 정책 전달은180초 이내였다. 실패 회차의 기록 종료180.06초는 진행 중인
  step 마무리를 포함한다. 제어 종료 후 커서 회수·저장 단계는 별도로 기록한다.
- 입력 해제·GUI 닫기·빈 커서·소유 자식 종료 확인, 저장 NBT5/5 일치.
- 기술 오류0, 미실행0, 원본 월드 포인터/해시 및 연구 명세 해시 유지.
- 종료 후 Windows Python/Java0개, 프로젝트 관련 WSL Python/Java0개, STOP 설정 유지.

중간 안내의 첫 시드 Shift 변경8회는 `[0]`과 `0`의 표현 차이까지 센 임시 집계였다.
최종 감사는 스칼라 값으로 정규화했으며 실제 변경3회가 맞다. 원자료와 실행은 변경하지 않았다.
기존 `craft_success`는 늦은 통계 전 즉시 정책을 멈춰 false일 수 있다. 최종 성공은
`task_success_after_cleanup`과 서버·저장 NBT로 판단하며 이 필드를 정책 실패율로 쓰지 않는다.
