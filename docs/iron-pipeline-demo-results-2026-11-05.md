## 4. 평가 (평가 seed 104729, "철 캐줘" 발화로 시작)

설계(§5.12): LLM이 "철 캐줘"에서 목표를 제안하고 프로그램이 검증 → 빈 KB(실행마다 새 SQLite) 10회 / 마지막 성공
실행의 KB를 이어받는 3회(처음부터 전체 계획). 실행당 제어 15분. 입력·코드 해시를 배치 폴더 `frozen-inputs.json`에 고정하고
실행마다 확인했다. 성공 = 서버 인벤토리 철광석 ≥ 1. 두 조건의 성공률을 합치지 않는다.

**1차 (`results/iron-demo-eval-20261105`, sampling 1~3) — 3회 뒤 중단, 0/3.**

**3차 (`results/iron-demo-eval-20261105-r3`, 2차에서 찾은 문제를 고친 뒤의 확인, sampling 41~44) — 1/4.**
수정: 틀린 지식의 사후 반박, 모호한 채굴 조건 거부, 규칙 단계 다음 정책 단계는 시선을 수평으로, 조건 가설의 `tool`은
실제 도구만. E04 **성공**(359초) — 시선 수평이 규칙 단계 뒤 5번 발동했고 마지막 철광석 단계가 134스텝(2차는 수천 스텝)으로
끝났다(1회라 근거로는 약함). E01·E02는 원목 탐색 시간 초과, E03은 LLM이 "철 캐줘"를 "인벤토리 아이템이 아닌 행동 요청"이라며
목표를 내지 않아 시작 전 종료 → 목표 해석 프롬프트 수정. 사후 반박은 발동 상황이 없어 실전 확인 못 함. 표본이 작아 2차와
성공률을 비교하는 근거가 아니다. 3b(3회, 목표 프롬프트 수정 후): 0/3 — E02는 첫 맨손 철광석 탐색 13분으로 시간 초과(정책), E01·E03은 **지식 획득 미완**: 첫 답의 일부가 열람하지 않은
출처를 인용하거나 허용되지 않은 조건 키를 써서 거부됐고, 플래너는 빠진 고리를 하나씩만 드러내므로(돌 곡괭이 → 나무 곡괭이 →
판자·막대) 정지당 2라운드로는 체인을 다 채우지 못했다. 정지당 질문 라운드를 4로 늘림(설정 `budgets.knowledge_rounds`,
실행 예산 8회 안). 그 뒤 확인 3c(1회)도 지식 미완 — "조약돌이 빠졌다"는 질문에 LLM이 4라운드 내내 "조약돌 블록은
조약돌을 떨어뜨린다"(사실이지만 쓸모없음)만 답했다. 그래서 플래너가 중간 재료에도 등록 스킬의 선언 효과(돌 캐기 → 조약돌)를
쓰고, 다시 묻는 질문에 "그 아이템을 떨어뜨리는 블록"을 명시했다. 마지막 확인 3d: **성공**(782초, API 8회 — 실행 예산 8을 모두 사용). 철광석 정지에서 3라운드로 체인을 채웠고, 원목 조건은 두 번의 짧은 정지로
보충, 구덩이는 흙 한 구간으로 지면 도달(시선 수평 3회). 한 번의 확인이며 예산이 빠듯하다는 점이 새 관찰이다.

공통 관찰:
- **가드가 지킨 것**: 모든 실행에서 맨손 철광석 손실 0. 빈 KB의 첫 맨손 철광석 공격은 매번 게임에 보내기 전에 정지.
- **시간의 대부분은 정책의 탐색**: 지식 없는 첫 단계(맨손으로 철광석 찾기)가 72~6382스텝, 마지막 철광석 채굴이
  수백~수천 스텝. LLM 대기(정지)는 실행당 수십 초.
- **실패 원인**: 시간 초과(정책 탐색) 다수, 틀린 지식 1회(E03), 탈출 블록 허비 1회(E07).

## 5. 실행하면서 찾은 문제 (모두 실제 기록에서 발견, 테스트로 고정)

1. **작업대 GUI 갇힘**: 제작 직후 정책이 앞의 작업대를 `use`로 열었고, 도구 고정이 GUI를 닫는 인벤토리 키까지 막아
   420스텝 갇힘 → 곡괭이가 제작 칸으로 옮겨져 "도구 손실" 감지. 이제 작업대를 보고 누른 `use`만 가리고, 열린 GUI는
   세션이 닫는다(기록됨).
2. **점프 꼭대기를 높이로 오판**: 서버가 꼭대기 높이를 두 번 연속 같게 보고한다. 서 있는 높이 = 두 표본이 같고
   정수 블록 높이.
3. **줍기 때문에 제작 실패**: 규칙 스킬이 인벤토리를 기록한 다음 스텝에 흙이 주워짐. 시작 전 인벤토리 안정 대기.
4. **천장 치우기 시차**: 조준 표시는 1틱 만에 `air`가 되지만 서버 파괴 수는 4틱 뒤. 기다렸다가 다시 판단.
5. **LLM의 틀린 지식**: gpt-5.4가 두 번 "1.16.5에서 철광석은 raw_iron을 떨어뜨린다"(실제는 1.17+)고 했다. 이제
   철광석을 실제로 얻으면 그 주장에 게임 반박 근거가 붙고, LLM이 인용과 함께 조건(예: `game_version ≥ 1.17`)을
   제안하면 조건부로 분리한다(설계서의 조건부 분리 장면). 평가에서 자연 발생하면 기록된다.
6. **정책 탐색 편차**: 빈 지식의 첫 단계(맨손으로 철광석 찾기)는 5~10초인 경우와 11분인 경우(A4)가 같은 seed에서도
   나왔다. 바닥만 보거나 경계벽을 오래 바라봄. 평가에서도 시간 초과의 주 원인.
7. **보호 블록 고착 → 같은 시야 재시도**(평가 1차 E01): 원목 정책이 계획상 보호 블록인 돌벽만 계속 침. 이제 재시도 전
   돌아서기(알린 규칙 행동). 2차에서 7번 발동, 재시도 뒤 원목 단계가 대부분 완료.
8. **네트워크 오류 1회로 실행 종료**(1차 E02·E03): 네트워크·429·5xx만 1회 재시도(예산 차감). D1에서 503을 실제로 복구.
9. **지면 위 탑**(D1): 탈출 구간을 고정 높이로 정해, 이미 지면에 올라왔는데도 더 쌓음. 이제 지면에 서면 완료.
10. **틀린 지식의 사후 처리 누락**(2차 E03): LLM이 "돌은 곡괭이, 등급 hand"(뜻: 아무 곡괭이)를 줘서 프로그램이
    "맨손 가능"으로 읽음 → 계획에서 나무 곡괭이가 빠지고 맨손 돌이 드롭 없이 부서짐(사후 감지 3회) → 그 지식을 반박하지
    않고 같은 KB로 재계획만 반복. 평가 뒤 적용: 허용 근거 지식에 게임 반박 → `disputed` → 관측을 담아 다시 질문,
    "도구 종류 + hand" 같은 모호한 형식 거부.
11. **조건 가설의 의미 오류**(2차 E04·E08·E10): raw_iron 주장이 게임 반박 뒤 조건부로 나뉘었지만, LLM이 조건에
    "Silk Touch"를 넣음(실제는 Silk Touch **없이** raw iron). 형식(관측 가능한 키·인용)만 검사하고 의미는 검증하지 못한다.
    현재 문맥과 맞지 않아 계획에는 영향 없음. 평가 뒤 부분 방어: 조건의 `tool`은 실제 도구 id만.
